# 실패 상황과 Fallback 설계 v0.1

상태: **설계안 — 자동 복구 미구현**. 2026-10-28의 `move_tcp.py`, `solve_tcp_ik.py`, `move_gripper.py`와 기존 검사를 기준으로 작성했다. 이번 변경은 문서만 추가하며 로봇 동작·임계값·실패 후 실행 방식을 바꾸지 않는다.

목표는 모든 실패를 복구하는 것이 아니라 **측정 가능한 실패를 구분하고, 현재 상태와 검증된 대응에 따라 계속하거나 명확히 종료하는 것**이다. 실제 제품의 형상·공차가 정해지면 파지·정렬·삽입 기준을 추가한다.

## 1. 용어와 기본 원칙

- **실패 검출:** 관측값이 작업의 전제조건·제한·완료 조건을 만족하지 않는다고 판정.
- **원인 진단:** 실패를 만든 이유를 추정. 관측 사실과 별도로 기록.
- **Fallback:** 정상 절차를 계속할 수 없을 때 선택하는 대안. 재관측, 다른 계획, 검증된 복구, 개입 요청·종료를 포함.
- **Retry:** 같은 동작을 다시 실행. 상태가 바뀐 로봇에 같은 명령을 재전송하는 것이 적절한지 먼저 확인해야 한다.
- **Recovery:** 실패한 현재 상태에서 필요한 동작을 수행하고 후조건을 만족해 작업을 이어감. 중단만 한 경우는 복구 성공으로 세지 않는다.

실패마다 `검출 조건 / 관측 증거 / 즉시 대응 / 재개 전제조건 / 허용 복구 / 종료 조건 / 시험 방법`을 연결한다. 장면을 초기화하고 다시 성공한 것은 새 trial의 성공이며 이전 실패의 복구 성공이 아니다.

예를 들어 `TCP 위치 오차가 10.86mm다`는 관측이다. `중력 보상이 빠졌다`는 원인 설명이다. 개발자가 보상을 꺼서 만든 실험에서는 원인을 알지만, 실제 실행에서는 목표 설정·제어·접촉 등 다른 원인도 가능하다. 제어기가 원인을 관측으로 구별하지 못하면 `unknown`으로 남긴다.

## 2. 현재 코드에 연결할 실패 분류

아래 코드는 **추가할 공통 보고 형식의 이름**이다. 현재는 예외 문장과 판정 항목으로 구현되어 있으며 이 enum이나 자동 복구가 존재하는 것은 아니다.

| 제안 코드 | 검출 조건과 증거 | 즉시 대응 및 이후 후보 | 현재 상태 |
|---|---|---|---|
| `INPUT_OR_PRECONDITION_INVALID` | 잘못된 pose·회전, 지원하지 않는 초기 상태, 계획과 현재 시작 상태 불일치. 명시적 단위·좌표계 불일치는 공통 입력 계약 도입 후 검사 | 실행 금지. 입력·현재 관측을 확인하고 새 계획. 목표 의미를 임의 변경하지 않음 | 형식·초기 상태 검사 있음. 단위/frame 계약은 미구현 |
| `MODEL_OR_CONTROL_INVALID` | 예상과 다른 TCP/모터 구조, 모델 불일치 | 중단 후 개발 설정 수정·재검증. 런타임 LLM이 구조·게인을 수정하지 않음 | 구조 검사 있음 |
| `IK_NOT_CONVERGED` | 유효한 입력에 대해 200회 내 오차 기준 미달 또는 QP solver 해 탐색 실패. 반복 수·잔차·solver 이유 기록 | 물리 실행 금지. 검증된 다른 초기 추정 각도 또는 허용 접근 자세의 계획을 검토 | 제한된 IK 및 실패 반환 있음 |
| `PLANNED_CONTACT` | IK 후보 또는 명목 경로 후보에서 허용되지 않은 접촉 검출. 후보 각도·충돌 쌍·검사 단계 기록 | 해당 계획 거부. 다른 경로를 계산·검증할 수 없으면 종료 | 후보·경로 샘플 검사 있음 |
| `UNEXPECTED_CONTACT` | 실제 실행 중 그 단계에서 허용하지 않은 접촉 검출. 발생 시각·충돌 쌍·깊이·현재 상태 기록 | 실행 중단, 상태 확인. 현재 버전은 종료. 검증되지 않은 자동 후퇴 금지 | 빈 그리퍼 이동 검사·실패 주입 시험 있음 |
| `MOTION_LIMIT_EXCEEDED` | 관절 범위, 속도, 목표 추종 오차, 모터 입력 제한 위반. 세부 유형과 실제값/한계 기록 | 실행 중단. 위반 이유와 현재 상태 확인 전에는 동작 재개하지 않음 | 각 제한 검사 있음 |
| `TCP_NOT_REACHED` | 7초 실행 후 마지막 0.5초 중 위치 오차 >1mm 또는 방향 오차 >0.5도 | 목표 미도달로 판정. 현재 상태·제어 설정·접촉 정보를 확인. 같은 명령 무조건 반복 금지 | 실제 TCP 기반 판정 있음 |
| `NOT_SETTLED` | 마지막 0.5초 중 관절 속도 >=0.5도/초, TCP 속도 >=1mm/초 또는 TCP 각속도 >=0.5도/초 | 안정 미확보. 아래의 제한된 추가 안정화 조건을 만족할 때만 연장 후보 검토 | 각각의 속도 판정 있음 |
| `GRIPPER_STATE_INVALID` | 열린 이동에서 패드 간격 80~90mm 밖, 양쪽 구동 관절 차이 >0.5도, 연결 잔차 >0.2mm | 이동 중단. 열린 상태·모델·관측 재확인. 물체 파지 여부로 잘못 해석하지 않음 | 그리퍼 상태 검사 있음 |
| `SIMULATION_INVALID` | NaN/Inf, 엔진 경고, 예상과 다른 물리 시간 | 시뮬레이션 종료. 해당 상태를 유효한 복구 시작점이나 성공 근거로 사용하지 않음 | 오류 검사 있음 |

주의할 구분:

- `IK_NOT_CONVERGED`는 도달 불가능의 증명이 아니다. 기존 계획서의 포괄적인 `UNREACHABLE` 대신 이 관측 가능한 표현을 사용한다.
- `PLANNED_CONTACT`는 가상 후보의 거부이고, `UNEXPECTED_CONTACT`는 실행 중 접촉이다. 하나의 `COLLISION` 코드만으로 합치지 않는다.
- `MOTION_LIMIT_EXCEEDED`의 현재 세부 기준은 전체 관절 속도 >15도/초, 팔 추종 오차 >2도, 관절 정지점 초과 >0.001rad, 보상된 모터 입력의 범위 초과다. 이 값들은 현재 데모의 검증 기준이며 모든 작업의 범용 기준이 아니다.
- 여러 조건이 동시에 실패할 수 있다. 대표 코드와 `violations[]`를 함께 기록하며, 상태 무효·미확인·접촉·제한 위반은 단순 목표 미도달보다 먼저 처리한다.
- 중력 보상 누락과 명령 갱신 정지는 서로 다른 **주입 원인**이지만, 관측이 동일하면 모두 `TCP_NOT_REACHED`가 될 수 있다.

사용자가 창을 닫은 경우는 `status=cancelled`, 기록이 빠진 경우는 `INCOMPLETE_RECORD`로 구분한다. 현재 프로그램은 둘 다 실패 종료하지만 향후 복구기는 사용자 취소 후 자동 재시작하지 않는다. 연결 중단으로 명령 수행 여부가 불명확한 실물 상황은 아래의 `EXECUTION_UNKNOWN`으로 다룬다.

## 3. 파지·조립·실물 단계에서 추가할 분류

다음 항목은 **아직 검출기·복구기 미구현**이다. 임계값은 부품과 센서를 정한 뒤 시험 전에 고정한다. 현재 자유 공간 이동의 1mm 기준을 삽입 성공 기준으로 그대로 복사하지 않는다.

| 제안 코드 | 관측 가능한 정의 | 복구 후보와 전제조건 |
|---|---|---|
| `OBJECT_UNAVAILABLE` | 신뢰할 수 있는 관측에서 필요한 부품이 없거나 사용 불가 | 다시 관측하거나 독립적인 다른 작업을 먼저 수행. 가려서 안 보이는 경우는 존재하지 않음으로 단정하지 않음 |
| `GRASP_NOT_CONFIRMED` | 닫힘 후 작은 검증 리프트에서 물체가 들리지 않거나 그리퍼와의 상대 자세를 유지하지 못함 | 물체 위치·지지 상태·그리퍼 비어 있음을 확인한 후 허용된 다른 파지 후보 검증. 그리퍼 닫힘만으로 파지 성공 선언 금지 |
| `PART_LOST` | 확인된 파지 이후 물체와 그리퍼의 상대 자세가 허용치를 벗어나거나 물체 낙하 관측 | 이동 중단 후 물체·주변 조립 상태 확인. 안정적으로 놓인 위치에서만 재파지 후보 검토 |
| `ALIGNMENT_OUT_OF_TOLERANCE` | 파지 부품과 결합 대상 사이의 상대 위치·방향이 기준 밖 | 접촉 전 자유 공간에서만 허용 정렬 후보 검증. 자세 오차의 관측 신뢰도가 충분해야 함 |
| `INSERTION_INCOMPLETE` | 정해진 시간/이동 예산 내 삽입 깊이·자세 후조건 미달 | 원인 미확정 상태에서 더 세게 밀지 않음. 접촉·파지·후퇴 경로가 확인되고 별도 후퇴 스킬이 검증된 경우만 후퇴·재정렬 후보 검토 |
| `PLACEMENT_UNSTABLE` | 놓은 뒤 물체가 허용 영역을 벗어나거나 안정 시간 동안 계속 움직임 | 지지·현재 자세 확인 후 재배치 후보 검토. 사람이 고쳐 놓으면 개입으로 기록 |
| `OBSERVATION_UNCERTAIN` | 관측 누락·오래된 관측·가림·필요 정확도 미달 | 제한된 재관측. 확인할 수 없으면 종료/개입 요청. 없는 측정값을 0으로 채우지 않음 |
| `EXECUTION_UNKNOWN` | 명령이 전달되었을 수 있지만 완료 응답을 못 받아 수행 여부 불명 | 동작 ID 조회와 새 관측으로 확인할 때까지 재전송 금지. 단순 API timeout과 물리 명령 timeout을 구분 |

삽입 단계에서는 접촉 자체가 정상일 수 있다. `스킬 단계 + 부품/표면 쌍 + 접촉 조건`으로 허용 접촉 정책을 정의한다. 상대 속도·접촉력 등을 사용하려면 해당 값을 신뢰할 수 있게 측정할 수 있어야 한다. 없는 힘 센서나 미검증 토크 추정을 근거로 “끼임을 검출했다”고 주장하지 않는다.

`INVALID_PLAN`, `BUDGET_EXCEEDED`, API 오류 등은 에이전트 계층의 실패로 따로 기록한다. 계획 형식 오류 수정이나 API 재요청이 물리 동작 재시도를 자동으로 발생시키지 않게 한다.

## 4. Fallback 결정 구조

```text
실패 검출 → 실행 보류/중단 → 증거 보존 → 현재 상태 다시 확인
                                      ├─ 취소·상태 무효·미확인 → 종료/개입 요청
                                      └─ 상태 확인됨 → 허용된 복구 후보 확인
                                                       ├─ 후보 없음/예산 소진 → 종료
                                                       └─ 후보 있음 → 조건·경로 검증
                                                                    → 제한 실행 → 후조건 재검사
```

규칙 기반 실행 계층이 접촉·속도·관절 제한과 관측 유효성을 검사한다. LLM 응답을 기다리는 동안 계속 움직이지 않는다. 시뮬레이션에서 시간을 멈추는 것과 실물의 감속·정지·하중 유지 제어는 다르며, 후자는 실물 adapter와 로봇 제어기에서 따로 구현·검증해야 한다.

복구는 다음 순서로 확장한다.

1. **기록하고 종료:** 현재 동작을 유지하면서 오류 문장을 구조화한 보고서로 바꾸는 첫 구현.
2. **검증된 고정 규칙:** 적용 조건이 좁고 명확한 복구 하나씩 추가. 아직 자동 실행 가능한 항목은 없다.
3. **단일 LLM의 선택:** 현재 관측과 보고서를 받아 이미 검증된 후보 중 하나와 허용 파라미터를 제안. 일반 코드가 다시 검증한 뒤 실행.

복구 후보는 `필요 관측 / 적용 전제조건 / 변경 가능한 파라미터 범위 / 중단 조건 / 완료 조건 / 검증 이력`을 가진다. LLM은 성공 임계값을 완화하거나 관절·힘 제한을 해제할 수 없다. 런타임에 임의 제어 코드를 생성·실행하지 않는다.

### 작은 복구 후보의 범위

- **다른 IK 초기 추정 각도:** 계산에서 다른 출발점을 써 해를 다시 찾는 방법이다. 실제 로봇을 그 각도로 순간 이동시키지 않는다. 최종 작업 목표를 유지하고 실제 현재 자세부터의 경로를 새로 검증해야 한다.
- **제한된 추가 안정화:** 단순 `NOT_SETTLED`에서만 후보로 둔다. 접촉·제한 위반이 없고 관측이 유효하며 오차가 허용된 경향으로 감소하는 것을 확인해야 한다. 1초 연장 1회는 초기 제안이며 별도 물리 시험 전 자동 실행하지 않는다. 목표에 못 간 채 정지한 경우의 일반 해결책으로 사용하지 않는다.
- **접근 경로 변경:** 작업 목표를 유지하고 허용된 중간 접근점만 변경한다. 지금은 대체 경로 생성·현재 상태에서의 재개가 없어 자동 사용 불가다.
- **접촉 후 후퇴:** 마지막 명령을 거꾸로 재생하거나 무조건 위로 이동하지 않는다. 실패 후 부품·그리퍼·조립 상태에서 후퇴가 가능한지 확인하고 검증된 후퇴 기능이 있을 때만 후보가 된다. 초기 범위에서는 종료한다.

`move_tcp.py`는 현재 초기 home 상태에서만 실행한다. 따라서 중간 상태에서 이 함수를 다시 호출하거나 home으로 reset하는 동작을 복구라고 포장하지 않는다. 현재 상태를 시작점으로 받는 실행기와 재관측·경로 재검증을 구현하기 전에는 자동 재개하지 않는다.

제안 예산은 기존 계획서와 맞춰 에피소드당 재계획 최대 2회, LLM 요청 최대 8회로 둔다. 물리 복구는 실패한 단계당 최대 1회, 에피소드 전체 최대 2회로 제한하는 안이다. 동일 단계에 새 action ID를 붙여 예산을 초기화하지 않는다. 복구 계획이 검증에서 거부된 경우도 재계획 예산을 사용한다. 각 동작의 시간·거리·힘 제한은 복구 스킬별로 고정한다. **이 예산은 설계 제안이며 현재 실행 코드의 동작은 실패 시 종료다.**

## 5. 실패 보고서에 남길 정보

`FailureReport`는 다음 최소 정보를 갖도록 제안한다. 실제 schema 구현은 다음 단계다.

| 정보 | 필요한 이유 |
|---|---|
| run/episode/action ID, 원래 단계 ID, attempt 번호, 발생 단계·시각 | 같은 실패와 재시도를 연결하고 예산 우회 방지 |
| status, 대표 error code, 전체 violations | 취소·미완료·작업 실패·상태 미확인을 구분 |
| goal, 관측값, 단위·좌표계, 판정 임계값·검증 프로파일 버전 | 무엇을 달성하지 못했는지 객관적으로 확인 |
| 실제 관절 각도·속도, TCP, 입력 명령, 접촉 쌍과 거리 | 다음 동작의 출발 상태와 실패 근거 |
| 관측 source·시각·revision·유효성, 물체/파지/조립 진행 상태 | 오래되거나 불명확한 상태로 복구하는 것을 방지 |
| 마지막 정상 관측과 실패 시점 관측의 참조 | 중간에 검사가 예외를 던져도 증거 보존 |
| 관측 사실과 별도의 원인 가설, 가설의 근거 | “삽입 깊이 부족”을 곧바로 “마찰 문제”로 단정하지 않음 |
| 후보 대응·허용 근거·남은 예산, 모델/스킬 버전 | 조건에 맞는 대응만 선택하고 이후 경험 검색에 활용 |

유효하지 않아 읽을 수 없는 값은 `null`과 누락 이유를 남긴다. 잘못된 물리 상태에서 추가 계산을 강행해 정상 관측처럼 채우지 않는다. LLM에는 필요한 수치와 관련 로그 참조만 제공하고 매 2ms의 CSV 전체를 매번 보내지 않는다.

현재 CSV는 접촉 검사에서 예외가 발생한 순간의 행을 기록하기 전에 중단될 수 있다. 따라서 **실패 코드만 붙이는 작업과 함께 마지막 정상 상태·확보 가능한 실패 시점 상태를 별도 보고서로 남겨야 한다.** 실패 로그 저장 자체가 실패해도 실행을 계속하지 않으며 로그 오류를 별도로 알린다.

10부품 조립에서는 이미 확인된 조립 상태를 보존하되, 충돌로 영향을 받은 부품·주변 관계는 다시 관측한다. 과거에 성공했던 단계라도 현재 무효가 되었을 수 있다. 단계 번호만 복구 지점으로 사용하지 않는다.

## 6. 첫 실패 시나리오와 평가

당장 새 복구 동작을 많이 만들지 않고 다음 사례의 분류·증거 보존부터 고정한다.

| 시나리오 | 만드는 방법 | 기대 결과 | 현재 확인 범위 |
|---|---|---|---|
| S0 정상 대조 | 현재의 위쪽 30mm 이동 | 정상 동작을 실패로 오인하지 않음 | 물리 도착 시험 있음 |
| S1 IK 계산 실패 | 유효 입력에서 계산 예산 축소 또는 관절 범위 제한 | `IK_NOT_CONVERGED`, 물리 실행 없음 | 기존 IK 검사 있음. 일반적인 도달 불가 판정은 아님 |
| S2 계획 중 접촉 | 물리 실행 전 후보 경로에 장애물 배치 | `PLANNED_CONTACT`, 실행 없음 | 후보 검사 있음. 경로 중간만 막는 전용 사례는 추가 필요 |
| S3 실행 중 접촉 | 2초 시점에 테스트용 장애물을 그리퍼에 배치 | `UNEXPECTED_CONTACT`, 중단·증거 보존 | 실제 MuJoCo 접촉·중단 시험 있음. 공통 보고서는 미구현 |
| S4 안정됐지만 미도달 | 중력 보상을 끄거나 명령을 초기 각도에 유지 | `TCP_NOT_REACHED`, 원인은 관측과 별도로 기록 | 두 물리 실패 시험 있음 |
| S5 중단/불완전 기록 | 창 닫기 또는 마지막 구간 기록 제거 | 취소/미완료 구분, 자동 재개 없음 | 중단 처리·미완료 기록 거부 있음. 공통 상태 구분은 미구현 |

장애물 순간 배치, 제어 코드 주입 등은 검출기를 시험하는 **실패 주입**이다. 현실적인 자연 실패 빈도를 대표하지 않으며 복구 성공으로 세지 않는다. 실물에서 충돌이나 끼임을 고의로 재현하는 것을 필수 실험으로 요구하지 않는다.

부품 도입 후에는 `파지 대상 위치 변화 → 파지 미확인`, `결합 대상 상대 위치 변화 → 정렬/삽입 미완료`, `관측 누락 → 재관측/종료`를 우선 추가한다. 제품별 형상·공차와 감지 가능한 신호를 먼저 정하고, 평가 전에 변화 범위와 성공 임계값을 고정한다. 힘·마찰에 대한 해석은 해당 관측을 검증한 후 추가한다.

평가는 검출과 복구를 분리한다.

- **실패 검출:** 검출해야 할 실패 중 검출 비율, 정상 동작의 오검출 비율, 검출 지연.
- **대응 적절성:** 재시도 금지 상황에서 재시도하지 않았는지, 예산·작업 제한을 지켰는지.
- **복구:** 사전에 정의한 복구 대상 실패 중, 장면 reset·사람 개입 없이 후조건을 만족한 비율. 후보 생성 성공과 실제 복구 성공을 분리.
- **전체 작업:** 최초 성공, 복구 후 성공, 종료/개입, 시간·토큰·비용을 구분. 실패와 재시도 비용도 포함.

주입한 원인은 평가용 정답으로 별도 보관하고 운영 정책/LLM/메모리 검색 입력에는 넣지 않는다. 초기 시뮬레이션의 실제 상태 관측은 `sim_ground_truth`라고 표시한다. 나중에 카메라 관측을 평가할 때는 운영 정책에 숨겨진 정답 위치를 넘기지 않는다.

조건별 정상·실패를 함께 시험하고, 복구가 불가능하도록 정한 사례도 포함한다. 모든 사례가 “재시도 한 번이면 해결”되게 구성하지 않는다. 먼저 고정 규칙을 검증한 뒤 동일한 도구·예산에서 단일 LLM과 메모리의 효과를 비교한다.

## 7. 스킬·메모리 및 참고 연구와의 연결

복구를 실행한 경험에는 `실패 특징 → 확인한 상태 → 적용 조건 → 복구 행동·파라미터 → 재검증 결과`를 저장한다. 실패한 복구도 남기고, 모델·부품·스킬·관측 방식이 달라지면 그대로 검증된 규칙으로 취급하지 않는다. 단일 성공을 범용 스킬의 검증 완료로 승격하지 않는다. 시뮬레이션과 실물 검증 이력은 분리한다.

[ASPIRE 공식 프로젝트](https://research.nvidia.com/labs/gear/aspire/)는 관측·입출력·실행 흔적을 살펴 실패를 진단하고, 수정한 행동을 실행 검증한 뒤 재사용 가능한 스킬로 축적한다. 여기서는 **실행 근거에 기반한 수정과 재검증**을 참고한다. 프로그램 탐색·자동 코드 생성 전체를 이번 4주 구현에 포함하지 않는다. 공식 페이지의 서지 표기는 2026 arXiv preprint이며 IEEE 논문으로 소개하지 않는다.

[IROSA 공식 프로젝트](https://markusknauer.github.io/projects/irosa/)는 IEEE RA-L 2026의 산업용 베어링 링 삽입 사례로, LLM이 검증된 도구를 선택하고 파라미터를 지정하는 구조를 제시한다. 여기서는 **LLM의 선택과 하위 실행 도구의 경계**를 참고한다. 자연어로 스킬을 조정하는 연구이며 우리 프로젝트의 자동 실패 복구가 검증됐다는 근거는 아니다.

## 8. 다음 구현 단위

다음 한 단계는 **공통 실패 코드 + 구조화된 FailureReport + 현재 사례의 분류·기록 검사**다. 지금의 중단 정책을 유지하면서 S0/S1/S3/S4/S5를 명확히 구분하고, 실패 시점 증거를 저장한다. 새로운 자동 복구 이동이나 LLM 호출은 이 단계에 묶지 않는다.

이후에는 적용 조건이 명확한 복구 하나를 골라 정상·회복 가능·회복 불가 사례에서 검증한다. 그 검증이 끝나면 같은 선택지를 단일 LangGraph 에이전트에 제공한다.
