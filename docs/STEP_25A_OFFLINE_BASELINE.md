# 25A단계: 공통 조건의 규칙 기준선과 평가 기록

작성: 2026-11-01. 최종 성능 평가 전에 집계와 비교 조건이 올바른지 확인하는 개발용 시험이다.

## 왜 지금 만드는가

나중에 모델을 바꾸기 전에, 같은 물리 조건·도구·허용 행동·복구 예산을 적용했는지 확인할 틀이 필요하다. 현재는 LLM 대신 같은 규칙 정책을 `single`과 `roles` 두 구성으로 실행한다. 두 구성의 차이는 역할 인계 구조이고, 판단 내용은 동일하다.

`benchmark_assembly.py`는 다음 세 조건을 각각 두 구성에서 실제 MuJoCo로 실행한다.

| 조건 | 복구 한도 | 기대 동작 |
|---|---:|---|
| 정상 | 1 | 삽입 성공, 복구 0회 |
| 정렬 오차 6mm | 0 | 하강 전 실패 검출 후 종료 |
| 정렬 오차 6mm | 1 | 재관측·재정렬 후 삽입 성공 |

“예상대로 실패를 감지했다”는 프로그램 검사 통과다. 이를 “물리 조립 성공”으로 집계하지 않는다. 성공은 해제·지지·깊이·자세·속도 측정 근거가 있어야 인정한다.

## 실행과 결과

```powershell
uv run --locked python scripts/benchmark_assembly.py --repetitions 1
uv run --locked python -m unittest discover -s tests -p test_benchmark_metrics.py -v
```

실제 실행: `runs/step25_baseline/20261101T053132_441032Z_b741f3a0`.

| 조건 | single 조립 성공 | roles 조립 성공 | 각 sim 시간 | 각 정책 호출 |
|---|---|---|---:|---:|
| 정상 | 성공 | 성공 | 73.356초 | 3 |
| 오정렬·복구 없음 | 실패 | 실패 | 49.710초 | 2 |
| 오정렬·복구 있음 | 성공 | 성공 | 86.752초 | 5 |

6회 중 4회가 물리 조립 성공이다. 나머지 2회는 의도적으로 복구를 꺼 실패했다. 예상 동작 검사로는 6/6 통과했다. 복구가 허용된 오정렬 사례 2회는 모두 복구 후 완료했다. 서로 다른 조건을 합친 4/6을 시스템의 일반 성공률로 발표하지 않는다.

API 호출, 입력/출력 토큰, API 비용은 모두 0이다. 정책 호출은 Python 판단 함수 호출 횟수다. 모델 호출 횟수와 동일한 개념으로 취급하지 않는다.

집계 계약 검사 4개가 통과했다. 예상 실패/조립 성공 구분, 성공 측정 근거 누락 거부, 실물·API 기록을 오프라인 결과로 잘못 집계하는 경우 거부, 중도 취소를 예상 실패와 구분하는 내용을 검사했다.

## 출력 파일

- `suite_manifest.json`: 시험 조건, 정책 구성, 반복 수, 구현 파일 지문.
- `episodes/`: 각 실제 실행의 관측·CSV·실패·그래프 상태.
- `metrics.csv`: 조건별 성공·복구·시간·정책 호출·비용 지표.
- `summary.json`, `REPORT.md`: 집계와 읽기 쉬운 결과 표.
- `progress.json`: 중간에 중단되더라도 완료한 실행의 결과 보존.

## 최종 평가와의 차이

이 결과는 LLM 단일/멀티, 모델, 스킬/메모리의 우위를 증명하지 않는다. 규칙 정책의 판단이 같으므로 같은 결과가 정상이다. 앞으로 실제 API 정책과 선택 가능한 대안을 연결한 뒤, 동결된 시험 작업에서 비교해야 한다.

현재 시험은 결정론적인 개발 장면이며 조건당 1회다. 반복 수를 늘리는 것만으로 새로운 작업에 대한 일반화 평가가 되지 않는다. 다른 시뮬레이션과 함께 실행했으므로 wall time은 기록용이고 계산 성능 비교에 사용하지 않는다. 최종 평가에서는 정상/실패 조건별 성공률, 실패 발생 건수 대비 복구 후 완료율, 전체 시스템 토큰·비용, 개입 횟수와 실행 시간을 함께 보고한다.
