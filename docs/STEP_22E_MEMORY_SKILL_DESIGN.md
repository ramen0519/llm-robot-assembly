# 22E — Memory·Lesson·Python Skill 구조 적용 설계

작성: 2026-11-10. 상태: **설계 정리 완료 / 새 기능 구현·실행 미완료**.

사용자 요청: 분해 프로젝트에서 개선한 메모리·스킬 구조를 조립 프로젝트에도 적용하고, 기존 구현과 비교해 재사용·수정·신규 구현 범위를 정리한다.

이번 변경은 문서뿐이다. 코드·환경·기존 실행 결과를 변경하지 않았으며 API·MuJoCo·실물 실행과 테스트 재실행은 하지 않았다. 최신 21N의 9개 연속 설치를 새 메모리·스킬의 성과로 계산하지 않는다.

## 1. 적용 결정

기존 로봇 실행기와 검증기를 유지하면서 **실제 관측 Memory → 근거 있는 Lesson → 제한 Python Skill 생성 → MuJoCo 검증 → 조건부 등록·동결 → 다음 작업에서 재사용** 구조를 추가한다.

이 요청으로 자동 스킬 생성을 계속 후속으로 두던 초기 계획을 갱신한다. 허용하는 것은 **별도 학습 단계에서 현재 실행기가 이해하는 행동·파지 값을 제안하는 제한 Python을 생성하고 검증하는 것**이다. 조립 실행 중 자유 Python을 즉시 실행하거나 IK·제어기·검사 기준을 생성 코드로 교체하는 기능이 아니다.

초기 조립 실행 정책은 현재 단일 Luna를 유지한다. 학습은 별도 회차로 수행하고, 실행 시작 전에 사용할 지식 버전을 동결한다. 실제 멀티에이전트 구조 비교는 이 기준선을 확보한 뒤 같은 도구·관측·지식·전체 예산으로 진행한다. 분해 프로젝트의 별도 API 승인/예산을 조립 작업에 전용하지 않는다.

실제 현재 경험 저장은 JSON 파일이다. 초기 문서의 SQLite 설계를 구현 완료로 해석하지 않는다.

### 현재 코드에서 확인한 연결 제한

- scripts/experience_memory.py는 four_post_frame_first_joint/v1과 첫 기둥 검사 조건에 결합돼 있다.
- scripts/skill_recipes.py는 generation_method=fixed_template_from_recorded_sequence, contains_generated_python=False를 강제한다.
- scripts/frozen_knowledge.py는 현재 구현 hash와 정확한 조건 일치를 요구한다.
- scripts/assembly_graph.py에는 memory_lookup과 recipe_summaries 전달 훅이 있다.
- scripts/openai_policy.py에는 경험/레시피 입력이 있지만 현재 실행 정책은 Python/새 스킬 생성 요청을 하지 않는다.
- scripts/run_assembly_graph.py의 수치 파지 모드는 use_memory/knowledge_bundle/recipe 동시 사용을 거부한다.
- scripts/run_frame_assembly.py의 live 그래프 호출에는 memory_lookup/recipe_summaries/condition_fingerprint가 전달되지 않는다.

따라서 옵션 하나를 켜거나 가드를 삭제하는 것으로 연결이 끝나지 않는다. 새 입력·상태·검증 계약을 확인한 후 지원되는 조합만 단계적으로 허용한다.

python_skill_program.py, skill_validation.py, skill_registry.py 전체는 분해 request/result·pose·support 계약에 결합돼 있다. 그대로 import하지 않고 공통 부분과 도메인 연결 부분을 분리한다. 분해 저장소가 변경되면 조립이 동시에 바뀌는 실시간 cross-repo import를 사용하지 않는다.

현재 등록된 지지쌍 선택 코드, RedMax 성공 판정, 과거 부품 ID·자세는 로봇 조립용 검증 스킬로 옮기지 않는다. 분해의 제한 Python과 같은 표현을 사용해도 새로운 MuJoCo 검증이 필요하다. 분해 검색에서 발견한 수락/시간 정보 중복 제거 문제도 복사하지 않는다.

## 4. 새로 정의할 데이터와 실행 계약

아래 이름은 계획이며 아직 제공되는 CLI나 구현된 클래스가 아니다.

### 4.1 AssemblyExperience v2 — 실제 관측

최소 기록 항목:

- episode/task/part/joint/attempt/evidence ID와 실패→수정 parent ID.
- observation_revision, 실행 전후 관측 참조, 당시 설치 완료 부품 목록.
- 부품 형상·치수·결합/지그 조건, 로봇·그리퍼·TCP·단위·좌표계.
- 제안한 파지 x_mm/y_mm/z_mm/jaw_yaw_deg, 바꾼 값, 실제 실행한 값.
- 단계: 사전검사 / 실제 실행 / 실행 후 검증 / 회차 전체 판정.
- 검사 수락 여부, 명령 제출·완료 여부, 실행 여부 불확실, 시간 초과·중단 이유.
- 접촉 쌍·측정 오차·패드 여유·삽입 깊이와 원시 FailureReport/검증 결과 참조.
- MuJoCo·모델·기본 스킬·검사기·실행 코드 버전, source run/event/file hash.
- 실제 모델/규칙/fixture 구분, 개발/등록/평가 구분, 비용·시간 근거 참조.

제안 거절, 실제 실행 실패, 실제 설치 성공은 다른 사건으로 보존한다. 없던 관측은 null/unknown이며 과거 기록을 추정으로 채우지 않는다. 과거 코드의 실제 관측은 그 버전의 참고 근거로 가져올 수 있지만 현재 코드로 재검증된 스킬이라고 승격하지 않는다.

v1 기록은 그대로 남기고 v2 reader/exporter를 추가한다. 분해/조립/실물의 기록 공간을 분리한다. 원시 trace 전체를 프롬프트에 넣지 않고 필요한 수치와 출처 참조를 제공한다.

### 4.2 검색 — 호환성과 관련성을 분리

1. 도메인·로봇/그리퍼·좌표/단위·지원 행동을 구분한다. 검증 스킬은 현재 실행 계약과 코드 범위가 호환돼야 한다.
2. 정확한 조건 일치 경험을 우선한다.
3. 다른 배치/치수는 작업 종류·형상 역할·결합 방식·실패 근거 등 선언한 특징으로 관련성을 정렬한다.
4. 실패와 수정 성공을 함께 제공하고 부모 연결을 보존한다. 실제 실행 여부·수락·시간 계약이 다른 기록을 중복으로 합치지 않는다.
5. 초기에는 기존 규모에 맞춰 최대3개 경험을 제공하고, 스킬도 작은 고정 상한을 둔다. 적용 불가·불확실·한도 초과를 기록한다.

유사 경험은 참고 가설이지 좌표 재생 허가가 아니다. 배치가 달라도 부품 좌표계·현재 형상으로 다시 계산하고 MuJoCo로 검사한다. 초기에는 JSON과 결정적 검색을 유지하며 벡터 DB·별도 검색 API는 도입하지 않는다. v1 동결 묶음의 엄격한 검사를 완화하지 않고 새 의미를 v2로 구분한다.

### 4.3 Lesson — 근거 있는 설명

제목, 가설, 적용·비적용 조건, 관측된 trigger, 근거·반례 ID, 관련 후보 코드 hash, 검증 범위를 저장한다. 관측된 접촉과 LLM의 원인 추측을 구분한다. 근거 ID 검사만으로 설명의 인과관계가 입증됐다고 하지 않는다.

### 4.4 GeneratedAssemblySkill — 제한 Python

처음에는 propose(ctx)가 **현재 허용된 다음 행동과 파지 수정 후보 또는 보류(None)**를 반환하도록 한다. 문맥은 복사한 읽기 전용 데이터이며 제안은 호스트가 현재 part/target/revision에 바인딩해 검사한다.

초기 허용 범위는 현재 위쪽 접근의 네 파지 수치와 기존 허용 행동이다. 임의 6D 파지, 새로운 waypoint, 힘·속도 제어는 기존 계약에 없으므로 별도 기본 동작 구현·검증 전에는 허용하지 않는다.

생성 함수는 MuJoCo 객체, qpos/ctrl, skills.pick(), 파일/네트워크, 검증기 수정 권한을 갖지 않는다. 스킬 등록은 현재 장면에서 파지를 승인했다는 뜻이 아니다. 장면 snapshot/revision, 승인 파지와 실행 파지 일치, 이동 중 충돌·파지 상태, 최종 설치 결과를 기존 경로에서 계속 검사한다.

실행 정책은 등록 스킬을 선택하거나 직접 파지를 제안한다. 별도 학습기가 코드를 생성하므로 기존 실행 프롬프트의 임의 Python 생성 금지를 단순 삭제할 필요는 없다. 새로운 선택 형식과 실제 실행기의 계약을 함께 검증한다.

## 5. 첫 사례: 첫 기둥의 파지 사전검사 거절을 줄이기

1. Luna가 기둥 파지를 제안한다.
2. 사전검사에서 삽입 중 손가락과 소켓 테두리의 간섭을 측정한다. 본 장면에서는 아직 집지 않은 상태다.
3. Memory에 제안 수치, 접촉/여유, 거절, 후속 수정과 실제 설치 결과를 연결한다.
4. Lesson에 이 조건에서 파지 높이 변경을 검토할 근거와 제한을 적는다.
5. Python 후보가 현재 패드 여유·기둥 치수·이전 파지로 새 높이를 계산한다. 성공했던 높이 하나를 모든 부품에 복사하지 않는다.
6. 형식·범위 검사와 기존 집기~삽입 사전검사를 통과한 후보만 본 장면에서 실행한다.
7. 해제·후퇴 뒤 실제 설치 결과를 검증하고 개발/등록 조건을 분리해 기록한다.
8. 다음 회차 전에 동결하고 Luna가 선택해 재사용한다.

이 사례는 **본 실행 전 파지 제안 수정**이다. 물체를 쥔 채 발생한 실제 조립 실패의 복구 성공과 구분한다. 파지 중 파지 위치를 바꾸려면 관측·놓기·재파지 같은 별도 검증 절차가 필요하다.

## 6. 작은 구현 단위와 성공 기준

| 순서 | 구현 단위 | 통과 기준 |
|---|---|---|
| 1 | 실제 로그 → AssemblyExperience v2 exporter | 기존 기둥/21N 기록의 제안·거절·실제 설치를 출처와 연결, 누락은 unknown, 원본·v1 불변. API/새 물리 실행 없이 검증 가능 |
| 2 | v2 조회·동결과 첫 기둥 수치 파지 연결 | 실제 모델 요청에 선택한 근거 ID·수치가 전달됨. 유사 근거가 성공/실행 권한을 바꾸지 않음. 물리 동작 변경분은 MuJoCo로 검증 |
| 3 | Lesson 생성·저장 | 실측/가설·적용조건·반례 분리, 없는 근거 거부. fixture 연결과 실제 모델 생성을 구분 |
| 4 | 제한 VM와 조립 proposal adapter | 수동 fixture로 현재 네 파지 값 제안/보류, 잘못된 단위·형식·관측·권한 거부. 자동 학습 성공으로 집계하지 않음 |
| 5 | Python 후보 생성→MuJoCo 검증→등록·동결 | 실제 생성 코드가 실제 행동에 사용됨. 개발 조건과 사전에 정한 별도 등록 조건의 근거 일치. 단일 성공은 provisional |
| 6 | 단일 Luna의 등록 스킬 선택·재사용 | 동결 스킬 선택→현재 상태 계산→사전검사→원본 장면 실행→결과가 동일 ID/hash로 연결. 실패 시 재관측·한도 안 수정 또는 종료 |
| 7 | 슬리브·덮개·전체 프레임과 비교 | 부품별 계약을 별도 검증한 뒤 9개 장면에 같은 지식·전체 예산 적용. 개발에 쓰지 않은 조건과 on/off 비교 |

등록 조건과 평가 조건은 후보 결과를 보기 전에 정한다. 첫 권고 범위는 개발 실패 조건 하나와 별도 배치/치수의 등록 조건 둘 이상이며, 실제 만들 수 있는 유효 물리 조건을 확인한 뒤 고정한다. 조건을 많이 통과했다는 이유만으로 모든 제품으로 일반화하지 않는다.

등록 스킬이 여러 행동을 묶더라도 각 행동 뒤 재관측·허용조건·예산·완료 판정은 호스트가 처리한다. 프로그램이 실패한 명령을 무조건 반복하거나 예산을 우회할 수 없다. 새 관측이 필요한 시점에는 기존 그래프로 제어를 돌려준다.

분해 순서 인터페이스 연결은 별도 개발 단위다. 현재 조립체의 실제 경험으로 위 작업을 시작할 수 있으므로 외부 플래너 완성을 기다릴 필요는 없다. 새 순서 연결과 메모리·스킬 변경을 한 시험에서 동시에 섞지 않는다.

## 7. 비교 방법

| 조건 | 추가 정보/기능 | 확인할 효과 |
|---|---|---|
| A | 현재 Luna 직접 제안, 장기 지식 없음 | 같은 코드에서의 기준선 |
| B | A + Memory | 경험 제공 효과 |
| C | B + Lesson | 경험 해석을 제공하는 효과 |
| D | C + 검증 Python 스킬 | 실행 가능한 절차의 재사용 효과 |

기본 동작, 관측, 장면, 모델, 파지 제안·복구·물리검사 한도, 전체 API 예산을 맞춘다. 기존 JSON recipe 경로는 해당 범위의 회귀/참고 기준으로 보존하며, 다른 파지 모드의 결과를 같은 조건의 대조군으로 합치지 않는다.

검색/공급/선택/VM 제안/권한 수락/사전검사/본 실행/성공을 각각 기록한다. 설치 성공률, 사전 거절 수, 실제 실패 후 복구 성공률, 모델·VM·물리 호출, 시간·비용·개입을 측정한다. 스킬 생성·등록 비용과 온라인 사용 비용을 나누고 평가 중 지식은 갱신하지 않는다. 비용 절감이나 일반화 효과는 측정 전 보장하지 않는다.
