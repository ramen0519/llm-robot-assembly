## 1. 작업 목표와 수행 방식

사용자는 완성 목표가 포함된 제품 자료를 제공하고 진행 상태와 결과를 확인한다. 제품마다 부품 좌표, Python 코드, 전용 registry를 작성하게 하지 않는 것을 기본 사용 조건으로 삼는다. 로봇·그리퍼·작업대·공급 영역은 한 번 준비한 공통 profile을 기본 사용한다.

v1.1은 제품 자동 준비 요구를 추가했고, v1.2는 초기 배치를 단순 격자와 작업대 가로·세로 자동 확장으로 구체화한다. 자동 초기 배치뿐 아니라 지원 조립 종류에 대한 목표·지지·파지·설치·검증 조건의 생성과 실행기 연결이 필요하다. 이 기능은 현재 완료된 것으로 가정하지 않는다.

분해 프로젝트에서 전달한 검증된 분해 결과를 조립 후보 순서로 받아, Astra의 행동 선택과 기존 MuJoCo 로봇 실행·검증을 연결한다. 입력 생성, 대화 문맥, 실패 대응, 경험·해결지침, 검색, 영상, 수집·평가를 아래 범위로 한 번에 통합한다.

내부적으로 모듈 순서에 따라 수정·확인하되 각 모듈마다 사용자에게 진행 허가를 다시 요청하지 않는다. 현재 세션과 실행 설정에서 이미 승인된 범위의 구현·검증을 끝까지 수행한다. 임의의 새 기능을 추가해 범위를 넓히거나, 기존 작업을 초기화해서 구현을 쉽게 만들지 않는다.

기존 프로젝트를 바탕으로 수정한다. 분해 저장소와 조립 저장소는 별도로 유지하고 파일 계약으로 연결한다. 현재 작업 브랜치의 미커밋 변경과 사용자가 진행한 코드를 보존한다. 최종 결과는 구현 변경, 실행 가능한 명령, 검증 근거, 알려진 제한을 포함한다.

## 3. 이번 구현 범위와 공통 기본값

| 항목 | 기본 계약 |
|---|---|
| 사용자 입력 | 완성 배치·단위·부품 구분이 확인되는 CAD/제품 묶음 또는 검증된 분해 export |
| 자동 준비 | 공통 작업장 안에서 지원 종류 판별·작업 조건·초기 배치 생성. 제품별 수동 좌표/코드 수정 제외 |
| 모델 | 현재 승인된 Astra 모델 ID와 같은 high 설정. 모든 비교 조건에서 동일 |
| 출력 한도 | 기존 2048 설정을 초기값으로 유지. 개발 검증에서 필요하면 네 조건을 함께 변경하고 평가 전에 고정 |
| 판단 단위 | Python이 지정한 현재 부품에 대해 허용 행동 하나와 필요한 파지 파라미터 |
| 설치 순서 | 검증된 역순 후보. 모델의 임의 순서 변경·대상 건너뛰기 제외 |
| 최초 모델 정보 | 완성품 상면·대각선 2장, 기하·작업 설정 |
| 후속 모델 정보 | 공유 대화 이력, 최신 상태·실패·이전 관련 행동·허용 동작·검색 지침 |
| 파지 후보 | 최초 포함 최대 3개/부품 |
| 정렬 복구 | 최대 1회/전체 run |
| 운반 재계획 | 최대 1회/전체 run, 부품당도 최대 1회 |
| 온라인 제어 모델 생성 | 최대 4N+4회/전체 run. N은 초기 설치 부품을 제외한 이번 설치 대상 수 |
| 문제 이미지 검색 | 문제·적용 조건 필터 후 DINO 유사도 상위 최대 3개 |
| 이미지 비교 불가 | 적용 조건을 직접 확인한 메타데이터 지침 최대 1개, 없으면 0개 |
| 실행별 메모리 | 시작 시 고정한 snapshot. 새 사례는 다음 실행부터 사용 |

제어 모델 생성 상한은 두 역할이 공유한다. 입력 토큰 count 등의 HTTP 요청은 별도 집계하고, 실제 생성 요청을 보낸 실패·재시도도 포함하며, 역할 전환·부품 변경·이어 실행 때문에 초기화하지 않는다. 기존 승인 요청 한도가 더 작으면 더 작은 한도를 적용한다. 지침 생성은 종료 후 사건당 최초 1회로 별도 처리 장부에 기록하고 현재 승인 비용·시간 범위에서 수행한다. 전체 비용에는 온라인 실행과 지침 생성 비용을 모두 포함한다.

이번 MVP에는 기존 파지 후보 수정, 조건부 정렬 복구, 조건부 운반 재계획을 포함한다. 실제 내려놓기–재파지, 자유 자세 전환, 비수직 삽입, 압입·나사·클립 체결, 일반 CAD 결합법 자동 발견은 후속 범위로 둔다. 기존 코드 스킬 검색·선택·코드 생성 경로도 기본 비교 모드에서 비활성화한다. 고정 Python 실행 스킬과 경험에서 얻은 자연어 해결지침을 사용한다.

## 4. 입력부터 실행까지 연결

### 4.1 공통 분해 전달 입력

제품 입력을 받는 단일 진입점을 추가한다. CAD 입력은 기존 분해 전처리·검증된 후보 생성·export를 호출하고, export 입력은 검증 후 재사용한다. 두 저장소와 실행 환경은 분리해도 되지만 일반 사용자가 매번 중간 파일을 수작업으로 옮기지 않도록 연결한다. 분해 처리 비용과 시간도 기록하며 현재 승인 범위 밖의 실행을 숨겨 시작하지 않는다.

STEP/CAD는 완성 배치와 부품 인스턴스를 읽을 수 있어야 한다. OBJ 묶음도 부품 구분·완성 pose·단위가 필요하다. 목표 없는 낱개 형상은 필요한 목표 정보가 무엇인지 알려주는 결과로 종료하며 조립 목표를 추측하지 않는다.

disassembly_export/v1의 원본 파일·hash·ID·좌표계·검증된 연속 전이·잔여 부품·역순 후보를 검사하는 어댑터를 추가한다. 기존 native_assembly_candidate/v1 및 cad_selected_chain_transfer/v1 경로를 망가뜨리지 않는다.

분해의 tools/check_disassembly_export.py가 검사하는 의미를 유지한다. --zip은 검증 후 ZIP을 만드는 출력 옵션이며 ZIP 입력 검사 옵션이 아니다. 파일 묶음을 다른 경로로 이동해도 상대 참조와 hash 검사가 작동해야 한다.

완전 분해 결과만 완전 조립 후보로 사용한다. 부분 결과, 끊긴 분기, 다른 시도의 성공을 섞은 체인, 부품·메시 불일치를 거부한다. robot_verified=false의 의미를 유지한다. RedMax 궤적을 거꾸로 재생하는 것을 로봇 조립 명령이나 로봇 검증으로 취급하지 않는다.

공통 정보는 메시·안정적인 부품 ID·기하 수치·완성 pose·목표 주변 관계·최초 이미지다. 조립 측은 로봇/그리퍼/TCP와 작업장 정보를 공통 profile에서 가져오고, 베이스/fixture 연결·초기 배치·결합 방식·설치 완료 조건은 4.3의 준비기로 자동 생성한다. 추가 지지나 자세 전환이 필요한 후보는 명시적으로 지원되는 작업 설정과 연결한다.

목표 pose와 현재 pose, 목표 관계와 실제 접촉을 구분한다. CAD 원점·로봇 body 원점·작업장 좌표 매핑을 유지한다. 모델용 pose는 설계의 world/mm/xyzw 규칙으로 통일하되 파지 x/y/z는 기존 계약의 부품 로컬 TCP 위치임을 명시한다. 엔진의 m/wxyz 등과 변환을 검사한다.

일반 STEP/OBJ를 읽고 목표 이미지를 만드는 것과 현재 로봇 실행기가 그 제품을 조립할 수 있는 것은 별도 상태다. 지원하지 않는 기하·설치 방식은 unsupported_execution_scope로 구분한다. 임의 도형으로 대체하거나 검증을 완화해 성공시키지 않는다.

### 4.2 매 판단의 입력과 출력

새 관측에는 현재 부품·목표, 현재/목표 pose, 설치 부품, TCP·그리퍼·파지 상태, 필요한 기존 grasp_task, revision, 허용 동작과 남은 예산을 포함한다. 실패 시 최신 실제 상태와 실패 당시 snapshot을 분리한다.

상세 메시, 모든 관절 배열, 전체 궤적과 진단 로그를 모델 입력으로 반복 추가하지 않는다. 기존 중요한 파지·결합 조건을 요약 과정에서 누락하지 않는다.

모델은 현재 허용된 행동 하나를 제안한다. pick에는 필요한 수치 파지 후보를 포함한다. 파라미터 유한성·범위·단위·좌표·부품/목표 ID·revision을 검증한 뒤 실행한다. 생성된 Python 코드나 임의 로봇 명령을 실행하지 않는다.

pick, insert, recover_alignment, replan_insert, stop 등 기존 기능을 상태에 맞춰 노출한다. finish를 사용한다면 실제 설치 검증 이후에만 허용한다. 성공과 다음 부품 진행은 물리 검증기가 결정한다.

### 4.3 제품 자동 준비

공통 환경 profile과 제품별 생성 결과를 분리한다. 환경에는 UR3e·Robotiq 2F-85·TCP·테이블 높이와 XY 자동 확장 규칙·공급/설치 영역의 배치 기준·허용 지그·지원 동작과 준비 예산을 두고, 입력마다 부품 ID·목표 변환·준비 자세·공급 초기 pose·작업 조건을 생성한다. 제품별 새 좌표표 또는 수동 registry 작성을 정상 사용 절차로 요구하지 않는다.

기존 수직 삽입 실행기가 지원하는 종류부터 기하 조건을 정의한 매개변수 템플릿으로 묶는다. 실제 입력 ID·기하·목표·검증 근거로 결합 상대·삽입축·지지·파지·설치 완료 계약을 연결한다. 특정 post_1/sleeve_1 이름이나 bbox 유사성만으로 조립 의미를 확정하지 않는다. 누락 물성의 명시된 시뮬레이션 가정과 출처를 기록하며 모델의 추측을 측정값으로 취급하지 않는다.

초기 배치는 고정 Python의 단순 격자로 생성한다. 기본 칸 크기는 준비 자세에서 가장 큰 부품의 XY 크기에 양쪽 여유를 더해 정하고, 열 수는 ceil(sqrt(N)), 행 수는 ceil(N/열수)로 시작한다. 안정적인 ID 순서로 배치하며 로봇·지그·완성품 영역을 피한다. 예약 영역 때문에 칸을 건너뛰면 필요한 행을 추가한다. 높이는 회전·단위 변환된 로컬 메시 최저점을 기준으로 계산하고, 메시 원점이 정중앙이라고 가정하지 않는다.

작업대는 공급 부품·조립체·로봇 설치 영역의 XY 경계와 외곽 여유로 가로·세로 및 중심을 자동 계산한다. 현실 작업대의 고정 크기에 맞출 필요는 없다. 상판 높이, UR3e·2F-85와 부품의 실제 크기, 고정 world 목표는 유지하고 바뀐 table 원점 변환을 검사한다.

배치 생성, 안정화, 실제 로봇 접근 가능 판정은 구분한다. 작업대 확장은 로봇 도달 범위의 확장을 뜻하지 않는다. 검사에서 도달하지 못한 부품을 보고하며 로봇/부품 축소나 실행 중 순간 이동으로 통과시키지 않는다. 재배치가 필요하면 유한한 준비 예산 안에서 기록한다. 이 변경에 이동 레일·자동 급품·새 결합 추론 기능을 추가하지 않는다.

현재 고정 ID의 TRAY_POSITIONS, 제품 목록, free_part_count 상한을 각각 검토해 데이터 기반 장면 생성과 명시적 지원 한도로 바꾼다. 숫자 상한만 늘려 대량 지원을 주장하지 않는다. 지원 수량 초과, 정보 부족, 지원되지 않는 동작, 이번 배치 규칙의 실패를 구분한다. 배치 실패가 모든 배열의 불가능 증명은 아니다.

초기화가 끝나면 실제 상태와 생성 근거를 저장해 기존 판단 루프로 넘긴다. 실행 도중 부품을 순간 이동시켜 재공급하거나 실패 상태를 없애지 않는다. 자동 트레이 교체·급품·물리 재파지는 후속 범위다. 입력은 유효하지만 작업이 지원되지 않는 경우 이유를 설명하되 자동 조립 성공으로 집계하지 않는다.

## 5. 공유 대화와 역할 분리

### 5.1 공통 이력

store=false에서 하나의 논리적 대화 이력을 애플리케이션이 관리하고 요청마다 필요한 전체 이력을 재전송한다. 모델 응답의 tool call과 해당 실행 결과를 올바른 call ID로 연결한다. 요청 형식은 설치된 SDK와 실제 응답 계약에 맞추고 지원하지 않는 필드를 추측해 추가하지 않는다.

초기 이미지 2장은 논리적 이력에 한 번 추가한다. 수동 history replay에서는 이후 요청에도 그 이력이 포함될 수 있으므로 이미지 전송·입력 비용을 최초 한 번만 발생한 것으로 계산하지 않는다. 서버 캐시 여부는 실제 usage로 기록한다.

최신 상태 JSON이 현재 사실 기준이다. 이전 관측과 실패 장면을 현재 상태로 덮어쓰지 않는다. 이력이 한도를 넘으면 조용히 앞부분을 잘라 초기 조건을 잃게 하지 말고 명시적인 context_budget 중단으로 기록한다. 초기 MVP에서 자동 LLM 요약 호출을 추가하지 않는다.

### 5.2 single / roles

single은 공통 프롬프트에 전체 조립·복구 책임을 가진 한 역할을 사용한다. roles_shared_history(기존 CLI roles의 별칭 허용)는 같은 모델·같은 공유 이력에서 assembly와 recovery의 초점 지시만 전환한다. 독립 대화의 에이전트 간 토론이나 병렬 협상으로 설명하지 않는다. 실험 명칭은 “단일 역할 대 순차 역할 분리”로 정확하게 기록한다.

정상 실행은 assembly가 담당한다. 수정 가능한 복사 검사 거부와 지원되는 주 실행 실패가 발생하면 Python이 recovery로 전환한다. pending_failure뿐 아니라 grasp_trials의 마지막 거부 결과도 확인한다.

recovery는 실패 근거·관련 이전 행동·지침을 검토해 허용 대응을 선택한다. 복구용 별도 승인 호출·인계 문장 생성 호출을 추가하지 않는다. 숫자 파지 수정 후 실제 pick이 검증되거나 정렬 복구 후 다시 삽입 가능한 조건이 검증되면 assembly로 돌아간다. replan_insert가 삽입·해제·완료 검증까지 수행한 경우 Python이 그 결과에 맞춰 해당 부품을 종료한다.

두 모드의 입력 필드, 물리 도구, 메모리, 복구 조건·예산, 모델 설정은 같다. 공통 프롬프트와 역할 문구의 전체 문안은 동반 master를 사용한다. 해결지침 출력은 applies_when, strategy, checks, evidence_refs 네 필드이며 세 prose 필드 null과 빈 근거 배열은 등록 보류로 처리한다. 근거 없는 원인 단정이나 상세 내부 사고 과정 출력을 요구하지 않고, 간결한 판단 근거와 구조화 행동을 받는다.

## 6. 실패·복구 계약

| 상황 | 대응 |
|---|---|
| 실제 pick 전 복사 검사 거부 | 지원되는 오류이면 남은 후보 예산 안에서 파지 수정·재검사 |
| 운반 사전검사 거부 | 미실행 운반·동일 상태·정확한 실패 단계 등의 기존 조건을 만족할 때 replan_insert |
| 삽입 전 정렬 실패 | 파지 유지·오차·여유·속도 등 기존 범위 안에서 recover_alignment |
| 그 밖의 실제 집기·설치 실패 | 지원되는 대응이 없으면 현재 run 중단 |
| 입력·제어·시뮬레이션·API·예산 문제 | 출처를 구분해 기록하고 해당 중단 규칙 적용 |

실패 코드만으로 대응을 고르지 않는다. source, phase, 실제 상태와 실행 직전 전제조건을 함께 확인한다. 복사본 PART_LOST는 주 실행의 실제 낙하와 다르다. grasp_bounds의 수정 가능한 후보 범위 오류를 일반적인 시스템 입력 오류와 구분한다.

기존 replan_insert를 모든 접촉·IK 실패의 복구로 확장하지 않는다. 정렬 복구 성공을 설치 완료로 집계하지 않는다. 충돌 검사, 파지·접촉·지지·설치 검증을 꺼서 복구를 통과시키지 않는다.

복구 실패도 예산을 사용한다. 같은 거부 후보를 같은 상태에서 반복하는 것은 새로운 수정으로 인정하지 않는다. 기존 resume의 추가 후보 예외를 공통 누적 3개 정책에 맞춘다. 상태 계보가 확인되지 않는 reset·별도 실행을 연속 복구로 결합하지 않는다.

## 7. 기록·경험·해결지침

고유 action ID와 check ID, 부모 관측·revision, 실제/복사본/계획 후보의 출처를 추가한다. 기존 failure_report.json, 개별 실패 기록, graph_events.jsonl, skill_trace.csv와 사전검사 근거를 재사용한다. AssemblyRecorder의 phase 문자열을 고유 action ID로 간주하지 않는다.

같은 부품·설치 목표의 첫 실패에서 사건을 열고 이전 관련 파지 맥락을 연결한다. 다른 실패 코드로 이어지는 수정 시도도 한 사건에 누적한다. 원래 대상의 실제 설치 검증 때 solved_local로 닫고, run 종료 후 등록 가능성을 확인한다. 후보 검사·집기·정렬 복구만 성공한 사건은 해결 사례가 아니다.

미해결 로그를 삭제하지 않으며 해결지침 검색 인덱스에서 제외한다. 문제 없이 성공한 실행도 일반 결과에 남기되 문제 해결 사례 수로 부풀리지 않는다.

경험은 객관적 관측·변경·검증 기록, 해결지침은 적용 조건·권장 대응·확인 사항·근거 ID로 구성한다. 사례 하나당 짧은 지침 하나부터 시작한다. 관측되지 않은 접촉·힘·원인을 채우지 않고 인과 해석은 가설로 구분한다. 한 사례의 성공을 다른 형상의 검증된 성공으로 일반화하지 않는다.

지침 생성은 실행 종료 후 근거가 정리된 후보에 대해 수행한다. Python이 형식·근거 ID·수치 출처·단위·동작 지원을 검사한다. 생성 실패는 이미 완료된 물리 성공을 취소하지 않으며 지침 등록만 보류한다.

전체 run 실패에서 앞선 부품의 국소 해결을 등록하려면 별도의 보존 검사가 필요하다. 기존 완료 검증기를 그대로 재호출하면 현재 그리퍼 개방 폭이나 다른 부품의 상태 때문에 오판할 수 있다. 원래 설치 완료 증거를 보존하고 해당 부품과 필요한 지지·결합 상대만 읽는 종료 보존 검사를 추가한다. 준비되지 않은 첫 버전은 전체 실패 run의 후보를 보류하고 전체 성공 run의 사례부터 등록한다.

## 8. 검색 통합

검색은 Python이 자동으로 수행한다. 새 기본 모드에서 검색어 생성용 Astra 호출, 기존 첫 파지 전 검색, 생성 코드 스킬 선택 경로를 끈다.

등록된 조립 사례 중 source/phase/code, 실행 환경·도구·계약, 필요한 기하·관측 조건, 현재 가능한 첫 대응과 예산이 맞는 사례만 남긴다. 전체 제품 ID·instance ID의 일치를 필수로 요구하지 않는다. 자유로운 LLM 원인 문장을 기계적 적용 조건으로 해석하지 않는다.

같은 규격의 정확한 실패 이미지끼리 DINO 임베딩 유사도로 정렬한다. 현재 분해의 고정 DINOv2·전처리·버전 기록 구조를 재사용하되 조립 카메라·그리퍼 포함 규칙을 따로 정의한다. 같은 사건의 다른 실패 사진을 대신 비교하지 않는다.

visual은 최대 3개, metadata_only는 직접 적용 조건을 확인할 수 있을 때 최대 1개, none은 0개다. 가짜 유사도 점수로 두 모드를 섞지 않는다. 초기 cosine 최소 임곗값은 두지 않고 순위 점수로만 취급한다. 필요한 조건을 확인하지 못한 지침을 개수 채우기용으로 반환하지 않는다.

Astra에는 짧은 지침 카드만 보낸다. 과거 원본 사진·전체 trace·임베딩 숫자를 추가하지 않는다. 검색은 허용 동작·시도 예산·물리 검증을 변경하지 않는다.

동일 사건의 중복 등록을 막고 반환 지침·scope가 검증된 archive와 일치하는지 검사한다. 단순히 archive hash가 정상이라는 이유로 변조된 별도 캐시 문장을 반환하지 않는다. 실행 시작 memory snapshot은 고정하고 새 사례는 다음 실행부터 조회한다.

## 9. 영상·이미지·재생

현재 viewer와 PNG 기능에 더해 시간별 전체 상태 기록을 구현한다. 기존 CSV의 TCP·활성 부품 측정값만으로 전체 로봇의 연속 MP4를 정확히 재생했다고 주장하지 않는다.

영상용 일정 주기 상태에는 로봇·그리퍼·전체 자유 부품을 재현할 정보, 모델/자산 식별, simulator version, simulation time, action/check/source를 포함한다. 기존 integration checkpoint 구조를 참고하되 주기 기록과 렌더 경로를 새로 연결한다.

실패 순간은 예외가 검출됐을 때 별도 snapshot으로 보존한다. 복사본이 폐기되기 전에 해당 상태를 확보하고, 정확한 실패 상태를 잃었으면 unavailable로 표시한다. 정상 마지막 상태나 영상에서 가장 가까운 프레임을 실패 순간으로 위장하지 않는다.

대표 실행 MP4, 초기/실패/해결후 PNG, 프레임–상태 연결 기록을 만든다. 복사 검사 장면과 주 실행 장면, 잘라 연결한 구간을 표시한다. 기록된 변환으로 렌더하며 성공 장면을 만들기 위한 재실행·텔레포트·미측정 경로 보간을 하지 않는다.

미디어 실패는 물리 결과와 별도로 기록한다. 벽시계 실행 시간, 시뮬레이션 시간, 모델 대기, 검색·렌더 시간을 구분한다. 비교 평가의 영상 기록 규칙은 네 조건에 동일하게 적용한다.

## 10. 수집과 평가 진입점

네 조건을 지원한다.

| 조건 | 역할 | 경험 검색 |
|---|---|---|
| S0 | single | off |
| S1 | single | on |
| R0 | assembly/recovery | off |
| R1 | assembly/recovery | on |

같은 trial manifest의 초기 상태·제품·작업장·장애물·seed·목표 순서와 같은 모델·도구·물리/API 예산을 사용한다. on 조건은 같은 동결 메모리를 사용하고 off 조건은 숨은 기존 경험·코드 스킬을 받지 않는다.

자동 준비한 초기 상태도 case별로 검증·고정해 네 조건에 동일 제공한다. 준비 성공률·시간·실패 사유·수동 보정 여부를 별도 기록한다. 준비 실패를 전체 사용자 흐름의 결과에서 숨기지 않고, 조립 정책 평가 대상과 분모는 사전에 선언한다.

개발·수집·평가 split을 별도 manifest로 관리한다. 평가 실행의 사례를 그 평가에 쓰는 메모리에 미리 넣지 않는다. 실패 주입·개발자 제공 수정 후보·scripted 정책·실제 Astra 선택을 각각 표시한다. 같은 제품의 다른 초기 조건 실험을 새로운 형상 일반화 실험으로 보고하지 않는다.

초기 파일럿 계획은 보류된 10개 평가 trial × 네 조건 = 40회다. 이 문서만으로 40회의 유료·장시간 배치를 자동 실행하지 않는다. 먼저 실제 승인된 run config의 범위에서 작은 end-to-end smoke를 확인하고 manifest·예산을 고정한다. 실제 수집·평가 실행은 그 범위가 승인된 실행 설정 안에서 수행한다.

전체 조립 성공, 검증된 설치 수, 사건 해결률, 중단 원인, API·시스템 오류, 시도 수, 입력/캐시/출력/추론 사용량, 모델·계획·물리·렌더 시간을 기록한다. 성공한 run만 시간·비용 평균에 넣어 실패를 숨기지 않는다. 물리 실패와 인프라 오류의 분모·처리 기준을 결과에 명시한다.

기존 승인 비용·시간 상한을 보존한다. 가격을 코드에 현재 가격인 것처럼 하드코딩하지 않는다. 가격 설정의 출처·기준일을 기록하고, 확인된 가격이 없으면 사용량을 보고하되 금액을 만들어내지 않는다. 개발에서 정한 한도와 출력 설정은 네 조건에 공통 적용하고 평가 전에 고정한다.

## 11. 파일 연결 지도

## 12. 완료 판정과 필수 결과물

다음이 연결돼야 구현 완료로 판정한다.

1. 이동 가능한 실제 export 입력이 기하·ID·단위·목표·순서로 연결되고, 잘못되거나 지원 범위 밖인 입력은 구분된다.
2. single/roles와 memory off/on이 공통 실행기에 연결되고 동일 설정·예산을 사용한다.
3. 초기 2장과 후속 공유 이력·최신 상태가 실제 요청 형식으로 구성되며 역할 전환에서 문맥을 잃지 않는다.
4. 파지 거부·실제 실패·복구·원래 설치 검증이 출처와 사건 ID로 연결된다.
5. 적격 경험 등록과 다음 실행의 검색·지침 적용·재검증이 동작한다.
6. 기록된 실제 상태의 영상·이미지와 물리 결과가 연결된다.
7. 수집·평가 manifest, 결과 집계, 실제 사용량과 중단 기록이 재현 가능하다.
8. 전체 프레임 통합 시연 1개에서 새 전달 순서에 따른 연속 실제 실행, 최종 물리 검증과 영상을 확인한다. 완주하지 못했다면 이 완료 항목은 미완료로 남긴다. 작은 셀의 성공으로 대체하지 않는다.
9. 지원 종류의 새 입력에 대해 제품별 코드·좌표·registry 수동 작성 없이 준비·판정·실행을 연결한다. 고정 부품명과 다른 ID 및 지원 범위의 치수·수량 변화를 확인하고, 적어도 하나의 새 입력에서 준비부터 실제 조립까지 완료한 증거를 남긴다. 초기 배치만 자동화했다면 작업 조건 생성까지 완료했다고 보고하지 않는다.

검증 결과는 입력 계약 검사, mock 모델 검사, 실제 MuJoCo 검사, 실제 Astra+MuJoCo 검사, 새 실행 경험 재사용, 미디어 검증으로 구분한다. mock 성공을 실제 모델/물리 성공으로 표시하지 않는다. 실제 키·자산·실행 예산이 없으면 해당 완료 항목을 false/not_run으로 남긴다.

기존 테스트를 재사용하고 변경 위험에 맞는 핵심 회귀검사를 추가한다. 후보 검사만 통과한 solved 등록, 정렬만 복구한 solved 등록, reset 전후 증거 혼합, 잘못된 revision, 복사/실제 source 혼동, 예산 초기화, 현재 run 메모리 누수 등을 확인한다. 선택 검사가 통과했다는 이유로 실행하지 않은 전체 suite까지 통과했다고 보고하지 않는다.

최종 구현 보고서에는 아래를 포함한다.

- 실제 적용한 commit/branch와 변경 파일, 작업서 대비 결정·제외 범위.
- 준비 상태와 지원하는 제품/동작/입력 범위.
- 복사해 실행할 수 있는 입력 검증·smoke·수집·평가·미디어 명령.
- 실행한 검사와 실제 run ID, model/config, 사용량·물리 검증·미디어 경로.
- 테스트하지 못했거나 막힌 항목과 이유, 다음에 필요한 입력/자산/실행 설정.
- 기존 기능 회귀와 새 기능의 관측 가능한 결과.

실제 증거가 없는 전체 성공, 일반 CAD 지원, 학습 완료, 성능 우위를 주장하지 않는다. 파일 링크만 주고 설명을 끝내지 말고 무엇이 바뀌었고 어떤 범위가 실제 검증됐는지 보고한다.
