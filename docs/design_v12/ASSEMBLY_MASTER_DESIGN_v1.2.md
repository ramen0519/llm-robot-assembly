# 조립 에이전트 최종 설계서

**버전:** v1.2  
**작성일:** 2026-11-23, 한국 시간  
**대상:** llm-robot-assembly  
**상태:** v1.1의 자동 준비 요구를 유지하고, 초기 배치를 단순 격자와 작업대 가로·세로 자동 확장으로 구체화했다. 실제 구현·검증 전이며 다른 조립 계약은 유지한다.  
**동반 작업서:** ASSEMBLY_CODEX_HANDOFF_v1.2.md

이 문서는 구현과 경험 수집을 시작하기 위한 설계다. 이번 정리에서 새 조립 코드, Astra 호출, MuJoCo 실행 또는 성능 실험을 수행한 것은 아니다. 구현자는 아래 계약을 실제 코드와 연결하고 완료 증거를 남겨야 한다. 과거 보고서의 “초안/후보/다음 논의” 표기보다 이 버전의 포함·후속 범위를 우선한다.

## 1. 목표와 이번 구현 범위

### 1.1 졸업 프로젝트의 목표

사용자가 완성 목표가 포함된 제품 자료를 제공하면, 시스템이 제품 분석·작업 준비·초기 배치·조립·복구·결과 생성을 이어서 수행한다. 일반 사용 흐름에서 제품마다 부품 좌표, Python 코드 또는 전용 registry를 작성하도록 요구하지 않는다. 로봇·그리퍼·작업대 등 공통 환경은 처음 한 번 준비한 기본 profile을 사용한다.

v1.0은 기존 제품별 작업 설정을 재사용하는 소규모 실험을 기준으로 정리했으므로, 새로운 제품의 초기 배치와 작업 조건까지 자동으로 생성한다는 요구를 충분히 포함하지 못했다. v1.1은 이를 신규 구현 항목과 완료 기준으로 보완한다. 지원 조립 종류를 넘어서는 모든 CAD의 자동 조립을 보장한다는 의미는 아니다.

분해 프로젝트가 제공한 역순 조립 후보를 바탕으로, Astra가 현재 상태에서 조립 행동과 파지 후보를 선택하고 Python 실행기·물리 검증기가 결과를 확인하는 시스템을 만든다. 실패하면 지원되는 복구를 시도하고, 해결된 경험을 이후 실행에서 재사용한다.

실험의 주 질문은 두 가지다.

1. 같은 모델·정보·도구·예산에서 조립/복구 역할을 나누는 것이 단일 정책과 어떤 차이를 만드는가.
2. 검증된 경험에서 만든 해결지침을 검색하는 것이 성공·복구·시도 수·시간·토큰 비용에 어떤 차이를 만드는가.

이번 “학습”은 경험과 해결지침의 축적·검색이다. Astra나 이미지 인코더의 가중치를 파인튜닝하는 과제는 포함하지 않는다.

### 1.3 후속 확장으로 남기는 범위

실제로 내려놓고 다시 잡는 물리 재파지, 일반 뒤집기, 임의 6D 자세 변경, 비수직 삽입, 압입·나사·클립 체결, 낙하 부품 회수, 끼인 부품 인출, LLM 코드 스킬 생성·선택, 자동 급품·트레이 교체, 제한 없는 CAD 작업 의미 추론은 후속 범위다. 초기 장면 생성과 지원 조립 종류의 기하 조건 판별·템플릿 연결은 이번 자동 준비에 포함한다.

기존에 관련 개발 도구가 있더라도 기본 single/roles 실험의 한쪽에만 활성화하지 않는다. 코드와 과거 자료는 보존하되 새로운 공통 모드에서는 숨겨진 해답·추가 도구로 사용하지 않는다.

이번 실행 환경은 검토한 조립 저장소의 MuJoCo/UR3e/Robotiq 2F-85다. 사용자의 실제 UR3와 같은 장치로 단정하지 않는다. 실제 로봇 제어·배포는 이 설계 작업 범위에 포함되지 않는다.

## 2. 검토 기준과 구현 원칙

| 프로젝트 | 검토한 기준 |
|---|---|

| 조립 이전 main | 7706cc23dc4ed500f4bf3035263af99c911e3345 |
| 분해 | main/research/astra-cases-v1, 8110fdcd5e919f3b3a1beb8c974b56a81069e7b4 |

사용자의 실제 Codex checkout이 위 버전과 같다고 가정하지 않는다. 현재 브랜치·미커밋 변경·AGENTS 지침·실행 설정을 먼저 읽고 최신 코드에 맞춰 적용한다. 기존 작업을 되돌리거나 검증을 약화해 보고서의 예시 이름에 맞추지 않는다.

함수·모듈·JSON 키의 정확한 이름은 기존 코드와 맞춰 조정할 수 있다. ID·단위·출처·검증·예산·역할의 의미와 기록 연결은 유지한다. 전체 변경은 하나의 구현 요청으로 처리하며 내부적으로 모듈별 작업·검증을 진행한다.

현재 구현과 새 작업의 핵심 차이는 다음과 같다.

- 기존 제품 로더에 새 disassembly_export/v1 공통 어댑터가 필요하다. [S3,S4]
- 현재 고정 부품 ID의 트레이 좌표표와 수량 검사를 그대로 두면 새 제품의 자동 준비를 지원하지 못한다. 일반 배치 생성, 부품 목록 기반 장면 생성, 지원 종류의 작업 조건 생성은 신규다. [S36,S40]
- 기존 Astra 요청은 독립 관측 패킷이며 최초 두 이미지·공유 대화 연결은 신규다. [S5]
- 기존 첫 결합/특정 슬리브 메모리는 새 공통 해결 사건 메모리와 다르다. [S27,S28]
- 정확한 연속 영상용 상태 기록, 공통 수집·2×2 평가 driver는 신규 작업이다. [S21,S26,S34,S35]

## 3. 분해 프로젝트와 입력 연결

### 3.1 전달 단위

사용자의 기본 진입점은 제품 파일 또는 기존 분해 export를 선택하고 실행하는 한 곳이다. STEP은 완성 배치와 부품 인스턴스를 해석할 수 있어야 하며, OBJ 묶음은 부품 구분·완성 pose·단위가 확인돼야 한다. 낱개 형상만 있고 완성 목표가 없으면 목표 자료가 필요하다는 결과를 반환한다. 모양만으로 조립 목표를 유일하게 추정한 것으로 처리하지 않는다.

CAD 입력은 기존 분해 전처리·계획·검증을 호출하여 아래 내부 전달 형식으로 연결한다. 분해와 조립 저장소를 합칠 필요는 없다. 배포 시 두 실행 환경과 호출 경로를 한 번 연결하며, 일반 사용자가 매번 중간 JSON·ZIP을 수작업으로 만들거나 옮기는 절차를 기본 흐름으로 두지 않는다. 검증된 export가 이미 있으면 버전·hash·출처를 확인해 재사용한다. 상위 단계의 시간·모델 비용도 전체 실행 비용에 포함하고 승인된 예산을 공유하거나 명시적으로 나눈다.

분해 프로그램의 export_v1.json과 그 파일이 참조하는 메시·기하·매핑·이미지·검증 자료를 하나의 폴더 또는 ZIP으로 전달한다. 두 Codex 프로젝트가 같은 파일시스템·환경을 공유할 필요는 없다. 자산을 한 번 검증한 뒤 조립 쪽에서 독립적으로 실행한다.

공통 정보는 부품 instance ID, 원본 ID·형상 ID, 부품별 상세 메시, 크기·중심·부피와 신뢰 상태, 완성품 assembly pose, 가까운 부품 관계, 상면·대각선 이미지, 검증된 분해 전이와 역순 후보, 단위·좌표·원점 변환 및 파일 hash다. [S1,S2]

현재 분해의 전달 검사 명령은 다음 형태다. 실제 경로는 해당 실행으로 지정한다.

```bash
python -B tools/check_disassembly_export.py "<run>/export_v1.json" --zip "<handoff>/<run_id>.zip"
```

--zip은 검증한 묶음을 새 ZIP으로 만드는 출력 옵션이다. 기존 ZIP을 검사하는 입력 옵션으로 설명하지 않는다. 출력 부모 폴더·기존 파일 충돌도 기존 도구의 규칙을 따른다. [S10]

### 3.2 입력 어댑터의 필수 검사

- schema, 파일 hash, run 출처, 부품 ID·메시 매핑과 연속 분해 전이.
- 완주 여부, 남은 부품, 역순 후보와 부품 집합의 일치.
- 알려진 메시 단위·회전·원점과 변환의 일관성.
- 조립 작업 설정이 현재 제품과 필요한 지지·고정 조건을 지원하는지.
- 이미지·geometry·part_mapping이 같은 제품 버전을 가리키는지.

전체 조립에는 완주한 assembly_candidate를 사용한다. 부분 분해를 완전한 조립 순서로 승격하지 않는다. 부분 조립 실험은 초기 설치 상태·목표 부분집합·작업 범위를 별도로 선언해야 한다.

분해 역순과 부품 경로는 로봇 실행의 후보다. export의 robot_verified=false 의미를 유지한다. RedMax 부품 궤적을 반대로 읽어 로봇 관절 명령으로 바로 사용하는 방식은 채택하지 않는다. [S1]

### 3.3 조립이 추가하는 작업 설정

설정을 다음 두 층으로 나눈다. 로봇·TCP·테이블 높이·최소 크기·자동 확장 규칙·공급/설치 영역의 배치 기준·허용 지그·동작 범위는 시스템 수준의 workcell profile에 준비한다. 부품 ID·기하·목표 pose·준비 자세·초기 공급 위치·현재 작업 조건은 입력마다 자동 생성한다. 같은 작업장을 사용한다는 사실만으로 모든 제품이 같은 지그와 작업 범위에 맞는다고 가정하지 않는다.

| 정보 | 의미 |
|---|---|
| 로봇·그리퍼·TCP | 현재 실행기의 모델과 기준점 |
| 작업대·고정 베이스·지그·트레이 | 초기 실제 작업장 |
| CAD→작업장 변환 | CAD 완성 pose와 로봇 목표 연결 |
| 부품 결합 상대·설치 방식 | 입력 기하·목표·검증 근거를 지원 종류의 매개변수화된 템플릿에 연결 |
| 파지 기하·조건 | grasp_task의 부품 기준 TCP 오프셋, 패드·개방폭·접근·삽입 관련 정보 |
| 성공 기준 | 지원 종류의 위치·자세·깊이·지지·해제·정지·허용 접촉 검증 로직을 입력 기하·목표 매개변수에 맞춰 구성 |

bbox·거리만으로 결합 종류나 파지 가능 영역을 자동으로 알아냈다고 처리하지 않는다. 임의 배터리 STEP의 파싱·렌더링이 성공하더라도, 작업 설정·동작 지원·실제 검증이 없으면 로봇 조립 지원 완료로 보고하지 않는다.

기존 제품별 작업 설정은 회귀검사와 실행기 재사용의 출발점이다. 새 기본 경로의 완료 조건은 지원 종류 안의 새 입력에 대해 작업 설정을 자동으로 생성하는 것이다. input_valid, task_supported, preparation_ready와 실제 조립 성공은 별도로 기록한다. 누락된 물성은 모델이 추측해 사실로 채우지 않는다. 명시된 시뮬레이션 profile의 기본 물성을 사용한 경우에는 가정·출처를 기록하고 CAD에서 측정한 값으로 표현하지 않는다.

### 3.4 지원 종류 안에서 작업 조건 자동 생성

첫 범위는 기존 수직 삽입 실행기와 검증기를 재사용할 수 있는 강체 부품·준비 자세·고정 베이스 조건이다. 종류별로 필요한 기하 특징, 결합 상대, 삽입축, 지지 조건, 파지 계약, 완료 검사를 정의한 템플릿을 구현한다. 입력의 실제 ID를 사용하고 특정 post_1/sleeve_1 이름 또는 파일명에 의존해 의미를 판정하지 않는다.

CAD 목표 pose, 실제 기하, 검증된 후보 전이 등에서 필요한 조건을 확인해 템플릿 매개변수를 생성한다. bbox, 근접 또는 외형 유사성만으로 결합 방식과 성공 조건을 확정하지 않는다. 기존 템플릿의 조건을 확인할 수 없으면 어떤 조건이나 동작이 부족한지 보고한다. 분해 후보가 있다는 사실만으로 로봇 파지·지지·삽입이 검증됐다고 하지 않는다.

이 매핑은 기존 제품 registry를 읽는 기능보다 큰 신규 구현이다. 기존 프레임의 수치만 복사하거나 입력 형상을 익숙한 도형으로 대체하는 방식으로 자동화를 통과시키지 않는다. 입력 메시와 시뮬레이션 충돌 형상 사이의 생성·근사·검증 관계를 남긴다. 로봇 동작·힘·체결의 일반적 의미 추론은 후속 범위로 유지한다.

### 3.5 초기 배치와 작업대 크기 자동 생성

사용자는 현실 작업대와 크기를 맞추는 것을 현재 목표로 두지 않는다. 시뮬레이션의 작업대 가로·세로는 부품 배치에 맞춰 자동으로 넓혀도 된다. 로봇은 UR3e, 그리퍼는 기존 Robotiq 2F-85를 유지한다. 초기 배치는 LLM 호출 없이 고정 Python으로 계산하며 제품마다 수동 좌표표를 추가하지 않는다.

첫 구현은 최적 포장보다 단순하고 재현 가능한 격자 배치를 사용한다.

1. 배치할 자유 부품 목록과 지원되는 기본 준비 자세를 얻는다. 단위를 통일하고 준비 자세의 회전을 적용한 로컬 메시에서 XY 외곽과 최저 Z를 구한다. 완성품 배치의 이동을 이중 적용하지 않는다.
2. 공통 한쪽 여유를 m으로 두면 칸 폭은 `max(part_width) + 2m`, 깊이는 `max(part_depth) + 2m`이다. 여유는 설정값이며 그리퍼 접근 성공의 보증이 아니다. 부품을 칸에 놓을 때는 메시 원점과 외곽 중심의 차이를 반영한다.
3. 자유 부품 N>0에 대해 열 수는 `ceil(sqrt(N))`, 행 수는 `ceil(N / columns)`를 기본값으로 한다. 안정적인 ID 순서로 채운다. 고정 로봇·지그·완성품 영역 바깥에 공급용 격자를 만들거나, 겹치는 칸을 건너뛰고 필요한 행을 추가한다. N=0이면 공급 배치 생성을 생략한다.
4. 각 부품의 높이 이동은 `tabletop_z - min_z(rotated_local_mesh) + clearance`로 정한다. 메시 원점이 정중앙인 직립 상자에서만 높이의 절반으로 단순화할 수 있다. 초기 안정화 후 실제 pose와 지지 상태를 다시 읽는다.
5. 공급 부품, 조립 목표, 고정 지그와 로봇 설치 영역을 모두 포함한 XY 경계에 바깥 여유를 더해 작업대의 가로·세로와 XY 중심을 계산한다. 상판 높이와 로봇·부품·그리퍼의 실제 크기는 유지한다. 작업대 중심이 달라져도 고정된 world 기준 로봇·목표 pose를 뜻하지 않게 이동시키지 않도록 좌표 변환을 함께 갱신한다.
6. 배치된 장면의 겹침·지지/안정성과 실제 로봇의 허용 접근을 별도로 검사한다. 초기 배치 성공과 파지·설치 가능 판정은 구분한다. 작은 후보 재배치가 필요하면 profile의 유한한 준비 예산과 고정 seed 안에서 기록한다.

예를 들어 자유 부품 9개, 최대 평면 크기 80×60 mm, 한쪽 여유 20 mm라면 칸은 120×100 mm이고 공급용 3×3 격자는 360×300 mm다. 이것은 공급 영역의 계산 예시이며 전체 작업대에는 로봇·조립체 영역과 외곽 여유가 추가된다. 이 수치는 실제 실행 결과가 아니다.

작업대를 넓혀도 UR3e 링크 길이·관절 조건은 변하지 않는다. 기존 UR3e 공식 사양의 도달거리는 500 mm이며, 이를 단순한 구형 안전 영역으로 쓰지 않고 실제 모델·그리퍼·자세·경로 검사로 판단한다. 멀리 놓인 부품의 접근 실패를 숨기거나 로봇·부품을 임의로 축소하지 않는다. [A4]

현재 고정 위치표, 특정 제품 목록, free_part_count 상한은 각각 데이터 기반 생성과 명시적 실행 한도로 정리한다. 작업대 면적 확장만으로 임의 개수의 실제 조립 지원을 주장하지 않는다. 지원 수량/자원 한도, 배치 생성 실패, 도달 실패를 구분한다. 실행 중 순간 이동·자동 급품·로봇 이동 레일은 이번 변경에 추가하지 않는다. 부품 크기 차이가 커서 격자 낭비가 문제가 될 때 가변 줄 배치를 후속 최적화로 적용할 수 있다. [S36,S40]

### 3.6 사용자에게 보이는 결과

일반 사용자는 제품을 선택하고 진행 상태·결과·영상을 확인한다. 기본 작업장 profile을 자동 사용하고 상세 설정은 선택 기능으로 둔다. 일상적인 좌표·ID·JSON 작성이나 제품별 코드 편집을 사용자 단계로 노출하지 않는다.

추가 자료가 정말 필요하면 누락된 정보만 구체적으로 안내한다. 예: 완성 배치가 없는 낱개 메시, 확인할 수 없는 단위. 지원 동작 밖인 경우에는 필요한 동작과 근거를 알린다. 입력 부족, 지원 밖, 준비 실패, 실제 실행 실패, 조립 성공은 별도 상태다. 자동으로 미지원 사유를 출력한 것은 자동 조립 성공이 아니다.

## 4. Astra 입력과 좌표 계약

### 4.1 최초 문맥

기본 기하 요약, 완성 상태의 가까운 부품 관계, 역순 조립 후보와 고정 베이스, 필요한 로봇·그리퍼 조건, 초기 실제 관측·현재 대상 작업 조건을 제공한다. 완성품 상면·대각선 이미지 두 장도 최초 문맥에 넣는다.

두 이미지는 완성 목표 CAD다. 현재 트레이와 로봇 상태의 사진이 아니다. 사용자가 같은 JSON·PNG를 열어 볼 수 있도록 실제 입력 산출물을 남긴다.

### 4.2 매 판단의 최신 문맥

현재 대상·작업 단계, 실제 current_pose와 goal_pose, 검증된 설치 부품, TCP·그리퍼·보유 부품, 관측 revision, 허용 동작·예산, 직전 결과·검증, 필요한 이전 행동·실패 요약·검색 지침을 제공한다.

실패 후에는 새 관측을 읽는다. 복사본 검사의 pose가 주 실행의 current_pose를 덮어쓰지 않는다. 메시 정점/면, 관절·제어 전체 배열, 전체 경로·원시 로그는 실행기가 보유하며 기본 모델 입력에 넣지 않는다.

모든 부품 쌍의 정밀 거리를 매번 계산하지 않는다. 현재 대상·결합 상대·관련 장애물과 검증기가 확인한 접촉을 우선한다. 완성품 가까운 관계는 goal_assembly_relations로, 현재 접촉은 current_observations로 구분한다. 근접을 지지·체결 증명으로 쓰지 않는다.

### 4.3 단위와 원점

| 데이터 | 기준 |
|---|---|
| Astra용 current/goal pose | workcell_world, mm, quaternion xyzw |
| 조립 물리 실행 내부 | 기존 m 및 MuJoCo quaternion wxyz |
| 파지 x_mm/y_mm/z_mm | PART 좌표계에서 본 TCP 오프셋 |
| jaw_yaw_deg | 기존 파지 계약에 정의된 회전 규칙 |
| 원본 기하·메시 | 원래 unit/frame과 변환 메타데이터 보존 |

분해 기본 기하의 mm와 native 메시의 cm를 같은 값으로 취급하지 않는다. CAD assembly→world와 CAD part→simulation body 원점 변환을 각각 유지한다. 이미 배치가 적용된 메시에는 assembly pose를 두 번 적용하지 않는다. bbox의 기준축·부피의 유효성도 표시한다. [S2,S6,S7,S8]

upright 부품의 PART-frame z_mm 증가가 파지 높이 증가라는 기존 의미를 보존한다. 그리퍼의 아래쪽 TCP +Z 방향 설명과 부호를 혼동하지 않는다.

## 5. 행동·실행·검증 계약

### 5.1 역할 분담

| 판단 | 담당 |
|---|---|
| 현재 부품·목표·순서·허용 동작 | Python 상태 관리자 |
| 다음 행동 하나와 필요한 숫자 파지안 | Astra |
| IK·로봇 경로·접근·운반·삽입·제어 | 기존 Python 실행기 |
| 파지 유지·접촉·설치 완료 | 물리 검증기 |
| 역할 전환·다음 부품·중단 | 검증 결과와 예산에 따른 Python |

LLM이 자유 경로 waypoint나 로봇 관절 명령을 생성하지 않는다. 순서 변경·자동 다른 부품 전환도 기본 행동에 넣지 않는다.

### 5.2 기본 행동

| 행동 | 의미 |
|---|---|
| pick | 숫자 파지 후보 사전검사 후 주 실행 집기·들기 검증 |
| insert | 운반·정렬 검사·삽입·해제·후퇴·설치 검증을 포함한 기존 복합 동작 |
| recover_alignment | 지원 조건에서 측정 기반 정렬 복구. 성공 후 insert 필요 |
| replan_insert | 미실행 운반 거부 조건에서 경로 전략을 바꾸고 전체 insert 재수행 |
| stop | 현재 지원/예산 안에서 중단 |
| finish | 기존 호환 계약에서 실제 허용될 때만. 정상 frame 종료를 위한 추가 호출은 생략 가능 |

모든 행동을 항상 노출하지 않는다. Python이 현재 상태와 지원 기능·예산에서 허용 목록을 만든다. finish_on_verified_insert 경로처럼 실제 설치 검증으로 자동 종료할 수 있으면 종료 선언만을 위한 모델 호출을 추가하지 않는다. [S9,S13,S15]

Python은 제안의 field set, 동작, 부품·목표 ID, observation_revision, reason 길이, 숫자·범위·좌표 계약을 검사한다. 실행 직전 상태/전제조건도 다시 확인한다. 실패한 검사를 성공으로 바꾸거나 물체를 순간 이동·고정해서 조립 완료를 만들지 않는다.

## 6. 에이전트 역할과 대화

### 6.1 비교 모드와 공통 조건

| 모드 | 구성 | 역할 |
|---|---|---|
| `single` | 단일 정책 객체 | 조립과 지원되는 복구를 모두 판단 |
| `roles_shared_history` | assembly·recovery 정책 객체 | 조립 진행과 실패 대응의 프롬프트·담당을 분리하고 실행 기록은 공유 |

두 모드는 같은 Astra의 **정확한 모델 ID**, `reasoning.effort=high`, 출력 한도, 초기 입력, 실행기, 최신 상태, 검색 정책, 메모리 snapshot과 전체 예산을 사용한다. 실제 응답의 모델명과 설정을 기록한다. 모델이나 설정을 지원하지 않으면 임의로 바꾸지 않고 실행 전 조건 문제로 보고한다. 예산 값과 비교 조건은 수집·평가 절을 따른다.

역할 분리는 “공유 이력을 사용하는 역할 분리”로 명명한다. 두 정책 객체가 같은 append-only 대화·상태·비용 장부를 참조하며 하나의 물리 실행을 순차 담당한다. 단일 모드도 같은 실패·복구 단계 신호를 받고 역할 이름만 single로 유지한다. 독립 에이전트의 병렬 탐색·토론·합의를 평가한 것으로 표현하지 않는다.

### 6.2 Python이 관리하는 인계와 반환

| 조건 | 역할 전환 또는 처리 |
|---|---|
| 새 부품의 설치 시작 | assembly가 현재 부품·목표의 허용 행동을 선택 |
| 수정 가능한 복사 파지 검사 거부 | 최신 실제 상태와 남은 후보 예산을 확인하고 recovery로 인계 |
| 지원되는 실제 운반/정렬 실패 | 해당 복구 전제조건과 예산을 확인하고 recovery로 인계 |
| 숫자 파지 후보 수정 완료 | 수정 후보의 복사 검사뿐 아니라 **주 실행의 실제 pick 및 파지·들림 검증** 후 assembly로 반환 |
| `recover_alignment` 완료 | 실제 파지 유지와 정렬 재검증 후 assembly로 반환하여 insert를 다시 판단 |
| `replan_insert` 완료 | 이 함수는 설치까지 수행하므로 설치 검증 후 해당 부품을 완료 처리하고 다음 부품의 assembly로 진행 |
| 지원 복구 없음 또는 예산 소진 | 중단 조건을 기록하고 종료 |

인계 자체는 Python 상태 전이다. 인계 문장 생성이나 “복구 성공” 선언을 위한 추가 모델 호출은 없다. 한 판단은 모델 생성 한 번으로 제한하고, 성공한 실제 insert는 Python 검증으로 완료한다. 불필요한 finish 생성 호출도 추가하지 않는다. 현재 코드의 복구 의미와 검증 연결을 유지한다. [S9,S14,S15]

인계 기록에는 실패·관측 revision·대상·이전 행동·검증·허용 대응·예산을 연결한다. 복사 실패와 실제 상태를 구분하며 단일 모드에도 같은 근거를 제공한다. `decision_mode`, `active_role`, 물리 작업 상태는 따로 기록한다.

### 6.3 기본 대화 구현: store=False와 수동 이력 전달

현재 조립 코드는 매번 한 개의 현재 packet을 전달하고 `store=False`를 사용한다. 이전 이력이나 응답 연결은 아직 구현돼 있지 않으므로 다음 공통 대화 관리기를 추가한다. [S5]

1. 최초 기하·작업 설정·완성품 이미지 두 장을 초기 문맥으로 등록한다.
2. 매 요청에 공통 instructions와 현재 역할 instructions를 명시적으로 공급한다.
3. 모델이 반환한 `response.output`의 재입력 가능한 항목을 원래 순서·식별자로 보존한다. opaque reasoning 항목도 임의로 제거하거나 사람이 읽는 사고 과정으로 변환하지 않는다.
4. 함수 제안을 검증·실행한 뒤 원래 `call_id`에 연결된 `function_call_output`으로 거부 또는 실제 실행·검증 결과를 추가한다.
5. 최신 관측·허용 행동·필요한 실패·검색 지침을 추가하고, 보존한 대화 이력과 함께 다음 요청에 전달한다.

SDK/API가 허용하는 재입력 형식으로 직렬화하되 원본 응답을 별도로 남긴다. 함수 호출 결과를 누락하거나 다른 호출의 결과와 연결하지 않는다. 과거 output을 임의 요약문으로 대체하지 않으며, 실제 실행되지 않은 제안을 성공 결과로 기록하지 않는다. 미완료·유효하지 않은 응답은 실행하지 않고 해당 정책 오류로 처리한다. [A1,A2,A3]

**초기 이미지는 논리적으로 두 장만 사용하지만, 수동 replay에서는 그 이미지가 이전 문맥의 일부로 다시 전달된다.** 초기 요청 한 번만 보내고 API가 자동으로 기억한다고 가정하지 않는다. 과거 문맥의 재전달·처리 비용을 실제 usage에 포함한다. 새 실패 사진을 Astra에 추가하지 않는 입력 정책은 유지한다. [A1]

기본안은 `previous_response_id`에 의존하지 않는다. 도입 시 저장·연결 방식을 양쪽 모드에 동일하게 변경해야 한다. 자동 요약·숨은 이력 삭제는 사용하지 않고 문맥 한도를 넘으면 중단 사유를 남긴다.

기존 `compact_context`의 32 KiB 검사는 **단일 상태 packet**에 대한 제한이다. 이미지와 전체 이력, instructions, tool schema를 포함한 요청의 토큰 계산이나 문맥 한도 검사를 대체하지 않는다. 기존 입력 토큰 count 요청과 모델 generation을 구분해 기록한다. 한 판단의 generation 한 번이 전체 HTTP 요청 한 번이라는 의미는 아니다. [S5]

## 7. 프롬프트와 출력 계약

### 7.1 공통 프롬프트

다음 문안을 두 모드에 동일 적용한다. 현재 동작·파지 계약은 별도 구조화 입력으로 공급한다.

```text
You propose exactly ONE next action for the current robot assembly task.

Treat the latest Python observation, verified action history, current part
and target, allowed actions, and remaining budgets as authoritative facts.
Earlier messages and goal images provide context; they do not override
the latest measured state.

Call propose_assembly_action exactly once. Use only the supplied part_id,
target_id, observation_revision, and a currently allowed action.
Python validates, executes, and verifies your proposal.

For pick, provide numeric grasp parameters only when a grasp contract is
present. Follow its bounds, units, and coordinate convention.
x_mm, y_mm, and z_mm are PART-frame offsets of the TCP.
jaw_yaw_deg follows the supplied contract.
For an upright part, increasing part-frame z_mm raises the grasp.
The downward TCP axis used to describe finger geometry does not reverse
that part-frame sign. Match the change to the direction in your reason.

Distinguish rejected simulation-copy checks from execution in the main
simulation. A passed copy check is not a verified physical pick or installation.

Apply retrieved guidance only when its stated conditions fit the current
task. Derive a candidate for the current geometry and use current verification.
Guidance cannot add actions, reset budgets, change the target order,
or establish success.

Do not invent measurements, contacts, causes, IDs, Python code, or new skills.
Do not reset the scene or blindly repeat a rejected candidate unchanged.
Write reason briefly in Korean, at most 512 characters, describing observed
evidence and the intended operational change. Do not output a chain of thought.

If no supported action is justified, choose stop when available.
Python alone determines installation completion and role transfer.
```

### 7.2 역할별 프롬프트

**단일 모드**

```text
You are the single assembly policy.
Handle both ordinary installation and supported recovery using the same
observations, action contracts, experience guidance, and total budgets.
After every result, use the fresh observation to choose the next allowed action.
```

**assembly 역할**

```text
You are the assembly policy.
Carry out the current installation using the latest observation and allowed
actions. Propose a grasp when requested.
After verified recovery handback, use its evidence and the fresh observation
to continue the original installation goal.
Python decides whether control transfers to recovery.
```

**recovery 역할**

```text
You are the recovery policy.
Examine the specific failure, relevant earlier actions, fresh observation,
and retrieved guidance. Select a supported recovery, a revised grasp within
the current contract, or stop.
Do not treat a passed copy check as a completed physical recovery.
Python verifies recovery postconditions and decides when control returns.
```

공통 정보·기능은 같고 역할별 주의 초점만 다르다. 명령은 순차 실행하며 인계 후 오래된 제안을 재실행하지 않는다.

### 7.3 출력과 검증

기존 strict function tool `propose_assembly_action`과 다음 필드를 유지한다. [S5,S6,S13]

| 필드 | 규칙 |
|---|---|
| `skill` | 현재 허용 목록의 행동 하나 |
| `part_id`, `target_id` | Python이 지정한 현재 대상과 일치 |
| `observation_revision` | 현재 revision과 정확히 일치 |
| `reason` | 한국어의 짧은 관측 근거·변경 의도, 최대 512자 |
| `grasp` | `grasp_task`가 있을 때만 schema에 포함. pick에는 수치 객체, 다른 행동에는 null |

파지 객체는 기존 `x_mm, y_mm, z_mm, jaw_yaw_deg` 계약을 따른다. 유한 수치·필드·단위·범위·revision을 검사하고, 실제 명령 직전 상태를 다시 확인한다. 범위 검사만으로 경로·파지·설치 성공을 판정하지 않는다.

현재 live frame의 설치 검증 후 자동 완료를 유지한다. `finish`를 기존 호환 기능으로 남기더라도 허용 목록과 실제 검증이 필요하며, 모델 선언만으로 성공 처리하지 않는다. [S9]

기본 few-shot은 0개다. 평가 과제의 정답 파지값·해결법을 프롬프트 예제로 미리 넣지 않는다. 형식 오류를 해결하기 위해 예시가 필요하면 해답이 없는 출력 형식 예시만 두 모드에 동일 추가하고 prompt version을 기록한다. 검색 지침과 실행 피드백이 실제 문제 문맥을 제공한다.

### 7.4 해결지침 생성 프롬프트

제어 중 매 단계가 아니라, 등록 후보의 근거가 완결된 뒤 별도로 사용한다. 해결지침 생성 비용도 수집 비용에 포함한다.

```text
Create one concise advisory guidance card from the supplied assembly incident.
Python has determined the incident and registration status.
Do not change that status or the source experience.

Return JSON using exactly these fields:
applies_when, strategy, checks, evidence_refs.

Write applies_when, strategy, and checks in concise Korean.
applies_when must retain the recorded phase, failure source, tool and
geometry conditions needed to understand this incident.
strategy must describe the evidenced adjustment and a currently supported
response to consider. Do not generate executable code.
checks must state what must be verified again in the present scene.
evidence_refs must contain only supplied evidence IDs.

Use only observed facts, action results, recorded parameter changes, and
installation verification. Do not invent measurements, contacts, or causes.
If a causal explanation is needed, label it as a hypothesis.
A successful instance does not establish a universal rule.
Quote numeric values only with their original units and coordinate frames.
Do not infer a successful installation from a passed preflight or recovery alone.
If evidence cannot support a usable card, return null for the three prose
fields and an empty evidence_refs array; Python will keep it pending.
Do not output a chain of thought or reproduce the full execution trace.
```

검증기는 해당 출력의 구조, 근거 ID, 인용 수치·단위, 지원 행동을 확인한다. 세 prose 필드가 모두 null이면 지침 보류로 처리한다. 모델 해석의 인과적 정확성이나 다른 제품에서의 성공이 이 검사로 입증되는 것은 아니다. 지침 생성 실패는 이미 검증된 물리 설치 성공을 취소하지 않는다.

## 8. 실패·복구와 중단

### 8.1 대응 그룹

| 관측된 상황 | 다음 대응 |
|---|---|
| 실제 pick 전 복사 파지 후보 거부 | 새 관측에서 숫자 파지안 수정 → 복사 검사 → 통과한 후보의 실제 pick |
| 잡은 부품의 미실행 운반 계획 거부 | 조건을 만족할 때 replan_insert |
| 삽입 전 정렬 실패 | 조건을 만족할 때 recover_alignment |
| 그 밖의 실제 집기·설치 실패 | 현재 지원 복구가 없으면 중단 |
| 입력·관측·시뮬레이션·제어·API·예산 문제 | 원인을 구분해 종료·기록 |

같은 failure_code라도 source·phase·현재 상태에 따라 대응이 달라진다. 복사본의 PART_LOST는 주 실행에서 물체가 떨어졌다는 뜻이 아니다. grasp_bounds의 수정 가능한 후보 범위 오류와 잘못된 부품 ID·관측·시스템 오류도 구분한다.

### 8.2 기존 복구의 정확한 범위

**숫자 파지 후보 수정:** 실제 물체를 내려놓고 다시 잡는 동작이 아니다. 복사 검사에서 거부된 후보를 수정하고 최신 원본 상태에서 재검사한다. 후보 통과와 원본 상태·revision 일치 후 실제 pick을 실행한다. 기존 GraphGraspRecovery의 특정 post_1 코드 스킬 경로를 범용 복구 기능으로 설명하지 않는다. 기본 모드는 공통 숫자 후보 수정만 사용한다. [S9,S25]

**운반 재계획:** 실패가 PLANNED_CONTACT, phase가 insert_transfer/preflight이고 해당 운반 명령이 실행되지 않았어야 한다. 부품·목표·로봇·그리퍼·보유 변환·설치 상태가 거부 당시와 맞고 미사용 거부 근거와 예산이 남아 있어야 한다. 임의 IK 실패나 삽입 중 접촉에 이 기능을 연결하지 않는다. direct_then_rrt를 사용하는 실행기가 경로를 계산하며, 전체 insert를 다시 실행하므로 설치까지 성공한 뒤 insert를 중복 실행하지 않는다. [S15,S24]

**정렬 복구:** ALIGNMENT_OUT_OF_TOLERANCE가 insert_alignment_check에서 발생하고 현재 파지가 유지돼야 한다. 현재 구현은 측면 오차 20 mm 이하, 림 여유 20 mm 이상, 자세 오차 1도 이하, 속도 1 mm/s 이하, 다른 물체의 지지를 받지 않는 상태 등을 확인한다. 실제 복구는 10 mm 상승과 측정 기반 재정렬을 포함한다. 이 값은 검토한 기존 실행기의 범위이며 새 제품에 대한 보편적 허용오차가 아니다. 최종 값은 해당 실행기 계약과 함께 버전으로 관리한다. [S14]

복구 성공 후에도 목적에 맞는 후조건을 확인한다. 정렬 복구 성공은 재삽입 가능 조건의 회복이며 설치 완료가 아니다. 지원하지 않는 실제 파지 상실·부분 끼임·깊이 실패를 임의 인출·재파지로 처리하지 않는다.

### 8.3 중단과 이어 실행

지원 복구 없음, 유효한 관측/실행 상태 확인 불가, 허용 예산 소진, 남은 복구 실패이면 중단한다. 중단은 현재 실행기와 예산의 결과이지 제품의 절대 조립 불가능 증명이 아니다. 상태·근거를 보존하고 자동 release/home/reset을 문제 해결로 집계하지 않는다.

검증된 checkpoint로 같은 논리 run을 이어갈 때 상태·목표·기억 snapshot·시도·API 예산을 보존한다. 임의 reset, 과거 상태로 되돌림, 초기조건 변경, 구현기 교체를 같은 연속 해결로 합치지 않는다.

현재 frame_resume.py의 추가 파지 후보 3개 예외는 새 누적 3개/부품 정책과 다르다. 기본 모드에서는 예산을 갱신하지 않도록 바꾸고, 별도 확장 예산 실험이라면 다른 조건으로 기록한다. [S29]

## 9. 경험과 해결지침

### 9.1 사건 하나의 경계

같은 논리 run·원래 부품 instance·설치 목표에서 첫 유효 실패가 나면 사건을 연다. 관련 이전 관측·파지·실제 pick을 참조로 연결한다. 같은 부품을 해결하는 동안 실패 코드가 바뀌어도 하나의 사건에 각 시도와 결과를 순서대로 남긴다.

원래 부품의 실제 설치 검증을 통과하면 solved_local로 닫는다. 복사 검사 통과, 실제 pick 성공, 정렬 복구 성공만으로 닫지 않는다. 아무 문제 없이 바로 설치된 경우는 일반 성공 로그로 남기며 문제 해결 경험을 만들지 않는다.

예산 소진·미해결·중단은 원본 로그로 유지하고 해결 사례 검색 인덱스에 등록하지 않는다. 해결된 사건 안의 실패한 중간 시도는 삭제하지 않는다. 복사 검사는 실제 실행에서 분기한 검사로 연결하고 그 궤적을 주 실행 물리 궤적으로 합치지 않는다.

### 9.2 저장 내용과 모델 입력

| 구성 | 내용 |
|---|---|
| 객관적 경험 | 사건/실행/부품/목표, 기하·작업·도구·버전·단위, 첫 문제와 관련 이전 행동, 모든 수정·검사·실행, 원래 설치 검증 |
| 해결지침 | 적용 조건, 권장 대응, 확인·제약, 근거 ID |
| 참조 자산 | 상세 trace, 실패 snapshot·이미지, 입력·설정·원본 hash와 모델/프롬프트 출처 |

논리적으로 경험과 해결지침 두 가지다. 물리적으로 한 사례 폴더 안에 JSON과 이미지·참조 파일을 두어도 되며 처음부터 여러 DB를 만들 필요는 없다. 교훈과 별도 LLM 생성 코드 스킬을 다시 나누지 않는다.

초기에는 사건당 지침 하나를 작성한다. 모델 해석은 객관적 사실 필드를 바꾸지 않는다. “파지 높이를 변경한 뒤 설치가 통과했다”와 “항상 높이가 원인이다”를 구분한다. 정확한 값·단위·접촉 상대가 기록되지 않았으면 만들어 넣지 않는다.

7절의 지침 출력 필드는 applies_when, strategy, checks, evidence_refs다. Python은 별도로 기계적으로 확인 가능한 applicability 조건을 관측·실행 계약에서 보유한다. 자유로운 지침 문장을 그대로 Boolean 적용 조건으로 실행하지 않는다. 검증기는 형식·근거·수치·지원 동작을 확인하며, 인과관계나 새 제품 일반화를 입증하는 검사는 아니다. null 보류 출력, 근거 부족 또는 생성 오류는 원본 경험을 유지한 채 지침 등록을 보류한다.

### 9.3 국소 해결과 등록

run 종료 후 원본 근거를 완결하고 등록한다. A가 해결된 뒤 B에서 전체 run이 실패할 수 있으므로 부품 사건의 결과와 전체 결과를 나눠 저장한다.

전체 실패 run의 A 경험을 등록하려면 설치 완료 당시 검증과 종료 시 A 및 필수 지지·결합 상대가 정상 설치 상태를 유지한다는 근거가 필요하다. 새 국소 보존 검사 어댑터를 추가한다. 기존 설치 검증기를 그대로 재호출하면 현재 그리퍼 개방 조건이나 다른 부품 검사 때문에 무관한 이유로 실패할 수 있다. 원래 해제·설치 증거를 유지하고 현재 관련 부품의 pose·속도·지지·끼움 관계만 적절히 확인한다. [S8,S15]

보존 검사를 위해 현재 로봇을 움직이거나 장면을 초기화하지 않는다. 자료가 부족하면 보류한다. 이 어댑터가 첫 구현에서 준비되지 않았다면 전체 실패 run의 후보를 보류하고, 검증된 전체 성공 run의 해결 사건부터 등록할 수 있다. 이 대체 범위를 구현 결과에 표시한다.

### 9.4 중복·기억 고정·출처

같은 사건을 재저장·재요약해도 하나의 독립 경험으로 센다. 논리 run/incident ID와 근거 hash를 사용한다. 원본 사례와 반환 지침·scope가 실제로 연결되는지도 확인한다.

실행 시작 시 검색 메모리를 고정한다. 이번 실행의 새 경험은 종료 후 등록하며 다음 실행부터 사용한다. 평가 묶음 전체는 같은 동결 memory snapshot을 사용한다. 분해와 조립의 저장 구조는 공통화하되 메모리 적용 영역은 구분한다.

현재 첫 결합 경험 검색은 미해결 사례도 반환하고, 슬리브 경험은 특정 부품·역할 이력·전체 성공에 제한된다. 새 공통 구조에서 기존 자료를 삭제하지 말고 적합한 것만 새 등록 절차로 이관한다. [S27,S28]

## 10. 검색과 지침 전달

### 10.1 검색은 Python이 수행한다

지원되는 대응이 남은 새 실패에서 검색한다. 별도 Astra 호출로 검색어를 만들지 않는다. pending_failure뿐 아니라 grasp_trials의 마지막 거부 결과도 공통 실패 이벤트로 처리한다. 새 실제 관측과 허용 동작을 만든 뒤 query를 구성한다. [S9]

아직 실패하지 않은 첫 파지 전 검색은 기본 모드에서 끈다. 기존 sleeve_memory_policy.py의 검색어 생성 호출은 별도 실험용으로 보존할 수 있으나 기본 모드에 섞지 않는다. stop만 가능하면 온라인 해결지침 검색을 생략할 수 있다. 동일 실패·관측·메모리 query의 결과는 역할 사이에서 공유한다. [S32]

### 10.2 적용 조건 필터

등록·지침 검사가 완료된 사례 중 다음을 확인한다.

- 조립·시뮬레이션 등 실행 영역과 실행 시작 snapshot.
- source·phase·failure_code 또는 명시적으로 버전 관리한 동등 문제 매핑.
- 검출된 접촉 관계·기하 조건·현재 파지/설치 상태 등 지침의 필요한 적용 조건.
- 로봇·그리퍼·실행기 계약과 설치 방식의 호환.
- 현재 판단에 필요한 첫 대응의 허용 여부와 남은 예산.
- 반환 scope·지침과 검증된 원본 사례의 일치.

부품/제품 ID 전체 일치를 일반 필터로 강제하지 않는다. 과거의 전체 행동 순서가 현재 allowed_actions에 전부 있어야 하는 것도 아니다. 현재 첫 대응과 후속 기능의 지원을 확인한다.

필수 조건이 관측되지 않았으면 확인된 것으로 처리하지 않는다. 형상 의미·원인을 LLM 문장에서 추출해 사실로 만들지 않는다. 과거의 파지 수치는 그대로 실행하지 않고 현재 기하·계약에서 새 후보를 검증한다.

### 10.3 영상 순위와 이미지 없음

기존 분해의 DINOv2-small, 384차원 L2 정규화 특징과 cosine 비교 구조를 재사용한다. 모델·가중치·구현·전처리·카메라 규격을 version으로 고정한다. 조립용 카메라 규격은 별도로 부여한다. [S30,S31]

| 모드 | 조건 | 반환 |
|---|---|---|
| visual | 정확한 현재 실패 이미지와 같은 규격의 과거 실패 이미지가 있고 적용 조건 통과 | cosine 내림차순 최대 3개 |
| metadata_only | 영상 비교는 불가하지만 필요한 문제·도구·기하 조건을 현재 기록만으로 직접 확인 가능 | 최대 1개 |
| none | 후보 없음 또는 필요한 조건 확인 불가 | 0개 |

비교할 과거 이미지는 필터에 일치한 바로 그 실패 이벤트에 연결돼야 한다. 같은 사건의 다른 실패를 첫 대표 이미지로 대신 비교하지 않는다. visual이 가능한 경우 metadata 결과를 가짜 점수로 섞지 않는다. 영상 없을 때의 metadata 경로는 신규 조립 기능이다.

초기에는 최소 cosine 임곗값을 임의 지정하지 않는다. 점수는 상대적 영상 특징 유사도이며 동일 원인·성공 확률을 뜻하지 않는다. 상위라도 덜 관련된 사례가 나올 수 있으므로 필수 조건과 실행 검증을 유지한다. cutoff는 개발 자료에서 정해 평가 전 고정할 수 있다.

같은 사건은 한 번만 반환하고 부족한 개수를 다른 문제로 채우지 않는다. visual 동점과 metadata 복수 후보의 순서는 case ID로 결정한다. metadata의 ID 순서는 효용이나 영상 유사도의 순위가 아니다.

### 10.4 문제 이미지 규격

대상 중심 고정 상면 정사영 한 장을 기본으로 한다. 작업 좌표계 방향, 여백·해상도, 대상 강조색, 그리퍼·주변 색상과 배경을 고정한다. 대상·그리퍼·검출된 접촉 상대·결합 상대와 필요한 주변 부품을 포함한다. 부품 ID나 실행 결과 글자가 영상 특징을 좌우하지 않도록 검색용 이미지와 보고용 라벨 이미지를 구분한다.

숨은 부품을 모델 판단으로 임의 제거하거나 매번 다른 시점을 선택하지 않는다. 한 장이 완전한 3D 관측이라는 주장은 하지 않는다. 카메라 변경 시 새 version으로 임베딩을 구성한다.

복사 검사 실패는 폐기 전 해당 실패 복사 상태를, 실제 실패는 주 실행 상태를 캡처한다. 미실행 계획 후보라면 candidate 출처를 명시한다. 실패 상태를 확보하지 못하면 없음/last_valid_context로 표시하고 후자를 실패 순간 영상처럼 비교하지 않는다.

사건 대표 저장 이미지는 첫 유효한 실패 한 장이다. 후속 다른 실패에서 새 검색이 필요하면 해당 snapshot의 query 한 장을 추가할 수 있다. 각 query가 독립 해결 사례를 생성하는 것은 아니다.

### 10.5 Astra 전달과 검색 기록

Astra에는 적용 조건·전략·확인 사항·근거 ID의 짧은 카드만 전달한다. raw vector, 과거 원본 이미지, 전체 trace를 보내지 않는다. 카드의 현재 적용 가능성을 확인하더라도 행동 허용·예산·성공 판정은 바뀌지 않는다.

빈 검색 결과는 정상이다. 렌더/인코더 장애, 데이터 무결성 오류, 적용 가능한 후보 없음은 로그에서 구분한다. 인덱스 캐시와 원본 archive의 지침·scope가 실제 일치하는지도 검사한다.

검색 로그에는 failure/action/check·관측 ID, 메모리 snapshot, 필터, 후보·제외 사유, 이미지·모델 version, 모드·점수·반환 사례, 처리 시간을 남긴다. 기존 SQLite/파일/NumPy 구조를 우선 활용하고 벡터 DB를 필수 서비스로 추가하지 않는다.

## 11. 실행 기록과 영상

### 11.1 원본 기록과 간결한 피드백

실행은 proposal, validation/preflight, execution, verification, recovery/transition을 구분한다. action ID는 재시도마다 새로 부여하고 검사·계획 후보는 별도 check ID와 부모 action을 가진다. 기존의 phase 문자열을 유일한 action ID로 사용하지 않는다.

Python은 자세한 관측·경로·실패·접촉 근거를 보관하고 Astra에는 최신 상태, 핵심 실패, 관련 이전 행동, 허용 대응과 검색 지침만 전달한다. 실패 당시 snapshot과 다음 판단의 최신 관측을 분리한다. live_simulation, mujoco_preflight_copy, planner/IK candidate 등 출처를 명시한다.

기존 skill_trace.csv, graph_events.jsonl, failure_report.json/개별 failure, 파지 사전검사 trace를 재사용한다. 기존 콜백이 검증 통과한 표본만 남기는 경우 실패 직전 표본을 실패 순간으로 대체하지 말고, 검사 거부 시점의 상태를 별도로 캡처한다. [S20,S21,S22,S23]

거부된 후보의 겹침·계산 거리, 실제 접촉력, 마지막 정상 값은 구분한다. 특정 패드 높이를 전체 경로의 최소 여유라고 표시하거나, 제한된 탐색 실패를 물리적 경로 부재 증명으로 저장하지 않는다.

### 11.2 연속 영상은 별도 상태 기록기로 만든다

현재 viewer와 실제 MuJoCo 상태 PNG는 재사용할 수 있다. 그러나 기존 TCP·활성 부품 중심 CSV가 전체 로봇·그리퍼·모든 부품의 연속 재생 자료를 이미 제공한다고 가정하지 않는다. [S21,S26]

새 영상 기록기는 다음을 수행한다.

1. 주 실행의 로봇·그리퍼·모든 부품을 재현할 상태와 시뮬레이션 시각을 일정 주기로 저장한다. 초기 권장값은 20 fps이며 물리 step/설정과 함께 기록한다.
2. 모델·자산 hash, MuJoCo 버전, action/check/source를 연결한다. 기존 mjSTATE_INTEGRATION checkpoint를 참고하되 주기 기록은 새로 연결한다.
3. 기록된 상태를 별도 renderer에서 읽어 MP4와 주요 PNG를 만든다. 목표 pose 사이를 보간해 실행한 것처럼 만드는 영상은 사용하지 않는다.
4. 실패 순간은 정기 표본과 별개로 캡처한다. 정기 영상 프레임이 충돌 순간을 정확히 담는다고 가정하지 않는다.
5. 복사 검사·계획 후보·주 실행 영상과 cut을 명시한다. 서로 다른 run을 하나의 연속 성공으로 이어 붙이지 않는다.

렌더링을 위해 실제 로봇 동작을 다시 수행하지 않는다. replay는 기록된 실행을 보는 기능이며 새 물리 성공 실험으로 세지 않는다. 필요한 상태/모델/코덱이 없거나 렌더가 실패하면 media_status를 별도로 보고하고, 물리 성공과 미디어 완료를 서로 덮어쓰지 않는다.

## 12. 경험 수집과 평가

### 12.1 먼저 검증할 과제 범위

첫 비교 실험은 고정 바닥판과 기둥 하나, 또는 고정 바닥판·기둥·슬리브로 구성된 작은 조립 셀에서 수행한다. 실행 시간이 짧고 문제의 원래 대상이 분명한 과제에서 입력·실행·복구·메모리 연결을 먼저 확인한다. 전체 프레임은 별도의 통합 시연 과제로 두며, 실제 연속 실행과 마지막 물리 검증을 통과한 경우에만 전체 완주로 보고한다.

현재 build_frame_scene의 first_sleeve_cell은 기둥·슬리브 셀을 지원하지만 runner의 특정 single 모드 모델 설정과 연결돼 있다. 새 구현은 장면 profile을 모델·역할 설정에서 분리해 네 비교 조건이 같은 셀을 사용하도록 한다. 일반 --parts 3은 제품 목록의 앞부분을 선택하므로 자동으로 기둥·슬리브 셀이 된다고 가정하지 않는다. [S26,S36]

국소 과제에서 앞서 설치된 부품을 초기 조건으로 제공할 수 있으나, 그 부품들은 로봇이 이번 실행에서 설치한 것으로 세지 않는다. 초기 배치의 pose·지지·결합 관계를 검증하고 initial_installed와 이번 실행의 실제 설치 목록을 구분한다. 부분 조립 목표의 성공을 전체 제품 완주로 표현하지 않는다.

현재 큰 프레임의 과거 장애물 시연에는 여러 번의 운반 재계획이 필요했던 기록이 있다. 이 과제를 재계획 1회/run인 주 평가에 그대로 넣어 전체 성공을 기대하지 않는다. 작은 과제의 장애물 조건을 별도로 선언하거나, 다중 재계획 과제는 다른 예산층의 추가 시연으로 분리한다. 서로 다른 예산의 결과를 같은 비교표에서 합산하지 않는다. [S37]

### 12.2 비교할 네 조건

| 조건 | 역할 구성 | 과거 경험 검색 |
|---|---|---|
| S0 | 단일 역할 | off |
| S1 | 단일 역할 | on |
| R0 | 조립·복구 역할 분리 | off |
| R1 | 조립·복구 역할 분리 | on |

모델 식별자·reasoning 설정, 기하와 초기 상태, 로봇·그리퍼·실행기, 최초 이미지, 관측·행동 계약, 복구 예산, API·토큰·비용 상한을 동일하게 유지한다. memory-on 두 조건은 같은 등록 사례와 검색 규칙을 사용한다. memory-off에서도 현재 실행의 실패 피드백과 대화 이력은 유지한다. 차이는 과거 실행에서 얻은 지침의 조회 여부다.

각 case의 네 조건은 동일한 초기 장면을 받는다. 실행 순서는 조건별로 몰아서 수행하지 않고 case별로 회전하거나 사전에 정해 저장한다. 동일한 물리 입력이 모델 출력의 완전한 재현성을 보장한다는 뜻은 아니다.

자동 준비한 장면도 case별로 한 번 검증·저장해 네 조건에 동일 적용한다. 모델 모드에 따라 더 쉬운 배치가 나오도록 준비기를 다르게 호출하지 않는다. 자동 준비 성공률과 소요 시간, 수동 보정 여부를 조립 실행 결과와 별도로 보고한다. 준비에 실패한 입력을 전체 사용자 흐름의 결과에서 숨기지 않으며, 조립 정책 비교의 실행 대상과 분모는 사전에 정한 조건에 따른다.

### 12.3 시작 규모와 시행 순서

아래 횟수는 빠른 파일럿을 위한 시작 규모·상한이다. 통계적 충분성이나 목표 성공률을 보장하지 않으며, 모든 단계를 끝내야 경험 수집을 시작하는 것은 아니다.

| 단계 | 시작 규모 | 목적 |
|---|---:|---|
| 오프라인 물리 확인 | 대표 경로 4개 | 정상 설치, 파지 후보 거부 후 수정, 정렬 복구, 운반 재계획 |
| 실제 Astra 연결 확인 | 총 4회 | 먼저 S0·R0 각 1회, 메모리 준비 후 S1·R1 각 1회 |
| 개발 | 6조건×2역할 모드, 12회 이내 | 상태 전달·프롬프트·실행 상한 보정 |
| 경험 수집 | 별도 10조건×2역할 모드, 최대 20회 | memory-off에서 사건을 수집하고 공통 지침 구성 |
| 파일럿 평가 | 미사용 10조건×4비교 조건, 40회 | 역할 구성과 과거 메모리의 효과 비교 |
| 통합 시연 | 전체 프레임 과제 1개 | 분해 전달부터 연속 조립·영상 결과까지 검증 |

오프라인 물리 확인은 규칙 정책으로 실제 MuJoCo를 실행하는 검사다. API를 흉내 낸 mock 계약 검사와 구분하고, Astra의 판단 성능으로 집계하지 않는다. 최초 실제 연결이 확인되면 개발·수집을 시작할 수 있다. 수집 후 지침과 인덱스를 고정하고 memory-on 연결을 확인한 다음 평가로 진행한다.

수집 20회는 해결 경험 20개를 뜻하지 않는다. 한 실행에서 여러 문제 사건이 생길 수 있고, 해결 사례가 하나도 생기지 않을 수도 있다. 미해결 로그는 보존하되 해결 사례 검색에 등록하지 않는다. 유효한 메모리가 비어 있으면 그 사실을 보고하고, memory-on 효과를 확인했다고 주장하지 않는다.

### 12.4 초기조건·문제 주입·출처

실험 manifest에는 과제 ID, 장면 profile, 실제 설치 대상과 목표, 초기 pose·설치 상태, 장애물·교란 설정, 사용한 seed, 구현 버전, split과 실행 조건을 기록한다. 장면 seed와 경로 탐색 seed를 구분한다. 현재 경로 계획기의 seed가 조립 장면 전체를 무작위 생성하는 기능이라고 가정하지 않는다. 공통 manifest·초기조건 생성기·평가 driver는 추가 구현 항목이다. [S26,S34,S35,S39]

교란은 선언된 초기화 단계 또는 명시된 시험 훅에서 적용한다. 실행 중 물체를 임의로 이동시키고 자연 발생 실패로 기록하지 않는다. 지원 범위 밖이거나 물리적으로 유효하지 않은 초기조건의 제외 규칙은 평가 결과를 보기 전에 정한다.

| 출처 | 기록 규칙 |
|---|---|
| 자연 발생 실패 | Astra가 실제 제안한 후보·행동과 관측된 실패를 연결 |
| 통제된 문제 | 고정된 불리한 첫 후보, 정렬 오프셋 등의 주입 위치·값·시점과 작성 주체 기록 |
| 규칙 기반 수정 | scripted 또는 mixed 출처로 기록하고 Astra 자율 해결 실적과 분리 |
| mock 응답 | 계약 검사에 사용하고 실제 모델 호출·물리 해결 데이터로 집계하지 않음 |

현재 first_alignment_offset은 삽입 명령에 정해진 오프셋을 주는 개발 조건이고, first_post_grasp_interference의 첫 후보는 DevelopmentFirstGrasp가 고정한다. 새 비교에서는 문제 주입을 특정 메모리·코드 스킬 선택 기능과 분리해야 한다. 네 조건 모두 같은 첫 문제와 같은 복구 기능을 받도록 한다. [S9,S38]

강제한 첫 파지 후보도 부품별 총 후보 예산에 포함한다. 그 후보를 모델이 제안한 것으로 표시하거나 발생하지 않은 API 호출을 세지 않는다. 자연 실패와 통제된 문제의 결과는 별도 행·소계로 보고한다. 통제된 문제 해결률을 일반 작업에서 자연적으로 얻은 조립 성공률로 표현하지 않는다.

### 12.5 수집·평가 분리

개발, 경험 수집, 평가용 초기조건 목록을 구분한다. 같은 원본 실행의 복사 검사, checkpoint, 재시작, 이미지와 지침은 공통 출처를 유지한다. 같은 실행의 다른 파일이나 실패 장면을 별개의 독립 평가 과제로 취급하지 않는다.

주 평가의 메모리는 수집 split에서 검증한 사례로 구성한다. 개발 중 프롬프트를 다듬는 데 사용한 조건은 평가에서 제외하고, 원본 사건이 같은 변형을 수집·평가에 나눠 넣지 않는다. 데이터의 버전과 제외 목록을 함께 고정한다.

평가를 시작하기 전에 프롬프트, 실행기, 검색 설정과 메모리 snapshot을 동결한다. 평가에서 새로 생긴 경험은 이후 실험을 위해 보관할 수 있으나 현재 평가 묶음의 검색 집합에는 추가하지 않는다. 평가 결과를 보고 그 평가의 검색 임곗값이나 예산을 변경하지 않는다.

같은 프레임의 미사용 초기 위치를 평가했다면 “동일 과제군 내 미사용 초기조건 평가”라고 설명한다. 새 CAD·제품에 대한 일반화를 주장하려면 기하·제품 계열을 분리한 추가 평가가 필요하다. 이는 첫 졸업 프로젝트 프로토타입의 필수 범위는 아니다.

### 12.6 지표와 결과 해석

| 지표 | 정의 |
|---|---|
| 과제 성공률 | 지정한 전체 과제 목표의 물리 검증 통과 run 수 / 시작한 평가 run 수 |
| 부품 설치 결과 | 이번 run에서 검증한 설치 수 / 선언된 목표 설치 수 |
| 사건 해결률 | 원래 대상 설치와 보존 조건을 만족한 문제 사건 수 / 확인된 물리 문제 사건 수 |
| 복구별 결과 | 파지 후보 수정·정렬·재계획의 시도 수와 성공 수, 이후 원래 설치 성공 여부 |
| 검색 결과 | hit·miss·검색 오류, 모드, 반환 사례와 실제 사용한 지침 ID |
| 시간 | 벽시계 경과, 모델 대기·검색·렌더·사전검사 시간, 원본 시뮬레이션 시간 |
| 모델 사용량 | 실제 요청 수, 입력·출력·캐시·추론 사용량이 제공되면 해당 값, 확인된 비용과 미확정 비용 |

정렬 복구 함수의 성공을 사건 해결로 바로 세지 않는다. 자연 발생 사건은 모드마다 어려움과 발생 빈도가 달라질 수 있으므로 사건 해결률만으로 우열을 판단하지 않고 과제 성공률과 통제된 문제 비교를 함께 제시한다.

정책의 stop, 후보·복구·호출·시간 예산 소진은 성공하지 못한 실행이다. API 장애·시뮬레이션 이상은 별도 사유로 기록한다. 기본 표에는 시작한 전체 실행과 모든 종료 상태를 보이고, 인프라 정상 실행만의 조건부 성공률을 추가할 때는 제외 수와 분모를 함께 공개한다. 재시도 결과로 원래 실패 행을 덮어쓰지 않는다.

시간 비교는 같은 장비·실행 설정에서 수행하고, 무거운 시뮬레이션을 동시에 실행해 CPU 경합이 생긴 기록을 일반 단일 실행 시간과 섞지 않는다. 복사본 검사 계산량을 원본 시뮬레이션의 물리 진행 시간으로 합치지 않는다. 표본이 작은 파일럿에서는 성공 건수/전체 건수, 조건별 결과와 시간·사용량 분포를 함께 제시한다.

## 13. 실행 예산과 비용

### 13.1 공통 행동·호출 한도

N은 초기부터 설치돼 있던 부품을 제외한 이번 과제의 로봇 설치 대상 수다.

| 항목 | 첫 구현 기준 |
|---|---|
| 파지 후보 | 최초 포함 최대 3개/부품, 동일 사건과 이어 실행에서 누적 |
| 정렬 복구 | 최대 1회/run |
| 운반 경로 재계획 | 최대 1회/run, 부품당도 최대 1회 |
| 실제 내려놓기·재파지 | 이번 MVP 범위에 포함하지 않음 |
| 제어 모델 생성 요청 | 최대 4N+4회/run을 초기 상한으로 사용 |
| 모델 출력 한도 | 기존 2,048토큰을 초기값으로 유지 |
| 해결지침 생성 | 등록 후보 사건당 최초 1회, 제어 판단 장부와 별도 집계 |

생성 요청 수 4N+4는 최대 3개 파지 후보와 설치 판단, 추가 복구를 위한 운영 상한이다. 입력 토큰 count HTTP 요청은 별도 수로 기록하며 이 생성 횟수와 섞지 않는다. 기존 승인 요청 한도가 더 작으면 더 작은 한도가 적용된다. 실제 호출을 그 수까지 채울 필요는 없다. 물리 검증으로 완료된 상태에 불필요한 finish 호출을 추가하지 않는다. 실패한 복구와 형식 오류·불완전 응답도 발생한 요청·비용 장부에 남긴다. 역할 전환·새 객체·checkpoint 재개로 상한을 초기화하지 않는다.

### 13.2 토큰·금액·시간 설정

기존에 승인된 호출·토큰·금액 상한을 유지한다. 명시된 상한 밖의 실행을 자동으로 시작하지 않으며, 실제 모델·가격·상한이 없는 설정으로 유료 수집을 무제한 실행하지 않는다. 설정을 보완해야 할 때는 현재 프로젝트의 설정 파일과 운영 권한을 따르고 새 승인 흐름을 임의로 추가하지 않는다.

최초 연결과 개발에서 사용량을 확인해 과제별 상한을 조정하고, 평가 전에 네 조건에 공통으로 고정한다. 초기 이미지 2장과 누적 대화를 도입하므로 과거 단독 요청의 입력 상한을 그대로 충분하다고 가정하지 않는다. 출력 2,048토큰에서 불완전 응답이 반복되면 개발 조건에서 원인을 확인하고 모든 비교 모드에 같은 변경을 적용한다. 평가 도중 특정 모드에만 더 큰 한도를 주지 않는다.

요금표는 실제 실행 모델의 공식 자료로 확인하고 출처·확인일을 설정에 기록한다. 과거 설정의 단가를 현재 가격으로 주장하지 않는다. 청구 사용량과 캐시 관련 값은 제공된 실제 응답에 따라 정산한다. 알 수 없는 사용량·비용은 0이 아니라 미확정 또는 예약 값으로 보존한다.

호출별 timeout과 run 전체의 벽시계 상한을 명시하고 동일한 과제의 네 조건에 적용한다. 모델·검색·물리 실행의 대기 시간을 포함하며, 외부 호출의 완료 여부가 불명확할 때 같은 물리 명령을 자동 재실행하지 않는다. 기존 LlmConfig/ApiLedger의 승인된 상한·예약·정산 검사를 유지한다. [S33]

### 13.3 경험 생성 비용

해결지침 생성은 제어 중 매번 호출하지 않고 사건 근거가 정리된 뒤 수행한다. 최초 1회 생성이 실패하면 사건 원본을 보존하고 지침 등록을 보류한다. 재처리가 필요하면 별도 작업과 비용으로 기록하며 숨은 반복 호출로 처리하지 않는다.

경험 수집·지침 생성·이미지 임베딩 준비 비용과 평가 중 제어·검색 비용을 구분해 보고한다. 지침 생성 실패가 이미 검증된 물리 조립 성공을 취소하지는 않는다. 반대로 지침 생성 성공이 원래 조립의 성공 증거가 되지도 않는다.

## 14. 완료 기준

완료는 아래 계층별로 실제 확인한 범위를 보고한다. 하위 계층 통과만으로 상위 계층까지 완료했다고 표시하지 않는다.

| 계층 | 필요한 증거 |
|---|---|
| 사용자 흐름 | 제품 입력부터 분해 호출/결과 재사용, 자동 준비, 실행과 결과 확인까지 한 진입점으로 연결 |
| 입력 연결 | 분해 전달 묶음의 ID·메시·단위·좌표·목표·순서 검증, 조립 작업장과 현재 상태 연결 |
| 제품 자동 준비 | 지원 종류의 새 입력에서 제품별 코드·좌표·전용 registry 수동 작성 없이 목표·준비 자세·배치·작업 조건 생성과 검증 |
| mock 계약 | 두 역할 모드와 memory off/on의 입력·출력·예산·실패 연결 검사. 실제 모델 성능으로 세지 않음 |
| 실제 물리 실행 | 규칙 정책을 포함해 실제 MuJoCo에서 파지·운반·설치·복구와 독립 성공 검증, 출처가 있는 trace |
| 실제 Astra 실행 | 실제 응답·검증된 행동·공유 사용량 장부가 같은 run에 연결되고 목표 설치를 검증 |
| 경험 재사용 | 별도 실행에서 만든 해결 사건을 등록·고정하고 새 실행의 검색·지침 사용·현재 장면 검증을 추적 |
| 미디어·보고 | 재생 가능한 영상과 장면 이미지, 성공/실패·복구·시뮬레이션 출처 표시, 표와 원본 기록의 일치 |

최소 통합 결과물에는 입력 묶음, 고정된 실행 설정과 버전, 원본 관측·행동·실패·검증 기록, API 사용량, 등록 사례와 검색 기록, metrics 표, 성공·실패 대표 이미지, 연속 실행 영상을 포함한다. 영상은 실제 실행 상태에서 생성하고 실패 장면·복사 검사·다른 run의 성공을 하나의 연속 실행처럼 편집하지 않는다.

전체 프레임 데모의 완주는 필수 목표로 남기되, 아직 완주 증거가 없으면 완료 판정을 보류하고 어느 단계에서 멈췄는지 제출한다. 부분 과제 성공 영상으로 전체 프레임 완주를 대체하지 않는다. 새로운 분해 역순 후보가 입력 검사를 통과했다는 사실과 로봇이 그 순서를 실제로 완주했다는 사실도 구분한다.

자동 준비 검증에는 기존 고정 부품명과 다른 ID, 허용 범위의 치수·부품 수 변화가 있는 입력을 포함한다. 같은 지원 종류의 새 입력 적어도 하나에서 사용자 제품별 수정 없이 준비부터 실제 조립까지 완료한 근거가 필요하다. 단순 ID 변경이나 미지원 결과 출력만으로 형상 일반화·조립 성공을 입증하지 않는다. 작업 조건 생성기를 구현하지 못한 경우에는 초기 배치만 자동화했다고 정확히 보고한다.

Codex 최종 보고에는 변경한 파일, 연결한 기능, 실제 실행한 검사와 결과, 실제 Astra 호출 여부, 남은 실행 차단 조건, 재현 명령과 산출물 위치를 포함한다. 테스트 수만으로 물리·모델·재사용·전체 시연의 완료를 대신하지 않는다.

## 15. Codex 구현 단위와 파일 지도

아래 이름은 현재 연결점과 신규 제안의 구분이다. 실제 최신 저장소 구조에 맞춰 함수·경로를 정리하되 기능 계약을 유지한다.

| 작업 | 현재 연결점 | 추가·수정 내용 |
|---|---|---|
| 공통 입력 | planner_candidate_input.py, import_framework_battery.py | 새 export 어댑터·원본 검증·제품 task 매핑 |
| 제품 자동 준비 | 기존 제품 registry·frame_assembly_scene.py·workcell_scene.py | 공통 환경 profile, 지원 종류 템플릿, 데이터 기반 장면·초기 배치 생성 |
| 입력/현재 상태 | frame_product.py, frame_assembly_scene.py, frame_assembly_skills.py | 기하·목표·현재 상태 정규화, 첫 입력 PNG/JSON 출력 |
| 판단/대화 | openai_policy.py, assembly_policy.py | 공유 이력·tool 결과·공통/역할 prompt·strict schema |
| 실행/역할 | assembly_graph.py, run_frame_assembly.py | 최신 관측→검색→역할→실행→검증의 공통 연결 |
| 실패/재개 | failure_report.py, grasp_preflight_trace.py, frame_resume.py | 고유 사건·출처·정확한 상태와 누적 예산 |
| 기억/검색 | experience_memory.py, sleeve_grasp_memory.py, sleeve_memory_policy.py | 공통 사건·지침·등록·DINO검색, 이전 특수 경로 기본 비활성 |
| 미디어 | run_pick_place.py의 renderer, checkpoint 함수 | 주기 상태 기록·MP4·정확한 실패 snapshot |
| 실험 | 기존 개별 runner·benchmark 코드 | profile/manifest·수집·2×2 driver·집계 |

신규 파일은 예를 들어 disassembly_export_input.py, assembly_context.py, assembly_case_memory.py, assembly_media.py, run_assembly_experiments.py로 둘 수 있다. 이미 존재하는 기능이라고 문서화하지 않는다.

구현 순서는 입력 계약·기존 물리 회귀를 확보한 뒤 공통 판단/대화, 실패·기억·검색, 미디어, 배치 평가를 연결한다. 이는 하나의 전체 작업 안의 내부 순서다. 사용자에게 모듈별 재승인을 요청하며 중간 단계에서 멈추는 운영을 요구하지 않는다.

권한·API 키·자산 등 실제 환경 제한이 있으면 가능한 구현과 검증을 완료하고 막힌 단계·필요 자료를 구체적으로 보고한다. 실행하지 않은 검증은 미실행으로 남긴다. 대규모 수집·평가 명령은 명시한 실행 범위·예산 안에서만 수행하며 완료한 것처럼 미리 기록하지 않는다.

## 16. 설계 완료와 전달

v1.2는 v1.1의 제품별 수동 설정 없는 사용 목표를 유지하며 초기 격자 배치와 시뮬레이션 작업대 XY 자동 확장을 구체화한 구현 기준이다. 기존 실행·복구·기억·평가 계약은 유지하고, 3.4–3.6의 제품 자동 준비를 새 작업으로 포함한다. JSON 세부 키, 신규 파일명, renderer 연결 방식, 실제 장면 교란값은 여기서 정한 의미·지원 범위·검증 조건 안에서 Codex가 구현하며 정리한다.

남은 작업은 자동 준비를 포함한 실제 코드 수정, 지원 종류별 작업 조건 생성과 물리 실행의 통합 검증, 경험 수집과 평가다. 자동 준비 요구가 문서에 들어갔다는 사실로 새 제품의 범용 처리가 완료됐다고 판단하지 않는다. 생성 규칙을 구현·검증할 수 없는 조립 종류는 제한을 구체적으로 남긴다.

- ASSEMBLY_MASTER_DESIGN_v1.2.md: 전체 설계와 프롬프트·평가·완료 기준.
- ASSEMBLY_CODEX_HANDOFF_v1.2.md: 저장소에서 전체 변경을 수행하기 위한 작업 지시.

v1.0에서 정리한 출력·복구·경험·검색·공유 대화·평가 기준을 유지한다. v1.2의 변경은 초기 배치와 작업대 XY 크기 생성에 한정하며, 별도의 자동 급품·범용 결합 추론 과제로 확대하지 않는다. v1.1의 주요 변경은 제품 입력 단일 진입점, 공통 환경과 제품별 자동 생성 정보의 분리, 초기 배치 자동화, 지원 종류의 작업 조건 생성, 사용자 흐름의 완료 기준이다. 실제 재파지·자동 급품·범용 체결 의미 추론은 후속 범위다.
