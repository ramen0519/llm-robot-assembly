# 22J — 제한 계산 환경에서 스킬 후보 실행·출력 검사

작성: 2026-11-10. 범위: 현재 관측과 최신 거절 사건 → 호스트 검사 → 저장 후보 계산 → 재관측 → 파지 출력 검사.

**실제 Luna 원본 후보를 별도 계산 프로세스에서 해석해 파지값 또는 보류를 반환하는 연결부를 구현했다.** 새 검사 38개, 기존 후보·교훈 검사 69개가 통과했다. 최종 probe의 8개 시나리오도 기대 결과와 일치했다. API 호출·로봇 명령·`mj_step`은 모두 0회다. MuJoCo 새 장면은 생성하고 관측했지만 집기·삽입·파지 사전검사는 실행하지 않았다.

## 1. 이번 단계의 의미

이전 22I는 코드의 글자와 문법을 검사했다. 이번에는 그 코드가 조건을 판단하고 실제 숫자를 계산하도록 한다. 다만 생성 코드에 컴퓨터나 로봇 전체 권한을 주지 않는다.

- **호스트:** 우리가 작성한 연결부다. 현재 관측, 실패 기록, 적용 조건, 남은 횟수와 계산 결과를 검사한다.
- **VM:** 허용된 계산식과 조건문만 해석하는 작은 계산기다. 일반 Python의 `exec`·`eval`로 생성 코드를 실행하지 않는다.
- **자식 프로세스:** 이 계산기만 잠깐 실행하는 별도 프로그램이다. 끝나면 종료하고, 제한시간을 넘기면 중단한다.

생성 후보가 정상값을 반환하더라도 최종 판단은 호스트가 한다. 반대로 조건이 맞지 않으면 계산을 아예 시작하지 않을 수 있다. 출력이 `None`인 보류와, 오류·관측 불일치로 인한 거부는 서로 다른 상태로 남긴다.

## 2. 입력과 전체 흐름

1. `capture_observation()`이 현재 MuJoCo 장면의 부품 자세·속도·접촉, 지지, 그리퍼 간격, 실행기의 파지 상태를 읽는다. 관측을 위해 초기화·이동·시간 진행을 하지 않는다.
2. `make_observation()`은 관측 번호, 회차 ID, 적용 조건과 상태 fingerprint를 묶는다. fingerprint는 값이 달라졌는지 찾는 표식이지 물리적 진실성을 인증하는 서명이 아니다.
3. 호스트가 사전검사 거절을 받았을 때 `bind_rejection()`으로 당시 관측과 연결한다. 과거 Lesson의 거절을 현재 장면의 실패인 것처럼 전달하지 않는다.
4. `evaluate_candidate()`가 후보 근거, 현재 관측, 정확한 조건·설치 목록, 빈손·지지·정지·수직·열린 그리퍼, 제안 예산을 확인한다.
5. 현재 관측을 다시 읽어 변경 여부를 확인한 뒤, 후보 함수에는 기존 계약의 7개 입력 필드만 전달한다. 로봇 객체나 파일 경로는 넘기지 않는다.
6. 제한 VM에서 `propose(ctx)`를 계산한다.
7. 계산 후에도 다시 관측한다. 그 사이 장면이나 관측 번호가 달라지면 계산값을 버린다.
8. 반환값이 `None`이면 보류한다. 숫자 제안이면 네 필드·유한 수치·부품 경계·각도 범위를 검사한다. 실패한 값은 자동으로 자르거나 수정하지 않는다.

제안에는 현재 part/target/episode/revision, observation ID, 후보 코드 hash, 거절 ID를 호스트가 붙인다. 아직 `pick()`을 호출할 수 있는 실행 승인 결과는 아니다. `requires_current_scene_preflight=True`, `execution_authorized=False`를 유지한다.

## 3. 호스트가 강제하는 조건

| 항목 | 검사 |
|---|---|
| 자료형 | 참/거짓 값은 정확한 bool만 수락. 정수 1/0을 대신 넣는 입력 거부 |
| 관측 최신성 | 호출 전·후 현재 관측을 비교. 같은 시각의 관절·부품·제어값 변경도 fingerprint로 탐지 |
| 기록 조건 | UR3e·2F85·명목 TCP·part-local 중심·mm/deg·top-down, config/joint·MuJoCo 버전 일치 |
| 설치 상태 | 과거 사례의 시작 설치 목록이 알려져 있고 현재 목록과 같아야 함. unknown을 빈 목록으로 바꾸지 않음 |
| 지원 부품 | upright box, X/Y 20–60 mm, Z 30–80 mm |
| 빈손 | 실행기의 held state 및 현재 양쪽 패드 접촉 확인 |
| 지지·자세 | 지지가 관측되고 수직 1° 이내 |
| 속도·개방 | 선속도 <1 mm/s, 각속도 <0.01 rad/s, 패드 간격 ≥80 mm |
| 실패 연결 | 같은 회차·동일 상태의 거절이어야 함. 실패 코드와 단계가 교훈의 질문과 일치 |
| 예산 | 호스트가 정한 남은 제안 횟수 0–3, 0이면 계산하지 않음 |
| 출력 | 정확한 `x_mm/y_mm/z_mm/jaw_yaw_deg`, bool 금지, 유한 수치, 위치 ±반치수, 각도 ±180° |

실패 후 다시 관측하면 관측 번호만 증가할 수 있다. **물리 상태가 그대로인 경우에는 이전 거절을 새 관측 번호와 연결해 사용할 수 있도록 했다.** 상태·회차·조건이 바뀐 거절은 사용하지 않는다.

이 비교는 기록된 활성 부품 조건의 일치다. 전체 장면의 충돌 없음이나 모델 버전 전체의 물리적 적합성을 보증하지 않는다. 현재 검증에서는 C1/C2가 일치했으며, 설치 시작 상태가 unknown인 C3는 사용하지 않았다.

관측 속도가 순간적으로 낮다는 사실은 일정 시간 동안 안정됐다는 검사와 다르다. 기록에 `instantaneous_measurement_not_settling_window`를 명시했다. 기존 `settle()`·이동·사전검사의 조건을 완화하지 않는다. 임의의 복원 장면에 새 skills 객체를 붙여 `held_pose=None`이 됐다고 빈손으로 해석해서도 안 된다. 실제 연결 시 계속 사용 중인 실행기의 상태 이력을 유지하고 장면 접근을 직렬화해야 한다.

## 4. 제한 계산 환경

분해 프로젝트의 `orchestrator/python_skill_vm.py`를 바이트 그대로 고정 복사했다. 출처와 SHA256은 `scripts/vendor/SOURCE.md`에 남겼다. 원본에 명시적 라이선스가 확인되지 않아 공개 라이선스로 추정하지 않았다. 다른 저장소를 실시간으로 import하지 않는다.

| 제한 | 현재 설정 |
|---|---|
| 허용 문법 | 22I의 함수 1개·지역 대입·조건문·사칙연산·제한된 min/max/abs·자료 읽기·반환 |
| 소스 | 최대 16 KiB, AST 최대 600개. 부모와 자식 모두 검사 |
| 계산 횟수 | 기본 1,000단계, 호출 시 최대 5,000단계 |
| 실행시간 | 자식 종료 대기 기본 3초, 최대 5초. 초과 시 종료·정리하고 재시도하지 않음 |
| 입력 | 순수 JSON 값만, 순환 객체·비유한 수치·과도한 크기/깊이 거부. context 최대 16 KiB |
| 프로세스 출력 | stdout 최대 32 KiB, stderr 최대 4 KiB. 초과 시 중단 |
| 자격증명 | API 키·사용자 PATH·Python 환경 설정을 자식에 전달하지 않음 |
| 파일·로봇 접근 | 생성 코드에 경로나 객체·import·임의 함수를 제공하지 않음 |

실제 원본 VM은 더 넓은 문법을 지원하지만 이 연결부는 22I 검사로 범위를 좁힌다. vendor 파일·정적 검사기·코드·입력의 hash와 실제 import 위치도 확인한다. 입력은 복사하며 자식 결과도 엄격한 JSON으로 검사한다. 일반 Python 실행을 허용하거나 운영체제 수준의 완전한 보안 격리를 증명한 것은 아니다. 자식의 제한시간 종료와 VM 내부 크기 검사도 운영체제 메모리 quota와는 다르다.

## 5. 실제 결과

사용한 후보는 22I의 `96fb203da360bcc6ca2b876d25a5206986fcf1fc44281003ad6a039026003bee`다. 코드 hash `92418c389b6d2a178cbfffe978a84babd93b835ccb1cc3b29d4e551ca371b2a8`의 Luna 원문을 수정하지 않았다.

**제어한 검사 자료 7종:** 현재 입력과 거절 사건을 작성한 offline fixture다. 원본 후보 계산은 실제 별도 프로세스에서 수행했다. 새 물리 실패나 복구 성공이라고 보고하지 않는다.

| 시나리오 | 관측 결과 |
|---|---|
| Z=0, 유효한 입력 | `{x_mm:0, y_mm:0, z_mm:1, jaw_yaw_deg:0}` 제안, VM 123단계 |
| Z가 위쪽 경계 30 mm | 후보가 `None` 반환, VM 113단계 |
| 부품을 들고 있음 | 호스트 보류, VM 시작 안 함 |
| 호출 전 관측 번호 변경 | 오래된 관측 거부, VM 시작 안 함 |
| 남은 제안 횟수 0 | 호스트 보류, VM 시작 안 함 |
| 계산 도중 상태 변경 | 계산은 했으나 제안 폐기 |
| 상태 그대로 새 관측 번호 | 이전 거절과 연결하여 Z=1 mm 제안 |

**새 MuJoCo 장면 1종:** `build_frame_scene(10)`과 `FrameSkills`를 새로 구성하고 관측만 읽었다. 지지는 false, 양쪽 접촉 false, 선속도·각속도 0, 수직 내적 1, 패드 간격 약85.4 mm였다. `part_not_supported`로 보류했으며 VM을 시작하지 않았다. 원래 장면은 부품을 바닥 위에서 생성하므로 시간 진행 없이 지지되지 않는 것이 정상이다. 새 실제 거절 사건도 없었다. qpos/qvel/ctrl/act/time은 관측 전후 동일했다.

**이 1 mm 제안이 실제 삽입에 유효한지는 아직 확인하지 않았다.** 기존 후보의 잠정 상태와 교훈·코드는 수정하지 않고, 계산 결과를 별도의 실행 기록으로 연결했다. 후보 JSON의 생성 당시 `code_executed=False`는 과거 기록이며 이번 계산 여부는 새 기록의 `vm.execution_confirmed`와 결과를 따른다.

## 6. 검증과 재현 명령

- 새 VM 검사 12개: 실제 자식 프로세스, None·계산 오류·단계 한도·할당 차단, 별도 timeout/출력 한도/시작 실패 모의 검사, 환경·입력 보존.
- 새 호스트 검사 26개: 관측·조건·실패·예산·자료형·출력, 계산 전후 변경, unknown 설치 목록 거부. 실제 자식 2개 사례와 호스트 경계 모의 검사를 구분했다.
- 기존 후보 검사 34개 및 교훈 검사 35개 통과.
- 최종 probe 8/8 기대 결과 일치. 원래 자료 68개와 후보 원문 보존 확인.
- API 호출 0, 추가 API 비용 0. 로봇 명령·`mj_step`·새 조립 성공 판정 0.


