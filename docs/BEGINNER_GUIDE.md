# 처음부터 이해하는 UR 계열 조립 에이전트 프로젝트

이 문서는 1인·4주·약 10부품·실물 조립 시연이라는 목표를 처음 로봇을 배우는 관점에서 설명한다. 기어박스는 설명용 후보이며 아직 제품으로 확정되거나 동작이 검증되지 않았다. 설명 속 함수 이름은 역할을 나타내는 의사코드이며 설치된 SDK의 실제 API라고 가정하지 않는다.

개발 순서는 **MuJoCo 시뮬레이션 완성 → 실물 연결 → 실물 조립·평가**다. 처음에는 시뮬레이터가 알려주는 부품 상태를 사용하며 카메라 인식과 실물 통신은 뒤에 붙인다. 사용자는 새로 구축하는 상황이다. 선배들의 연구실 발표자료를 참고하되 재사용 코드는 아직 확보되지 않았다. 아래 실물 설명은 전체 구조를 이해하기 위한 것으로 첫날 모두 구현할 항목은 아니다.

장비 표기 주의: 아래 UR3는 초기 대화의 명칭이며, 연구실 발표자료에는 UR3e가 명시되어 있다. 실제 장비 기종을 확인한 뒤 모델을 확정한다. 두 기종을 같은 모델로 취급하지 않는다.

**만들 시스템은 ‘무엇을 할지 결정하는 부분’과 ‘그 동작을 실제로 수행하는 부분’이 연결된 구조다.**

사용자가 ‘이 부품들로 조립해’라고 입력하면 LLM이 부품의 선행 관계와 현재 상태를 보고 다음 작업을 정한다. 스킬 실행기는 그 작업을 이동·그리퍼·검사로 나눈다. 로봇 소프트웨어는 목표 자세, 관절 각도, 경로와 실행 시간을 계산하고 실제 제어기로 전달한다. 실행 결과는 다시 에이전트에 돌아온다.

LLM API와 LangGraph만 설치하면 로봇이 움직이는 것은 아니다. 로봇 모델, 좌표계, 파지 위치, 움직임 계획, 제어 연결, 결과 판정도 필요하다. 다만 이 기능의 알고리즘을 모두 직접 발명할 필요는 없다. 기존 소프트웨어를 설정·연결하고 조립에 필요한 동작을 구현하는 것이 핵심이다.

**기어 하나를 축에 끼우는 작업을 끝까지 따라가면 필요한 기술이 드러난다.**

1. 현재 조립 상태에서 그 축과 필요한 스페이서가 준비됐는지 확인한다.
2. 기어가 어디 있고 어떤 방향인지 확인한다.
3. 기어를 잡을 위치와 그리퍼 방향을 정한다.
4. 로봇이 그 자세를 만들 수 있는지 계산한다.
5. 작업대와 다른 부품을 피해서 접근하는 경로를 계산한다.
6. 속도·가속도 제한에 맞춰 경로에 시간을 붙인다.
7. 로봇이 경로를 따라 움직이고 그리퍼를 닫는다.
8. 실제로 기어를 잡았는지 확인한다.
9. 기어를 들고 축 위의 접근 위치까지 이동한다.
10. 정렬·삽입 동작을 수행한다.
11. 삽입 깊이와 자세, 놓은 뒤의 안정 상태를 확인한다.
12. 결과를 기록하고 다음 부품을 선택한다.

이 과정에서 순서 선택은 작업 계획, 3번은 파지 계획, 4번은 IK, 5번은 모션 플래닝, 6번은 궤적 생성, 7번은 제어, 10번은 접촉 조작, 8·11번은 검증에 해당한다. 실제 소프트웨어 안에서는 이 기능들이 반복 호출되므로 엄격한 일회성 직렬 순서인 것은 아니다.

**위치를 말하려면 기준 좌표계와 손의 방향이 먼저 필요하다.**

로봇에게 ‘기어 위로 가’라고 하려면 어디를 원점으로 삼는지 정해야 한다. 대표적으로 로봇 밑동, 카메라, 작업대, 부품에 각각 좌표계가 있다. 카메라가 측정한 위치는 카메라 기준이므로 로봇 밑동 기준으로 변환해야 이동에 사용할 수 있다.

Pose는 위치와 방향을 합친 말이다. 같은 지점에도 그리퍼를 위에서 내릴 수 있고 옆에서 접근할 수 있다. 이번 작업에서는 기어를 어느 방향으로 잡아야 구멍을 막지 않고 축에 넣을 수 있는지도 정해야 한다.

TCP는 로봇이 도구의 대표 위치로 사용하는 기준점이다. 로봇 손목 끝과 2F-85의 실제 파지 중심은 다르다. 이 차이를 모델과 제어기에 반영하지 않으면 손목은 목표에 도착했는데 손가락은 다른 곳에 위치할 수 있다. 그리퍼의 장착 방향·길이와 실제 TCP를 확인하는 작업이 먼저 필요하다.

처음에는 보정된 고정 치구와 정해진 트레이 위치로 시작한다. 이것은 위치를 알고 작업하는 조건이다. 나중에 RGB-D와 마커로 위치를 측정하면 카메라 내부 파라미터와 카메라-로봇 좌표 변환도 보정해야 한다. 카메라가 있다는 것만으로 정확한 부품 자세가 자동으로 얻어지지는 않는다.

**FK는 관절 각도에서 손의 자세를 계산하고, IK는 목표 자세에 맞는 관절 각도를 찾는다.**

FK(정기구학)는 각 관절이 현재 이만큼 돌아가 있을 때 그리퍼가 어디를 향하는지 계산한다. 로봇 링크의 길이와 연결 구조가 필요하다.

IK(역기구학)는 그리퍼를 이 위치와 방향에 놓으려면 각 관절을 얼마나 돌려야 하는지 계산한다. ‘손을 기어 위로 보내기’에 필요한 계산이다. 같은 손끝 자세를 만드는 관절 조합이 여러 개일 수 있고, 로봇 길이나 관절 제한 때문에 해가 없을 수도 있다.

IK가 계산됐다는 사실은 목표 자세를 만들 후보가 있다는 뜻이다. 현재 자세에서 그 후보까지 충돌 없이 이동할 수 있다는 뜻은 아니다. 팔을 거의 일자로 뻗은 자세처럼 특정 방향으로 움직이기 어려워지는 특이점도 고려해야 한다.

처음에는 기본 의미와 입력·출력을 이해하고 기존 solver를 사용한다. MoveIt은 IK 플러그인 구조를 제공한다. 직접 UR3의 역기구학 수식과 수치 solver를 새로 만드는 것을 4주 과제로 추가하지 않는다. [MoveIt 기구학 문서](https://moveit.picknik.ai/main/doc/concepts/kinematics.html)

**모션 플래닝은 현재 관절 상태에서 목표까지 갈 수 있는 경로를 찾는 일이다.**

목표 자세의 IK가 있어도 곧바로 모든 관절을 목표값으로 움직이면 팔꿈치가 작업대에 닿거나, 손에 든 기어가 다른 축을 칠 수 있다. 모션 플래너는 로봇 전체 형상, 관절 제한, 주변 물체와 경로 중간 상태를 검사한다.

그리퍼뿐 아니라 손에 든 부품도 충돌 형상에 포함해야 한다. 부품을 집으면 계획 장면에서 로봇에 부착된 물체로 관리하고, 배치하면 새로운 조립 위치의 물체로 관리한다. 실제 파지 성공을 확인한 뒤 그 상태를 반영한다. 10부품 조립 중에는 작업 환경이 계속 바뀌므로 처음의 빈 작업대 정보만 사용해서는 안 된다.

MuJoCo의 실제 파지 접촉과 모션 플래너의 ‘부착 물체’ 표현은 역할이 다르다. 후자는 손에 들린 물체를 포함해 충돌을 검사하기 위한 표현이다. 이것만으로 물리적 파지가 성공했다고 판정하지 않는다.

MoveIt은 OMPL 등의 경로 계획 기능과 충돌 검사, 자세·관절 제한을 연결한다. 우리 작업대·그리퍼·부품을 올바르게 등록하고 계획 결과를 검증하는 작업은 남는다. [MoveIt 모션 계획](https://moveit.picknik.ai/main/doc/concepts/motion_planning.html), [Planning Scene](https://moveit.picknik.ai/main/doc/examples/planning_scene/planning_scene_tutorial.html)

**경로에 실행 시간을 붙인 것이 궤적이고, 그 궤적을 따라 움직이는 것이 제어다.**

경로는 어느 자세를 거쳐 갈지 나타낸다. 궤적은 각 자세에 언제 도달할지까지 정한다. 같은 경로라도 매우 빠르게 움직이는 것과 천천히 움직이는 것은 다르므로 속도와 가속도 제한을 반영한다. [MoveIt 궤적 처리](https://moveit.picknik.ai/main/doc/concepts/trajectory_processing.html)

실제 로봇 제어기는 목표와 실제 관절 상태의 차이를 계속 줄이며 움직인다. 실제 UR3의 모터 제어기를 새로 만드는 작업은 하지 않는다. 기존 드라이버와 컨트롤러에 실행 가능한 명령을 전달하고 완료·오류·중단 상태를 확인한다. MuJoCo에서는 대응되는 구동기와 제어 루프를 구성해야 한다.

LLM은 동작 선택이나 복구 판단이 필요할 때 호출한다. 모터를 움직이는 빠른 반복 제어는 로봇 제어 코드와 하드웨어가 맡는다. API 응답을 기다리며 매 순간 관절을 조절하는 방식으로 만들지 않는다.

**삽입은 자유 공간 이동에 더해 접촉 상태를 다루는 작업이다.**

부품을 축 위로 옮기는 경로가 성공해도 구멍 중심 오차, 프린팅 공차, 치형 위상, 마찰 때문에 실제 삽입은 실패할 수 있다. 따라서 MoveIt에서 경로가 나왔다고 삽입 성공으로 판정하면 안 된다.

초기에는 유도면·공차·지그와 제한된 삽입 동작을 설계하고, 성공을 실제 깊이·높이·자세로 확인한다. 그립을 놓은 뒤의 안정성도 본다. 정밀 힘 제어와 고급 접촉 탐색을 처음부터 모두 개발하는 범위로 넓히지 않는다. 실제 장비의 힘 측정과 제어 가능 여부는 별도 확인 사항이다.

삽입에는 의도된 부품 접촉이 있다. 이를 처리하기 위해 모든 충돌 검사를 꺼서는 안 된다. 단계별로 어떤 부품 사이의 접촉이 허용되는지 정하고, 다른 물체와의 충돌은 계속 검사해야 한다. 계획 장면의 접촉 허용은 마찰이나 접촉력을 해결하는 기능이 아니다.

**스킬은 이 여러 단계를 이름 하나로 묶은 실행 코드다.**

예를 들어 `pick(gear_a)`는 단순히 그리퍼를 닫는 함수가 아니다. 파지 위치 계산, 접근 경로, 접근, 닫기, 잡힘 확인, 들어올리기, 결과 반환을 포함한다. `insert(gear_a, shaft_a)`에는 목표 변환, 정렬, 제한된 삽입, 결과 판정이 들어간다.

처음 만들 기본 스킬은 pick, place, align, insert, retreat 정도다. 이동과 파지 방법은 공통으로 사용하고 물체의 ID, 목표, 파지 형상, 허용 범위를 파라미터로 전달한다. 각 스킬은 성공 또는 구체적인 실패 코드와 관측 근거를 반환한다.

전체 조립이 10부품이라고 10종류의 새로운 로봇 알고리즘이 필요한 것은 아니다. 공통 스킬을 여러 부품에 적용하되, 각 부품의 파지와 결합 조건이 정말 호환되는지 확인하는 것이 필요하다.

**LLM과 LangGraph는 실행 가능한 스킬 위에서 작업을 결정하고 관리한다.**

LLM이 받는 것은 현재 부품 상태, 목표 결합 관계, 사용할 수 있는 스킬과 관련 경험이다. 내보내는 것은 구조화된 계획이다. 코드가 계획의 ID·범위·선행 조건을 검사한 뒤 실행한다.

LangGraph는 관측, 경험 검색, 계획, 검증, 실행, 결과 확인, 재계획, 종료를 연결한다. 한 노드는 LLM 호출일 수 있고 다른 노드는 일반 Python 코드일 수 있다. 노드가 많다는 이유만으로 멀티에이전트가 되는 것은 아니다.

부품별 상태를 기록하면 중간 실패 이후 이미 확인된 조립을 보존하고 남은 단계만 계획할 수 있다. 목표 결합·선행 제약을 직접 제공했다면 에이전트가 그 제약까지 스스로 발견했다고 주장하지 않는다. 같은 작업을 항상 같은 순서로만 수행하면 규칙 기반 코드로도 해결 가능하므로, 부분 조립 상태·부품 배치·실패 조건의 변화에서 에이전트의 역할을 평가한다.

**메모리는 검증된 경험을 다음 계획에서 다시 읽는 기능이다.**

현재 작업의 몇 번째 단계인지, 무엇이 조립됐는지는 작업 상태다. 이전 작업의 성공 절차·적용 조건·실패 결과는 장기 경험이다. 실행 가능한 기본 스킬 코드는 별도로 관리한다.

처음에는 SQLite에 부품군, 결합 유형, 조건, 스킬 순서, 제한된 파라미터, 성공·실패 결과를 저장하면 된다. 다음 작업에서 조건이 맞는 경험 몇 개만 가져온다. 기구·좌표 보정이 바뀌면 과거 좌표나 보정값을 그대로 쓰지 않는다.

예를 들어 한 종류의 스페이서를 해당 축에 먼저 끼운 부분 절차가 검증됐다면 비슷한 작업에 참고할 수 있다. 다른 부품의 실패를 관측했다고 로봇이 새로운 모터 제어법까지 자동 학습하는 것은 아니다. 4주 버전의 축적 대상은 검증된 스킬의 조합과 적용 조건이다.

**각 소프트웨어가 해결하는 문제가 다르다.**

| 이름 | 역할 | 우리가 해야 하는 연결 |
|---|---|---|
| LLM API | 작업 계획·복구안 생성 | 입력 요약, 출력 스키마, 사용량 기록 |
| LangGraph | 작업 흐름과 상태 관리 | 노드, 분기, 재시도, 종료 조건 |
| 기존 IK·경로 기능 | 목표 자세와 이동 경로 계산 | 첫 MuJoCo 버전에 맞는 solver 연결, waypoint와 충돌 검사 |
| MoveIt 2 | 로봇 모션 계획, IK 연동, 충돌 검사 | 이후 도입 후보, 첫 MuJoCo 실행의 필수 설치는 아님 |
| ROS 2 | 로봇 프로그램 사이의 통신 기반 | 이후 제어 경로에 따라 도입, 상태·명령·실행 결과 연결 |
| UR 드라이버·컨트롤러 | 실제 UR3와 통신하고 궤적 실행 | 실제 기종·보정·네트워크 설정 |
| 그리퍼 인터페이스 | 2F-85 열기·닫기·상태 읽기 | 실제 연결 방식에 맞춘 제어 |
| MuJoCo | 물리적인 움직임·접촉·중력을 계산 | 모델, 구동기, 제어 입력, 결과 판정 |
| SQLite | 실행 경험 저장·검색 | 어떤 경험을 저장하고 사용할지 정의 |

UR의 공식 구성은 로봇만 있는 설정에서 시작하므로 실제 그리퍼·작업대 정보를 반영해야 한다. [UR 드라이버 구성](https://docs.universal-robots.com/Universal_Robots_ROS2_Documentation/doc/ur_robot_driver/ur_robot_driver/doc/overview.html)

**첫 MuJoCo 버전은 Python 중심으로 만들고, MoveIt 도입 시 연결 작업을 추가한다.**

MuJoCo는 물리 엔진이므로 설치만 하면 우리 작업의 IK·파지·경로 계획·실물 제어가 전부 만들어지는 것은 아니다. [MuJoCo 개요](https://mujoco.readthedocs.io/en/stable/overview.html)

가능하면 하나의 모션 계획 기능이 만든 관절 궤적을 공통 형식으로 받고, 시뮬레이션 adapter는 이를 MuJoCo 구동기에, 실물 adapter는 UR 제어 경로에 전달하게 한다. 두 경로에서 관절 이름·순서·단위·TCP·좌표계를 맞춰야 한다. 실행 후 실제 관측이 달라지면 과거 궤적을 무조건 재생하지 않고 다시 계획한다.

첫 버전은 기존 IK 구현과 고정 작업대의 제한된 waypoint 경로로 시작할 수 있다. 이동 경로의 충돌·관절 한계는 검사하되 임의 장애물 우회까지 지원한다고 표현하지 않는다. 사용할 IK 구현은 UR3 모델과 현재 개발 환경에서 동작을 확인한 뒤 정한다.

이후 MoveIt을 도입하면 관절 상태와 궤적을 주고받는 bridge가 필요할 수 있으며, MoveIt과 MuJoCo를 각각 설치했다고 자동 연결되는 것은 아니다. 연구실의 IK·경로·통신 코드가 확보되면 재사용 범위를 확인한다. 같은 스킬 이름을 써도 실제 좌표 보정과 접촉 동작 검증은 필요하다.

URDF는 로봇의 링크·관절·형상을 기술하는 파일이고, MJCF는 MuJoCo 모델을 표현하는 형식이다. 모델 파일은 제어 프로그램 자체가 아니다. 그리퍼 결합, 구동기, 충돌 형상, 관측·제어 루프도 설정해야 한다. RViz 같은 시각화에서 로봇이 움직여 보이는 것과 실제 접촉 물리가 검증된 것도 구분한다.

**두 루프의 역할을 각각 확인한다.**

시뮬레이션 루프는 계획 → 가상 실행 → 실패 검사 → 계획 수정이다. 실제 작업 조건을 반영하고 동일 계획·스킬·장면 버전의 검증 결과를 기록한다.

실물 피드백 루프는 실제 상태 확인 → 실물 실행 → 실제 결과와 예상 결과 비교 → 원인 확인·허용 범위의 수정 → 재시뮬레이션이다. 단순히 sim과 real을 한 번씩 실행하는 것만으로 피드백 루프가 완성되는 것은 아니다.

실물의 불확실한 접촉 실패를 LLM이 임의로 반복하게 하지 않는다. 확인된 복구 동작이 있는 경우만 재계획·재검증 뒤 실행하고 나머지는 중단·개입 필요로 기록한다. 시뮬레이션 성공과 실물 성공을 따로 집계한다.

**직접 작성할 부분과 재사용할 부분을 나누면 첫 개발 범위가 보인다.**

| 구분 | 내용 |
|---|---|
| 기존 기능 재사용 | 로봇 FK/IK solver, 기본 경로 탐색, 실제 UR 모터 제어, 물리 엔진 |
| 설정·보정·연결 | 로봇/그리퍼 모델, TCP, 작업대·카메라 좌표, 충돌 장면, 궤적 연결 |
| 직접 구현 | 조립 스킬, 전제·후조건, 에이전트 그래프, 계획 검증, 메모리, 평가 |
| 직접 설계·제작 | 조립체, 파지 구간, 유도면, 중간 지지 지그, 시험편 |

초보자 기준에서 가장 시간이 걸릴 가능성이 큰 것은 장비 연결, 좌표·TCP, 파지와 삽입의 안정화다. 라이브러리 사용법을 배우는 시간도 필요하다. 4주·10부품 계획은 기존 제어 자산과 장비 접근을 확보했을 때의 조건부 목표이며, 모든 기능을 처음부터 작성하는 일정이 아니다.

**학습과 구현은 작은 결과를 확인하는 순서로 진행한다.**

1. MuJoCo에서 UR3·2F-85·작업대를 띄우고 관절·그리퍼를 제어한다. 로봇 관절·좌표계·Pose·TCP의 의미를 함께 익힌다.
2. 기존 FK/IK 기능과 제한된 경로 검사를 연결하고 목표 자세까지 이동시킨다.
3. 스크립트로 한 부품을 실제 시뮬레이션 접촉으로 집고 놓고 삽입한다. 파지·삽입의 결과 판정을 구현한다.
4. 같은 스킬을 3→6→약 10부품 조립으로 확대하며 선행 조건과 중간 상태를 관리한다.
5. 이 스킬 위에 LangGraph의 단일 LLM을 연결한다. 계획 검증, 실패 보고와 제한된 재계획을 구현한다.
6. 성공·실패·API 사용량을 저장하고 다음 실행에서 관련 경험을 검색한다. 여기까지가 첫 시뮬레이션 완성 범위다.
7. 완료 기준을 통과한 뒤 실제 UR3·그리퍼 연결, 부품 출력, TCP·좌표 보정, 집기와 가장 어려운 결합의 실물 검증을 진행한다.
8. 전체 실물 조립으로 확장하고 실제 관측을 반영한 재시뮬레이션, 경험 재사용, 반복 평가를 진행한다.

첫 7–10일을 시뮬레이션 v1 완성의 목표로 제안한다. 고정 조건에서 약 10부품 전체 조립을 반복 실행하고, 단계별 성공 판정·실패 처리·경험 저장과 검색이 연결돼야 한다. 물체 순간이동이나 비물리적 부착으로 만든 시연은 물리 조립 성공으로 세지 않는다. 자세한 통과 기준은 [프로젝트 계획](PROJECT_PLAN.md)에 둔다.

이후 둘째 주 남은 기간부터 실물을 연결하고 셋째 주는 전체 실물 조립, 넷째 주는 평가와 시연 준비를 목표로 한다. 이는 모델·접촉 구현이 순조롭게 진행될 때의 일정 배분이다. 시뮬레이션 지연이 생기면 7일차·10일차에 남은 일정을 재검토하고, 실물 첫 실행에서 생긴 차이는 MuJoCo 모델·스킬에 다시 반영한다.

최종 시연에서 보여줄 것은 입력 명령, 계획과 선택 이유의 짧은 요약, 시뮬레이션 통과 여부, 실제 조립, 단계별 확인 결과, 사용한 경험과 비용이다. 기어박스를 선택하면 단순 배치와 조립 깊이 충족, 기어 회전 기능도 구분한다. 일부 부품 성공을 전체 10부품 성공으로 보고하지 않는다.
