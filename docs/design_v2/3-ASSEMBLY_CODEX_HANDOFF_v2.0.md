## 0. 가장 먼저 읽을 결정과 이전 문서 대체

### 0.1 사용자가 확정한 목표

**완성 CAD/부품별 목표 배치를 입력하면 고정 Python 코드가 실제 형상과 초기 배치를 준비하고, Astra가 잡을 부위·방향을 선택하거나 수정한다. Python과 MuJoCo가 접근·닫기·들기·운반·설치·해제·안정성을 실제로 시험하고, 실패 근거를 돌려주어 제한된 재시도와 경험 재사용을 수행한다. 사용자는 제품마다 좌표나 부품 관계 코드를 작성하지 않는다.**

기둥·슬리브·덮개라는 이름이나 사각 형상 분류를 통과해야만 시험할 수 있는 시스템으로 완성하지 않는다. 형상 이름 대신 유효한 입력, 실제 로봇·그리퍼, 충돌 형상, 접촉과 동작 검증을 기준으로 처리한다. 원통·곡면·오목한 케이스·비대칭 부품도 같은 공통 처리 경로에 들어가야 한다.

이 목표는 모든 입력의 물리적 성공을 보장한다는 뜻이 아니다. 실제 도달 실패·충돌·파지 실패·목표 경로 미발견·불안정·모델링 불충분·예산 소진을 측정 근거와 함께 반환할 수 있어야 한다. 단지 사각 부품이 아니라는 이유로 시험 전에 배제하는 기존 구현은 수정 대상이다.

### 0.2 우선순위와 명시적으로 철회하는 제한

이 v2.0과 동봉한 완료 프로파일 v1.2가 이번 구현의 최신 요구다. 기존 `ASSEMBLY_MASTER_DESIGN_v1.2.md`, `ASSEMBLY_CODEX_HANDOFF_v1.2.md`, `ASSEMBLY_FINAL_FIX_PLAN_cfe6c88_20261124.md`, 완료 프로파일 v1.0/v1.1의 충돌하는 지시를 아래와 같이 대체한다. 기존 문서를 무조건 모두 유지하라는 의미가 아니다.

단위·실제 상태·원 CAD 목표·물리 검증·시간/비용 제한·증거 보존은 계속 지킨다. 기존 F01–F16은 §10에서 새 경로에 맞게 유지한다. 전용 함수를 교체할 수 있으나 발견된 오류의 의미와 회귀 확인을 생략하지 않는다.

## 1. 최종 동작과 책임 분담

1. 사용자가 STEP/STP 또는 필요한 정보를 포함한 OBJ/검증 분해 패키지를 선택한다.
2. Python이 부품 인스턴스·단위·실제 메시·완성 pose·분해 순서/경로 근거를 준비한다.
3. Python이 충돌 자산·물성 가정·공통 기준 좌표를 생성하고 별도 완성 기준 장면을 검사한다.
4. Python이 초기 자세·배치를 자동 생성하고 로봇 도달·충돌·중력 정착을 확인한다.
5. Python이 현재 부품의 메시에서 파지 후보와 근거를 만들고 Astra에 제공한다.
6. Astra가 후보를 선택하거나 위치·방향을 수정/직접 제안한다.
7. Python이 후보의 기하·IK·접근·물리 집기를 검사하고 운반·설치 가능성도 별도로 확인한다.
8. 통과한 계획을 주 장면에서 실행하고 해제·후퇴·연속 최종 검증을 수행한다.
9. 실패하면 실제 단계·관련 부품·측정값을 반환하여 허용 예산 안에서 대응한다.
10. 원래 설치 문제의 해결이 검증된 사건에서 해결지침을 만들고, 다음 실행에서 조건 필터와 이미지 임베딩으로 검색한다.
11. UI에서 진행·최종 결과·영상·실패 근거·비용·경험 등록/검색 결과를 확인한다.

| 구성 요소 | 책임 |
|---|---|
| 고정 Python 전처리 | CAD/메시·좌표·기하·충돌 자산·초기 배치·후보 계산 |
| Astra | 현재 부품의 허용 행동과 파지 후보 선택/수정, 실패 해석과 짧은 해결지침 |
| Python 실행기 | IK·경로·그리퍼·실제 상태 기반 동작·재시도 상태 전이 |
| MuJoCo와 검증기 | 접촉·들림·슬립·충돌·관통·목표 오차·속도·해제 후 안정성 측정 |
| 경험 저장/검색 | 객관적 사건과 검증된 해결지침 보존, 조건 필터 후 이미지 유사도 순위 |

Astra가 성공을 선언하거나 임의 Python 코드를 생성해 실행하지 않는다. Python 후보 생성은 기하 보조이며 연구 모드에서 Astra 대신 최종 후보를 조용히 선택하지 않는다.

단일 에이전트와 순차 assembly/recovery 역할 비교는 기존 구조를 유지한다. 동일 Astra 모델/설정, 동일 후보 생성·물리 검증·입력·예산을 사용하며 공유 대화 이력을 보존한다. scripted는 개발 검증용 출처로 구분한다.

## 3. 입력·분해 프로젝트 연결·좌표 계약

### 3.1 제품별 수동 설정 없는 입력

- STEP/STP의 부품 인스턴스·배치·단위를 보존한다. 같은 형상의 반복 인스턴스를 하나의 부품으로 합치지 않는다.
- OBJ는 부품 구분·완성 배치가 남아 있는 파일/묶음과 단위 근거를 사용한다. OBJ에 없는 단위를 파일명이나 겉보기 크기로 몰래 추측하지 않는다. 기존 공통 단위 정책을 사용하는 경우 해석 근거를 기록한다.
- 단위·목표·부품 구분이 실제로 부족하면 `input_incomplete`와 필요한 정보를 명시한다. 제품별 좌표표/관계 registry 작성이 정상 사용 절차가 되어서는 안 된다.
- 공통 환경(API·모델·브리지 실행 경로·로봇/TCP·기본 물성·예산)은 최초 한 번 설정한다. 매 입력마다 사용자가 조립 의미를 손으로 코딩하게 하지 않는다.
- 원본 메시, 정규화된 부품 로컬 메시, 시각 자산, 충돌 자산과 각각의 hash/변환을 구분해 보존한다.

### 3.2 분해 결과와 경로

검증 분해 export가 있으면 기존 version/hash/단위 검증을 유지해 재사용한다. raw CAD만 입력하면 이미 연결한 공통 분해 브리지를 자동 호출한다. 다른 분해 저장소를 임의로 수정하거나 검증되지 않은 순서를 검증 완료로 포장하지 않는다. 인터페이스 어댑터는 조립 측에서 호환성을 명시한다.

검증된 역순은 설치 순서 후보이며 Python이 현재 부품을 지정하는 기존 정책을 유지한다. Astra가 별도의 순서 탐색 정책을 새로 맡도록 바꾸지 않는다.

분해 궤적이 있으면 각 부품의 SE(3) waypoint/시간, 시작·끝 pose, source frame/unit, 원본 경로 hash, 검증 증거와 상태를 prepared까지 보존한다. 요약 check ID만 남기고 경로를 잃지 않는다. 다른 조립 자세/분해 분기가 섞이지 않게 상태와 목표를 대조한다.

검증된 설치 순서를 확보하지 못하면 준비 미완료로 보고한다. 유효한 부품 역경로가 없거나 선택한 파지로 로봇이 따르지 못하면 그 사실을 기록하고, 검증된 순서와 CAD 목표 pose를 이용해 허용된 계획기로 운반·접근 경로를 생성하고 검증한다. 이 계획도 예산 안에서 확보하지 못하면 계획 실패다. 경로가 없다는 사실만으로 물리적 조립 불가능이라고 단정하지 않는다. 단, 입력 export 스키마가 필수로 요구하는 경로 증거가 누락/변조된 경우에는 그 입력 검증을 우회하지 않는다.

베이스와 고정 조건은 검증 분해 export에 있으면 우선 준수한다. raw CAD에 없으면 Python이 형상 이름에 의존하지 않는 기하·지지/안정성·분해 검증으로 제한된 베이스 후보를 자동 선택한다. 선택 근거와 공통 고정 fixture 가정을 기록하며 CAD가 고정을 명시한 것으로 꾸미지 않는다. 적합한 후보를 정하지 못하면 준비 실패와 근거를 보고한다. 제품별 수동 base/관계표 작성을 정상 사용 절차로 요구하지 않는다.

### 3.3 공통 변환

- `T_W_P`: 부품 로컬 좌표에서 작업장 world로 가는 변환.
- `T_P_TCP`: 부품 좌표계에서 표현한 TCP의 자세. 이 행렬은 TCP 좌표의 점을 부품 좌표로 옮기며, `T_W_TCP = T_W_P × T_P_TCP`를 사용한다.
- 내부 물리 단위는 m/rad. 모델용 위치는 기존 mm 규약을 유지하고 회전은 명시한 xyzw quaternion으로 통일할 수 있다. 엔진 wxyz 변환은 경계에서 처리한다.
- 목표 pose는 원 CAD에서 가져와 같은 공통 배치 변환만 적용한다. 실제 초기 자세·현재 자세와 별도로 저장한다.
- CAD 원점·body 원점·COM·bbox 중심의 변환을 명시한다. 중간에 recenter하면 mesh와 모든 pose/경로를 함께 변환한다.
- 작업장 배치를 위해 전체 CAD를 공통 회전/평행이동할 수 있지만, 부품 간 상대 목표 배치를 변경하지 않는다.

## 4. 일반 메시의 물리 장면과 자동 초기 배치

### 4.1 충돌 자산

유효한 강체 메시를 공통 처리한다. 곡면·오목함·기울어진 면이라는 이유로 사각 종류 검사에서 배제하지 않는다. 잘못된 면·열린 경계·자기 교차·체적/관성 계산 실패 등은 실제 진단으로 분리하고, 수행한 보정과 원본을 보존한다.

볼록한 부품에는 적절한 볼록 충돌 자산을 사용한다. 오목한 케이스·구멍·홈에는 자동 볼록 분해 등의 일반 방법을 구현한다. CoACD 등 기존 도구를 활용할 수 있으며 실행 환경과 재배포 조건을 확인한다. 새 파지 학습 모델 도입이나 학습을 필수 선행 과제로 만들지 않는다.

단일 bbox/convex hull은 빠른 범위 검사에 사용할 수 있으나, 구멍을 막아 버리는 최종 충돌 자산으로 대체하지 않는다. 시각 메시만 정확하고 실제 충돌은 잘못된 상태도 완료로 인정하지 않는다.

최소 품질 진단은 양방향 표면 편차, 체적/질량 일관성, 중요한 구멍·통로의 통과 여부, 목표 배치와 보존한 경로에서의 간섭이다. 체적 하나만 맞는 것으로 구멍 보존을 증명하지 않는다. 설치 간극과 관통 한도에 비해 충돌 근사가 거칠면 재분해하거나 `collision_geometry_invalid`로 보고한다. 검증되지 않은 근사를 성공 판정에 사용하지 않는다.

분해 도구·버전·파라미터·seed·품질 결과·자산 hash를 저장하고 캐시한다. 분해된 여러 geom은 한 강체 body에 붙이며, 겹치는 조각의 질량을 단순 합산해 관성을 왜곡하지 않는다. 가능한 원본 형상과 선언한 질량/밀도에서 질량·COM·관성을 계산한다. 누락 물성은 공통 시뮬레이션 가정임을 표시한다.

### 4.2 별도 완성 기준 장면

원 CAD 목표로 별도 상태를 만들고 완료 프로파일 v1.2의 정착/관찰 검사를 한다. 실제 고정 베이스 외 부품을 성공을 위해 weld/servo/mocap으로 고정하지 않는다. 목표 렌더링은 물리 검사를 대신하지 않는다.

완성 상태가 불안정하면 `reference_invalid`와 관측 근거를 남긴다. 모델링되지 않은 체결이나 추가 지지가 필요한 경우를 기하 입력 오류와 구분한다. 기준 장면을 주 장면으로 복사해 완성시키거나 정착 pose로 목표를 바꾸지 않는다.

### 4.3 초기 자세·배치·부품 수

메시의 지지면·질량중심에서 초기 자세 후보를 만들고 필요하면 짧은 물리 정착으로 확인한다. 원통이 굴러가는 등 실제 초기 상태의 불안정을 검사한다. 모든 부품 초기 회전을 identity로 가정하지 않는다.

초기 배치의 물리 정착이 끝나면 실제 pose를 미설치 부품의 보존 기준으로 한 번 확정하고 run 동안 고정한다. 원 CAD 목표와 구분하며 실행 중 이동을 숨기려고 재설정하지 않는다. 의도한 초기 정착 이동을 옛 초기값 대비1mm 이탈로 오판하지 않게 한다.

전체 완성 조립체 영역과 로봇 영역을 예약하고, 부품 간·그리퍼 접근 간격을 둔 격자/선반식 배치 후보를 결정적으로 생성한다. 작업대 XY를 자동 확장할 수 있지만 로봇 도달 범위는 별도 검사한다. 기하 배치 가능·정착 가능·로봇 접근 가능을 서로 다른 상태로 기록한다.

기존 `max_parts=10`을 제품 종류의 한도로 유지하지 않는다. N에 맞춰 body/registry/상태/영상/문맥을 생성한다. 대신 부품·geom 수, 메시 분해 비용, 준비 시간, 메모리, 동작/모델 예산에 실제 설정된 자원 한도를 적용한다. 한도 초과를 형상 미지원 또는 물리적 불가능으로 설명하지 않는다. 11개 이상에서 고정 배열/상한이 남지 않았는지 확인한다.

배치가 실패하면 설정된 후보/시간 예산 안에서 다시 배치한다. 예산 소진은 `layout_search_exhausted`와 시도 내역으로 보고한다. 실행 중 부품을 순간이동시켜 재공급하거나 로봇 도달을 가짜로 늘리지 않는다.

## 5. 파지 후보와 Astra 입력·출력

### 5.1 기본 구현: Python 기하 후보 + Astra 선택/수정

고정 Python이 실제 메시의 표면점·법선·마주 보는 접촉면·간격과 그리퍼 패드/개폐 형상에서 후보를 생성한다. 닫힘축에 대한 접근 방향·회전을 탐색해 위·옆·경사 후보를 포함한다. 접촉 쌍이 있다는 사실만으로 물리 파지 성공을 선언하지 않는다.

후보를 가용 폭, 손가락/손바닥의 접근·개폐 스윕, 주변 부품, 로봇 IK/관절 한계 등으로 검사한다. 계산량은 설정된 수량/시간으로 제한하고 후보 생성/기하 거절과 실제 물리 시험 횟수를 구분한다.

Astra는 후보 ID를 고르거나, 전체 pose를 제출하여 후보를 수정/직접 제안할 수 있다. Python이 생성한 좌표를 Astra가 직접 생성한 것으로 기록하지 않는다. 후보가 없으면 제한된 재생성이나 Astra 직접 제안 경로를 허용하고, 예산이 소진되면 탐색 실패로 보고한다. 후보 생성기의 누락을 모든 파지의 불가능 증명으로 해석하지 않는다.

### 5.2 후보 데이터

각 후보에 다음을 기록한다.

- `candidate_id`, `part_id`, 원본/충돌 mesh hash, scene revision, 대상 pose hash.
- 부품 좌표계의 TCP 위치·회전, 접근축/사전 접근 pose, 명령 개방 폭과 폐쇄 설정.
- 표면 접촉점/법선·패드 여유·후보 생성 근거와 통과/미검사 항목.
- `generator_version`, 후보 순위/seed, 출처 `python_geometry` 또는 `astra_pose`.

TCP는 패드 접촉점이 아니므로 부품 bbox 바깥일 수 있다. 기존 bbox 안 TCP 조건을 일반 파지의 성공/거절 기준으로 쓰지 않는다. 비정상적으로 먼 pose·NaN·잘못된 회전 등은 작업장/거리/형상 근거로 거절한다.

### 5.3 모델 입력

최초 목표 상면·대각선 이미지 두 장, 부품 ID와 기본 기하, 로봇/그리퍼 규약, 목표 정보를 유지한다. 실제 메시 전체나 점군 수치를 매 호출 텍스트로 보내지 않는다.

매 판단에는 현재 부품/목표, 현재 pose와 revision, 파지/설치 상태, 후보 요약, 최근 시도, 필요한 실패 측정값, 검색된 짧은 해결지침, 허용 행동과 남은 예산을 보낸다. 전체 후보 풀이 크면 기하적으로 다양한 제한된 목록을 제공하고 제외 기준을 기록한다.

후보 그림은 UI/진단 자료로 생성할 수 있으나 매 호출의 이미지 추가를 기본화하지 않는다. 실패 이미지는 검색·증거용으로 보존하고 기존 정책대로 임베딩 비교에 사용한다. 대화 문맥은 애플리케이션이 유지한다.

### 5.4 출력 계약 예시

다음은 구현할 계약 예시이며 현재 코드가 이미 이 스키마를 읽는다는 뜻은 아니다. 실제 SDK/기존 도구 구조에 맞춰 한 번 버전 변경하고 소비자를 함께 수정한다.

```json
{
  "skill": "pick",
  "part_id": "part_07",
  "target_id": "cad_goal:part_07",
  "observation_revision": 12,
  "grasp": {
    "mode": "candidate",
    "candidate_id": "part_07:r12:g03"
  },
  "reason": "이 후보는 확인된 접촉면 간격을 만족하고 목표 주변의 손가락 간섭을 피할 수 있는 후보입니다."
}
```

직접 제안/수정은 `mode=pose`, `frame=part_local`, `position_mm[3]`, `quaternion_xyzw[4]`, 실제 그리퍼 범위 안의 `opening_width_mm`로 표현한다. 수정한 후보의 원 ID도 기록한다. 위치와 방향은 완전한 pose로 해석하며 의미가 불명확한 Euler 델타를 섞지 않는다. 값의 유한성·quaternion·단위·part/goal/revision과 현재 상태를 먼저 검사한다.

직접 pose도 Python 후보와 동일한 기하·IK·물리 검사를 거친다. 후보 ID를 참조하면 서버가 저장한 pose/hash를 사용한다. 오래된 후보를 새 관측에 그대로 적용하지 않는다.

### 5.5 Astra 프롬프트의 필수 의미

프롬프트는 현재 관측으로부터 허용 행동 하나를 반환하도록 한다. 짧은 이유는 관측 근거와 선택 목적만 설명하며 장문의 사고 과정 출력을 요구하지 않는다. 측정하지 않은 접촉·성공·해결 원인을 지어내지 않는다.

예시의 의미는 다음처럼 고정한다.

- **접근 거절:** 손가락이 주변 부품과 충돌한 copy 후보이면 다른 방향/위치 후보를 선택. 주 장면에서 이미 부품을 집었다고 쓰지 않음.
- **집기 통과·설치 실패:** 들기는 성공했으나 설치 중 손바닥이 케이스에 막히면 설치 공간을 남기는 다른 파지를 검토. 이를 파지 미끄러짐으로 해석하지 않음.
- **실제 낙하/상태 변경:** 최신 관측과 허용 행동을 확인. 초기 위치로 되돌아갔다고 가정하거나 동일 후보를 오래된 revision으로 실행하지 않음.

기존 실행 프롬프트와 해결지침 생성 프롬프트에 이 예시를 짧게 반영하고, 특정 부품 ID·사각 종류를 정답으로 암기시키지 않는다.

## 6. 파지 시험·실제 실행·복구

### 6.1 분리된 검사 결과

`check_grasp`에 해당하는 공통 검사 흐름을 다음으로 나눈다.

1. **후보 계약/기하/도달:** 좌표·회전·그리퍼 폭·접근 및 로봇 충돌.
2. **물리 파지:** pregrasp 접근→집게 닫기→패드 접촉→실제 들림→슬립/낙하 검사.
3. **이 파지의 설치 가능성:** 운반→목표 접근→해제→빈 그리퍼 후퇴의 계획/필요한 물리 사전검사.

결과는 `grasp_feasible`, `installation_feasible_with_grasp`를 별도로 가지며 `passed/failed/not_run`과 근거를 기록한다. 후보 거절을 false 하나로 합쳐 원인을 지우지 않는다. 실제 검사 전에는 통과로 표시하지 않는다.

사전검사는 독립 copy에서 수행할 수 있다. copy의 부품 이동·시간·영상은 주 장면 실행과 분리한다. 주 장면의 성공은 주 장면에서 실제로 수행한 동작과 검증으로만 인정한다.

### 6.2 물리 실행과 상태 보존

실제 부품은 접촉·마찰로 잡고 운반한다. 계획용 복사 장면의 기하 검사에서 상대변환을 고정하는 것과 주 장면에서 부품을 weld/teleport하는 것을 구분한다. 주 장면의 물리 실패를 지우기 위한 순간이동/강제 고정은 금지한다.

현재 파지의 관측 상대변환은 다음 계획에 사용하고, 최초 파지 상대변환은 슬립 감시 기준으로 따로 보존한다. 작은 슬립을 계속 재기준화해 큰 누적 슬립을 숨기지 않는다.

copy 거절 후에는 주 장면이 그대로인지 확인하고 다음 후보를 검토한다. 주 실행 실패 후에는 실제 pose·그리퍼·접촉·안정 상태를 새로 관측한다. 부품이 안정적으로 놓여 있고 기존 허용 동작으로 접근 가능한 경우에만 새 pick을 진행한다. 손에 든 부품을 내려놓고 다시 잡는 별도 전략을 구현하지 않았으면 구현된 것처럼 호출하지 않는다.

### 6.3 예산과 재시도

기존 부품당 최초 포함 파지 후보 최대 3회, run별 정렬 복구/운반 재계획 각 1회 등 승인된 예산을 유지한다. 후보 선택→pose 직접 제안→역할 전환으로 누적 예산을 초기화하지 않는다. 내부 표면 샘플링 개수와 Astra가 제출해 시험한 후보 수를 구분한다.

제어 생성 상한 `4N+4`에서 N은 설치 대상 비고정 부품 수로 명시하고 기존 전역 요청·토큰·비용 상한도 함께 적용한다. 새 일반화 작업을 이유로 무제한 API나 무한 경로 탐색을 도입하지 않는다. 실제 동작에 필요한 범위와 예산 정의가 충돌하면 이를 명시하고 결과를 성공으로 조작하지 않는다.

실패는 현재 시도/예산 안의 결과다. IK 한 후보 실패나 경로 탐색 시간 만료를 모든 파지/조립의 불가능으로 단정하지 않는다.

## 7. 목표 pose 기반 운반·설치와 접촉

### 7.1 검증 분해 경로의 재사용

분해 부품 경로의 역방향은 설치 접근 후보로 사용한다. 이것은 로봇 관절 궤적이 아니다. 선택한 파지에서 UR3e·그리퍼·잡힌 부품의 IK·관절 한계·연속 경로 충돌·접촉을 다시 검사한다.

초기 집기 위치에서 역경로 시작점까지 별도 운반 경로를 계획한다. 원 경로가 현재 조립 상태와 맞지 않거나 그리퍼가 따라갈 수 없으면 현재 경로 계획기를 목표 pose에 연결해 제한된 재계획을 수행한다. 물체 경로만 통과한다고 로봇도 통과한 것으로 처리하지 않는다.

### 7.2 목표 TCP와 임의 방향

실제로 잡은 뒤 측정한 변환으로 계산한다.

```text
T_TCP_P = inverse(T_W_TCP) @ T_W_P
T_W_TCP_goal = T_W_P_goal @ inverse(T_TCP_P)
```

각 중간 waypoint에도 같은 계약을 적용한다. 목표 회전을 identity로 만들거나 접근/후퇴를 무조건 world +Z로 고정하지 않는다. 파지 자세·경로·주변 형상을 이용하여 접근과 해제 후 빈 그리퍼 후퇴를 검사한다. 손가락이 설치된 부품 사이에 갇히면 그 파지의 설치 실패로 반환한다.

### 7.3 접촉 정책과 관계 정보

제품별 수동 기둥–슬리브 관계표를 요구하지 않는다. 목표 CAD 배치와 표면 거리/교차, 실제 관측 접촉, 동작 단계를 이용해 관계와 검사 정보를 자동 생성한다.

패드–대상 부품의 파지 접촉, 제품–제품의 설치 접촉, 로봇–다른 부품/작업대의 충돌을 구분한다. 정당한 제품 간 접촉 쌍은 어느 부품부터 검사해도 동일하게 판정한다. 지지력의 방향은 별개로 보존한다.

목표에서 인접한 쌍이라고 해서 운반 중 모든 위치의 접촉을 허용하지 않는다. 실제 경로/단계·접촉 위치·관통·기설치 부품 변위를 함께 본다. 반대로 모든 일반 부품이 사각 소켓 바닥과 접촉해야 한다는 전용 조건도 적용하지 않는다.

연속 경로 충돌 검사는 로봇 링크·그리퍼·부품을 포함한다. 드문 waypoint만 확인해 그 사이 벽을 통과하는 경로를 허용하지 않는다. 실제 사용한 보간/검사 해상도와 한계를 기록한다.

### 7.4 완료와 동작별 추가 검사

공통 완료 판정은 동봉한 프로파일 v1.2를 따른다. 원 CAD 목표, 축별 5mm·상대각 3°·최종 경질 관통 0.5mm, 해제/이격, 속도, 정착 1초+연속 관찰 1초는 유지한다.

삽입 축·목표 깊이를 검증된 기하에서 실제로 정의할 수 있는 작업에는 깊이 오차<1mm와 사전 정렬<1mm/<1° 등 해당 조건을 유지한다. 일반 놓기 작업에 가상의 구멍 폭이나 깊이를 만들지 않는다. 적용 여부·근거·미적용 사유를 기록한다. 분해 경로 전체 길이를 삽입 깊이로 대체하지 않는다.

공통 완료는 모델링된 강체의 목표 배치와 물리 유지에 대한 판정이다. 명시적으로 모델링하지 않은 나사 조임·접착 경화·클립 잠김까지 증명하지 않는다. 그런 작업이 필요해 진행이 막힌 경우 실제 모델/동작 부족을 보고한다. 모든 곡면이나 배터리팩을 종류 자체로 차단하는 근거로 쓰지 않는다.

## 8. 실패·경험·해결지침·검색

### 8.1 객관적 사건

실패는 `source`, `phase`, `failure_code`, `executed_in_main`, action/check ID, scene revision과 실제 측정값을 포함한다. 최소한 아래 원인을 구분한다.

| 단계 | 예시 결과 |
|---|---|
| 입력/준비 | 정보 부족, 좌표/단위 모순, 충돌 자산 품질 실패, 기준 상태 불안정, 배치 탐색 소진 |
| 후보/기하 | 잘못된 pose, 오래된 후보, 가용 폭 초과, 접근 간섭, IK/경로 후보 미발견 |
| 물리 파지 | 패드 접촉 부족, 들림 실패, 슬립, 낙하 |
| 운반/설치 | 로봇·그리퍼·부품 경로 충돌, 설치 공간을 막는 파지, 목표 접근 실패 |
| 해제/완료 | 후퇴 경로 실패, 계속 로봇이 지지함, 목표 오차·관통·속도·관찰 창 실패 |
| 시스템/한도 | 시간·호출·후보 예산 소진, 자산/모델 오류, 미실행 |

실제 접촉에서 관측된 상대 부품과 위치/거리/관통을 반환할 수 있다. 경로 탐색이 실패했다는 사실만으로 특정 부품을 유일 원인이라고 단정하지 않는다. 관측 사실과 Astra의 해석을 구분한다.

### 8.2 경험과 해결지침

모든 시도는 실행 로그로 보존한다. 재사용 메모리는 **객관적 문제 사건+실제 변경/실행+원래 설치 완료 증거**와 그 근거에서 생성한 짧은 해결지침으로 구성한다. 별도의 생성 Python 스킬은 만들지 않는다.

파지 copy 통과만으로 설치 문제를 해결했다고 등록하지 않는다. 같은 부품/목표의 최종 설치가 검증되어야 해당 해결지침의 등록 근거가 된다. 전체 run 실패와 이미 검증된 개별 설치 해결은 구분해 기록한다. 입력/형상 변환 실패를 Astra의 파지 해결 경험으로 둔갑시키지 않는다.

실패 시도 부품을 중심으로 주변 관계가 보이는 실제 snapshot 이미지를 저장한다. 영상/이미지는 상태 hash, 모델, 카메라, action/check, source와 연결한다. 이미지 임베딩만 남기지 않고 원본 PNG와 필요한 상태를 보존한다.

지침 생성 프롬프트는 실제 실패·변경 파라미터·최종 검사 증거만 입력으로 받아 적용 조건, 권장 대응, 성공 근거와 한계를 짧게 출력하게 한다. 허용하지 않은 재파지/체결 행동이나 관측하지 않은 원인을 만들지 못하도록 기계 행동 계약과 증거 ID를 검사한다. 장문의 사고 과정을 저장하거나 근거 없는 인과관계를 사실로 승격하지 않는다.

### 8.3 검색과 비교 실험

문제 코드·단계·실제 접촉 상대 역할·그리퍼·동작·필수 기하 조건으로 먼저 필터링하고, 통과 후보 안에서 DINO 이미지 임베딩 유사도로 순위를 매긴다. 사각 `shape` 라벨이 없다는 이유만으로 일반 형상 경험을 배제하지 않는다. 이미지 비교 불가 시 검증된 조건의 메타데이터 검색을 명시적으로 구분한다.

Astra에는 짧은 지침·적용 조건·근거 ID를 전달하고 실패 이미지를 매번 추가 입력하지 않는다. 현재 장면에서 행동을 다시 검증하며 과거 성공을 현재 성공으로 간주하지 않는다.

연구용 수집은 기존 memory-off 정책, 평가는 고정 snapshot과 원본 중복 방지를 유지한다. 같은 입력에서 저장→다음 검색을 확인하는 기능 시험은 독립 성능 평가와 구분한다. 후보 생성기/충돌 자산/검증 정책/예산을 모든 비교 조건에 동일하게 적용한다.

## 9. 최소 UI와 자동 실행

기존 UI가 있으면 연결하고 없으면 기존 Python 실행기를 호출하는 얇은 로컬 UI를 만든다. 다른 실행기나 성공 판정기를 UI 안에 복제하지 않는다.

필수 기능은 입력 선택, 공통 환경 상태, 준비 진행, 목표 이미지, 현재 부품/단계, Astra/scripted 출처, 최종 결과·실패 근거·측정값, 실제 영상·로그 다운로드, 경험 등록/검색 결과다. 후보를 표시하는 UI는 실제 메시/좌표에서 생성한다. 사용자가 매 부품마다 잡을 부위를 클릭하거나 관계표를 작성해야만 진행되는 흐름으로 바꾸지 않는다.

물리 결과, 증거 audit 결과, 미디어 생성 결과를 구분한다. 파일 생성이나 exit 0만으로 전체 조립 성공을 표시하지 않는다. 후보 없음·준비 실패·부분 진행·실제 실패·미실행·전체 완료를 명확히 표시한다. 모델/환경 설정과 예산은 공통 설정을 사용하고 단계마다 승인을 다시 요청하지 않는다.

실시간 웹 3D 엔진을 새로 만드는 것은 필수가 아니다. 실제 실행의 상태/영상/이미지를 보고 교수 시연 자료로 확인할 수 있으면 된다. 재생은 저장 상태의 재생임을 표시하고 실제 원 run과 연결한다.

## 10. 기존 F01–F16: 이번 작업에서도 반드시 해결할 항목

아래 항목은 검토 commit에서 확인한 결함이다. 최신 코드에서 이미 고쳐졌으면 증거를 확인한다. 새로운 일반 경로로 교체하면 동일한 오류가 재발하지 않는지 확인하고 대응 위치를 보고한다. 원래 우선순위는 유지한다.

### F01 · P1 · 정상 접촉의 검사 방향 비대칭

- 기존 반례: 완성 배치의 덮개→슬리브 접촉은 허용되지만 슬리브 관점에서 같은 접촉이 금지되어 최종 검사가 실패.
- 수정: 목표 기하와 단계에서 정당한 제품 접촉 쌍을 검사 방향에 무관하게 판정. 지지력 방향은 별도 유지. 형상명 관계표를 공통 실행의 필수로 두지 않음.
- 확인: 같은 상태에서 부품 검사 순서를 바꿔도 동일 결과. 운반 중 무관한 접촉·관통은 계속 거절.
- 근거: [FrameVerifier](https://github.com/ramen0519/llm-robot-assembly/blob/cfe6c882fbb933c35c49b6544901beaaa0419a7a/scripts/frame_assembly_skills.py), [최종 실행 검사](https://github.com/ramen0519/llm-robot-assembly/blob/cfe6c882fbb933c35c49b6544901beaaa0419a7a/scripts/assembly_v12/execution.py).

### F02 · P2 · 복구 후 오래된 파지 변환 사용

- 기존 반례: 2mm의 상대변화를 현재 관측으로 보정했지만 다음 insert가 최초 held_pose를 사용해 보정을 되돌림. 오프라인 계산/제어 경계 재현이며 실제 미끄러짐 복구 성공 시험은 아님.
- 수정: 계획용 현재 파지 변환과 최초 슬립 감시 변환 분리. 운반·목표 TCP·waypoint 계산에 같은 현재 관측 계약 사용.
- 확인: 보정 후 다음 명령이 되돌아가지 않음. 누적 슬립 한도는 계속 감시. 일반 6D 회전/평행이동에도 같은 원칙 적용.
- 근거: [복구](https://github.com/ramen0519/llm-robot-assembly/blob/cfe6c882fbb933c35c49b6544901beaaa0419a7a/scripts/insertion_recovery.py), [삽입](https://github.com/ramen0519/llm-robot-assembly/blob/cfe6c882fbb933c35c49b6544901beaaa0419a7a/scripts/insertion_skills.py).

### F03 · P1 · 모델 응답과 사건의 실제 실행 여부 불일치

- 기존 반례: 실패 tool output은 executed=true, finally가 event만 실제 시간 변화에 맞춰 수정.
- 수정: source/phase/executed/check ID/상태를 확정한 결과에서 tool output·event·UI를 함께 생성. copy 진행과 주 실행을 분리.
- 확인: 이동 전 거절과 일부 주 이동 후 실패를 양쪽에서 동일하게 보고. 관측 revision도 일치.
- 근거: [execution.py](https://github.com/ramen0519/llm-robot-assembly/blob/cfe6c882fbb933c35c49b6544901beaaa0419a7a/scripts/assembly_v12/execution.py).

### F04 · P1 · 공통 실행 기한 누락

- 기존 반례: Recorder 기한이 지나도 copy 물리 step 진행. token count 중 기한이 끝나도 generation 시작.
- 수정: Recorder와 독립된 공통 Budget/cancellation을 메시 분해·배치·후보·copy·IK·RRT·물리 반복·API에 전달. 내부 제한과 남은 시간 중 작은 값 사용. count 뒤 timeout 재계산. 외부 인코더에도 유한 기한.
- 확인: 만료 후 새 step/HTTP/주 동작이 시작되지 않음. copy에 주 Recorder를 붙여 기록을 혼합하지 않음. 불명확한 API 응답의 예약 사용량과 무재시도 정책 유지.
- 근거: [scene.py](https://github.com/ramen0519/llm-robot-assembly/blob/cfe6c882fbb933c35c49b6544901beaaa0419a7a/scripts/assembly_v12/scene.py), [responses.py](https://github.com/ramen0519/llm-robot-assembly/blob/cfe6c882fbb933c35c49b6544901beaaa0419a7a/scripts/assembly_v12/responses.py).

### F05 · P1 · 수집/평가 계약과 원본 누수

- 기존 반례: direct run이 collection memory-on·미동결 evaluation을 허용. 같은 source_run_hash를 다른 lineage로 바꾸면 평가에 유입.
- 수정: direct/batch/UI 공통 검사. collection memory-off·development 지침 제외, evaluation 고정 snapshot/계획 필수. 원본 export/실험 조건 해시로 중복 확인. 현재 run 및 평가 중 생성 지침을 검색 snapshot에 섞지 않음.
- 확인: 이름 변경으로 동일 원본이 독립 평가가 되지 않음. 같은 제품의 다른 조건 시험은 명시한 분리 정책으로 처리. 동일 입력 재사용 기능 시험은 별도 표기.
- 근거: [entry.py](https://github.com/ramen0519/llm-robot-assembly/blob/cfe6c882fbb933c35c49b6544901beaaa0419a7a/scripts/assembly_v12/entry.py).

### F06 · P1 · 실행 자산/전처리 동결 누락

- 기존 반례: 실제 XML·mesh·TOML·third-party planner 변경에도 fingerprint 동일.
- 수정: 코드·환경·로봇/그리퍼/TCP·충돌 자산·물성·솔버·경로·후보 생성기·완료 프로파일·원본/준비 자료·seed·DINO 전처리/의존 버전을 실제 런타임 inventory로 동결.
- 확인: 실행에 영향 주는 변경은 평가 전에 검출. embedding 규약이 바뀌면 별도 버전/명시적 재임베딩. 네 비교 조건의 입력·후보 정책·검증·예산 일치.
- 근거: [artifacts.py](https://github.com/ramen0519/llm-robot-assembly/blob/cfe6c882fbb933c35c49b6544901beaaa0419a7a/scripts/assembly_v12/artifacts.py), [memory.py](https://github.com/ramen0519/llm-robot-assembly/blob/cfe6c882fbb933c35c49b6544901beaaa0419a7a/scripts/assembly_v12/memory.py).

### F07 · P2 · audit의 최종 검사와 사건 연결 누락

- 기존 반례: final verification이 false/없어도 audit pass. 다른 사건의 이미지/state/sidecar끼리 hash만 맞춰도 pass.
- 수정: 성공에는 모든 필수 부품·동일 최종 창·동작별 필수 검사·profile 증거 요구. event와 모델/state/image/action/check/source hash를 교차 대조.
- 확인: 잘못된 final/외부 사건 자료 거절. 준비 실패의 해당 없음, 있어야 할 증거의 누락, 물리/미디어/audit 결과를 구분.
- 근거: [validate_v12_run.py](https://github.com/ramen0519/llm-robot-assembly/blob/cfe6c882fbb933c35c49b6544901beaaa0419a7a/scripts/validate_v12_run.py).

### F08 · P2 · 제어 상한이 전체 API 예산을 덮어씀

## 11. 실제 완료 기준과 첫 경험 수집

### 11.1 입력 사례와 검증 범위

가능하면 사용자가 실제 사용할 배터리팩/선정 학습 데이터를 프로젝트의 입력 자료에서 우선 사용한다. 이 문서에는 그 파일이 첨부되어 있지 않다. 실제 파일을 확보하지 못했으면 이름만 붙인 합성 자료로 대체해 해당 제품을 검증했다고 보고하지 않는다.

실제 자료가 없어도 일반 경로 구현과 아래 결정적 합성 CAD/메시 fixture 검증을 완료한다. 같은 알고리즘을 사용하며 fixture 이름/ID를 분기 조건으로 넣지 않는다. 전처리·파지·조립의 어느 단계까지 확인했는지 분리한다.

| ID | 확인 사례 | 필수 증거 |
|---|---|---|
| V01 | 기존 10부품 사각 프레임 | 기존 실행 회귀와 F01 등 오류가 유지되지 않음. 이것만으로 일반화 완료를 선언하지 않음 |
| V02 | 곡면/원통, 오목한 케이스 또는 관통 구멍, 비대칭 형상 | 종류별 전용 코드 없이 입력·충돌 자산·후보·물리 시험에 진입. 실제 구멍 통과/벽 충돌 확인 |
| V03 | 옆 또는 경사 파지와 회전된 목표 | top-down이 아닌 파지를 적어도 하나 실제 실행. 목표 회전/좌표를 보존하고 해제 후 검증 |
| V04 | 일반 형상을 포함한 10부품 이상 조립체 | 자동 초기 배치→실제 로봇 집기/운반/설치→전 부품 최종 관찰→영상의 전체 run. 실제 Astra 정책의 완주 증거 필요 |
| V05 | 11개 이상(예:12개) 준비, ID/치수/전체 CAD 회전 변경 | 고정10 배열/형상명 분기가 없음. 준비 검증을 전체 조립 성공으로 세지 않음 |
| V06 | 실패 후보 후 다른 후보로 해결 | 파지 실패와 파지는 가능하지만 설치가 막힌 경우를 구분. 실제 설치 해결→지침 등록→다음 실행 검색/재검증 |
| V07 | 잘못된 성공 판정 반례 | 계속 잡고 있음, 과도 관통, 목표 밖, 창 중간 이탈, 필요한 동작 검사 누락, 불완전 창 거절 |
| V08 | 사용자 흐름 | UI의 입력·진행·실패/성공·영상·비용·경험 결과가 같은 run 기록과 일치 |

V04의 일반 조립체는 기존 사각 프레임의 이름 변경만으로 충족하지 않는다. 원통/곡면 또는 오목한 비사각 부품을 실제 집기·설치에 포함하고, 완성 목표와 물리 조건이 유효한 자료를 사용한다. 자료 자체가 기준 상태 검사에서 실패하면 그 사실을 보고하며 통과하도록 숨겨 고정하지 않는다.

V06의 의도적으로 만든 실패는 development 교란으로 표시한다. 자연 발생 실패와 구분하고 평가 성공률에 섞지 않는다. 같은 입력에서 지침 재사용을 확인한 것은 기능 확인이며 새로운 형상 일반화 성능을 입증하지 않는다.

기존 검사와 위 직접 변경 위험을 다루는 검사만 필요한 만큼 수행한다. 폐기한 사각 전용 계약을 무조건 통과시키려고 새 구조를 되돌리지 않는다. 어떤 기존 검사를 새 불변조건 검사로 교체했는지 설명한다.

### 11.2 실제 Astra·DINO·시범 수집

실제 모델 호출, 실제 DINO 특징 추출, 실제 MuJoCo 주 실행, mock/오프라인 검사를 따로 보고한다. 지침 등록 수와 다음 실행의 검색 receipt를 확인한다. 영상은 저장한 실제 상태와 연결한다.

기존 승인·설정 예산 안에서 실제 Astra 5회 시범 수집을 수행한다. 5회 모두 성공시킬 필요는 없지만 준비/판정/기록/등록에 시스템 오류가 없어야 한다. 물리적 실패는 원인·측정값과 함께 남기고 해결된 사건만 지침으로 등록한다. 문제가 없으면 기존 manifest와 예산으로 본 수집을 이어간다.

시범 5회는 대규모 성능/일반화 결론이 아니다. 모든 비교 조건의 평가 계획과 메모리 동결은 별도 명시한다. 실제 모델·자산·예산이 없으면 `not_run`과 구체 사유·재개 명령을 남기고, 가능한 구현과 오프라인 검증은 마무리한다.

### 11.3 완료 보고의 의미

최종 프로토타입 완료에는 일반 메시 경로, 실제 Astra의 전체 조립, 검증된 해결지침과 재사용, 최소 UI의 확인이 필요하다. 작은 예제·기준 배치 직접 설정·화면 표시·scripted/mock 결과를 대신 세지 않는다.

사용자 배터리팩 파일이 없으면 그 제품 검증은 미실행으로 남긴다. 일반 형상 fixture의 통합 검증 완료와 사용자 제품 검증 상태를 따로 보고한다. 실제 통합 실행이 막혔다면 구현 완료와 실행 검증 완료를 구분하고 전체 검증 완료를 선언하지 않는다.

## 12. 한 번의 통합 작업으로 수행할 순서

다음은 코덱스 내부 구현 순서이며 매 단계 사용자 허가를 다시 받는 절차가 아니다.

1. 최신 branch/HEAD/미커밋 변경/AGENTS.md와 기존 자산·예산·테스트 확인. 과거 commit으로 reset하지 않음.
2. 입력/좌표/경로/충돌 자산/일반 registry와 완료 프로파일 계약 정리. 기존 설계·프롬프트·README의 충돌 지시 갱신.
3. 일반 장면·초기 자세/배치·자원 관리 구현. raw CAD와 export 경로 모두 연결.
4. Python 후보 생성, Astra 후보/pose 출력, 일반 파지·복사 검사·주 실행 연결.
5. 역경로/목표 pose 운반·설치·해제·후퇴·연속 검증 구현.
6. F01–F16을 일반 경로에 적용하고 경험·검색·audit·통계·동결·UI 연결.
7. 직접 관련 검사와 실제 통합 실행, 기존 예산의 시범 수집, 사용 명령/최종 보고서 제출.

대규모 프레임워크 교체, 별도 학습 모델 훈련, 임의 코드 생성 스킬, 실물 로봇 연결은 이번 구현의 선행 조건으로 추가하지 않는다. 필요한 형상 처리 라이브러리·현재 실행기의 리팩터링은 이번 작업에 포함한다.

## 14. 검토 근거와 한계

검토 commit에서 기존 unittest 73개 통과, 정상 사각 완성 배치의 MuJoCo 검사, 일부 예산/로그/입력/메모리 경계 재현은 앞선 검토에서 확인했다. 이는 새 일반 메시 경로·실제 Astra 전체 조립·DINO·UI의 검증 결과가 아니다. 이번 문서 작성 과정에서 저장소는 수정하지 않았다.

현 코드의 일반화 제약은 [preparation.py](https://github.com/ramen0519/llm-robot-assembly/blob/cfe6c882fbb933c35c49b6544901beaaa0419a7a/scripts/assembly_v12/preparation.py), [scene.py](https://github.com/ramen0519/llm-robot-assembly/blob/cfe6c882fbb933c35c49b6544901beaaa0419a7a/scripts/assembly_v12/scene.py), [post_grasp.py](https://github.com/ramen0519/llm-robot-assembly/blob/cfe6c882fbb933c35c49b6544901beaaa0419a7a/scripts/post_grasp.py), [contracts.py](https://github.com/ramen0519/llm-robot-assembly/blob/cfe6c882fbb933c35c49b6544901beaaa0419a7a/scripts/assembly_v12/contracts.py)에서 확인했다.

일반 비볼록 충돌 처리의 기술 근거는 [MuJoCo 공식 computation/convex decomposition 문서](https://mujoco.readthedocs.io/en/stable/computation/#convex-decomposition)다. 실제 적용 버전의 지원 기능과 충돌 근사 품질을 확인한다. [Contact-GraspNet 공식 구현](https://github.com/NVlabs/contact_graspnet)은 형상 기반 공간 파지 후보 기술의 참고 사례이며, 이번 프로토타입에 그 모델을 반드시 추가하거나 해당 성능을 우리 시스템 성능으로 주장하라는 지시가 아니다.

본 v2.0의 새 구현 계약과 수용 기준은 사용자 목표를 구현하기 위한 설계 결정이다. 실제 코드에 이미 구현됐거나 모든 CAD에서 성공한다고 주장하지 않는다. 동봉한 `CODEX_PROMPT_ASSEMBLY_v2.0.txt`를 두 문서와 함께 전달한다.
