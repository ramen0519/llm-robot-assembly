# 21C단계 — 실패를 읽고 운반 재계획을 선택하는 정책

## 이번 단계의 목적

기존 `direct_then_rrt`는 직접 이동 경로가 막히면 모션 코드가 정해진 대체 경로 탐색을 수행했다. 이번에는 **실행 전 경로 실패 → 새 관측 → 정책의 재계획/중단 선택 → 검사된 실행**을 LangGraph에 연결했다. 기본값은 이전과 같은 재계획 예산 0이며, `--transport-replan-budget 1`을 지정해야 새 선택지가 열린다.

정책은 ‘다음에 무엇을 할지 고르는 부분’이다. 현재 물리 검증은 규칙 정책으로 수행했다. 실제 LLM API 연결부에도 같은 관측·선택지를 전달하도록 했지만, 이번 검증의 실제 API 호출은 0회다. 규칙 정책 성공이 LLM 추론 효과를 입증하는 것은 아니다.

성공 기준은 첫 기둥을 잡은 상태에서 막힌 직접 경로를 실행하지 않고, 새 관측에 근거한 정책 선택으로 우회한 뒤 실제 삽입을 검증하는 것이다. 6mm 정렬 오차가 함께 있으면 그 오류도 별도로 검출·복구해야 한다.

## 쉬운 예시로 보는 흐름

1. 로봇이 기둥을 접촉·마찰로 잡고 들어 올린다.
2. 구멍 위로 이동하려는 경로를 복사한 시뮬레이션 상태에서 검사한다. 장애물이 있어 `PLANNED_CONTACT`가 발생한다. 이 경로는 실제로 실행하지 않는다.
3. 실행기는 ‘방금 계획만 거부됐고 로봇·물체 상태는 그대로’라는 내부 기록을 만든다.
4. LangGraph가 관측을 새로 읽는다. 관측 번호는 증가하지만 이 시뮬레이션에서는 정책 판단 중 물리 시간이 진행되지 않는다.
5. 정책에 `replan_insert`와 `stop`을 제시한다. 전자는 ‘현재 파지를 유지하고 검사된 다른 운반 경로를 찾아 삽입을 시도’, 후자는 ‘이번 실행 중단’이다.
6. 재계획을 선택하면 실행기가 관측·상태·예산을 다시 확인한다. 기존 IK·모션 플래너로 후보를 만들고 로봇·그리퍼·운반 부품의 충돌을 검사한다.
7. 검사 통과 후 기존 제어기가 관절을 움직인다. 도착·정렬·삽입·해제·지지 상태를 측정해 성공 여부를 판정한다.

LLM이 관절 각도나 임의 Python 코드를 작성하는 도구는 아니다. 정책은 제한된 스킬을 선택하고, 실행 코드가 계획·물리 실행·검사를 담당한다. 아직 대체 파지나 자유로운 작업 분해까지 선택하는 구조는 아니다.

## 무조건 재시도와 다른 점

`scripts/rejected_insert.py`의 로컬 기록은 다음 조건을 모두 만족할 때만 유효하다.

- 실패는 실제 플래너에서 받은 `PLANNED_CONTACT`이며 발생 위치는 정확히 `insert_transfer/preflight`다.
- 기록은 실패한 계획 직전에 캡처한 상태와 연결된다. 단순히 JSON 보고서의 실패 코드를 맞춰 보내서는 실행할 수 없다.
- 시간, 관절·물체 상태, 제어값, 파지 관계, 충돌 형상, 주요 물리 설정, 목표 위치·방향이 동일해야 한다.
- 삽입 접촉을 허용하는 단계가 아니어야 한다.
- 재계획 요청 시 기록을 먼저 소비한다. 상태가 바뀌어 거부되거나 실행에 실패해도 같은 기록을 다시 쓰지 않는다.

정책에는 이 내부 배열 전체 대신 ‘실행 전 거부 여부, 발생 시점, 목표 TCP, 보존할 정렬 오차, 허용 대안’의 요약을 전달한다. 정책의 출력은 스킬·부품 ID·목표 ID·관측 번호·짧은 이유만 받는다. 목표 좌표나 복구 예산을 정책이 바꾸게 하지 않았다.

운반 재계획은 최대 1회, 기존 정렬 복구도 최대 1회다. 서로 다른 카운터로 기록한다. 재계획 시도 자체가 예산을 소비하며, 도중에 실패했다고 횟수가 되돌아가지 않는다. 실제 접촉·삽입 중 실패나 실행 여부가 불확실한 명령을 이 기능으로 재생하지 않는다.

## 기록의 의미

| 항목 | 의미 |
|---|---|
| `graph_state.transport_replans` | 정책이 선택해 시도한 재계획 횟수 |
| `graph_state.recoveries` | 검증까지 통과한 기존 정렬 복구 횟수 |
| `policy_replan_attempts` | 어떤 실행 전 실패를 근거로 재계획했고 어떻게 끝났는지 |
| `transport_executed` | 재계획 후 이동 실행기에 진입했는지. 도중 실패도 포함하는 보수적 표시 |
| `transport_completed` | 운반 실행이 정상 반환했는지 |
| `graph_events.jsonl` | 관측 번호, 정책 선택, 실행·검증, 예산 변화 |

운반은 성공했지만 다음 정렬 검사가 실패했다면 재계획 삽입 동작 전체의 `status`는 `failed`이고, `transport_executed`와 `transport_completed`는 `true`다. 이후 별도의 정렬 복구가 성공해 최종 조립이 성공할 수 있다. 이 구분이 없으면 ‘이동하지 못함’과 ‘이동 후 결합 실패’를 혼동하게 된다.

## 실행 명령

`C:\dev\llm-robot-assembly`에서 실행한다.

```powershell
uv run --locked python scripts/run_assembly_graph.py --mode single --transfer-obstacle --transport-replan-budget 1 --scenario alignment_offset --snapshots
```

예상 선택 순서:

```text
pick → insert(경로 거부) → replan_insert(우회 후 정렬 실패)
     → recover_alignment → insert → finish
```

정렬 실패 없는 시험은 `--scenario alignment_offset`을 빼면 된다. 정책 선택 없는 기존 자동 우회는 `--transport-strategy direct_then_rrt`이며, 이를 `--transport-replan-budget 1`과 동시에 사용하면 입력 오류로 거부한다. 두 방식의 결과를 같은 실험으로 혼동하지 않기 위해서다.

이 명령은 첫 결합 전용 실행기다. 전체 10부품 실행기의 기존 자동 우회는 유지되며, 전체 작업의 정책 재계획 횟수 배분은 이번 구현 범위 밖이다. 실제 LLM 실행은 별도로 명시한 라이브 설정이 필요하고, 설정 없이 위 명령을 실행하면 API를 호출하지 않는다.

## 제한과 다음 작업

고정된 첫 결합 장면과 기존 모션 플래너의 제한된 대안을 검증한다. 샘플 간 충돌의 수학적 연속 보장이나 일반적인 모든 장애물의 우회를 주장하지 않는다. 6mm 오정렬은 명시적인 개발용 시험 조건이다. 시험 장애물의 형상·위치도 고정되어 있다.

이번 결정은 규칙 정책으로 검증했으며 실제 LLM의 대안 선택 능력, 비용 절감, 멀티에이전트 우수성은 아직 비교하지 않았다. 그 비교에는 별도 시험 조건과 동일한 관측·도구·전체 예산이 필요하다. 등록된 복구 절차는 기존 조건에서만 재검증하며 이번 우회 성공을 새 스킬로 자동 승격하지 않는다. 실물 로봇 명령은 수행하지 않았다.
