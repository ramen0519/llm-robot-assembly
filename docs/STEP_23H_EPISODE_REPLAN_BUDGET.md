# 23H단계 — 두 기둥 연속 조립과 작업 전체 재계획 한도

## API 없이 진행한 이유와 목표

21C에서 첫 기둥에 연결한 ‘실패 후 재관측→정책의 재계획/중단 선택’을 두 기둥의 연속 작업으로 확장했다. API 키 없이 기존 규칙 정책과 실제 MuJoCo 물리 실행으로 검증했다. 이 기반 위에 나중에 실제 LLM 정책을 연결할 수 있다.

성공 기준은 같은 시뮬레이션에서 두 기둥을 차례로 집어 설치하고, 첫 설치를 유지하며, 재계획 한도가 부품마다 새로 생기지 않는 것이다. 제품 부품은 고정 바닥판과 두 기둥으로 3개, 로봇이 설치하는 부품은 2개다. 최종 목표인 10부품 제품을 줄인 것이 아니라 이번 모듈의 검증 단위다.

## ‘전체 예산’은 무엇인가

이번 예산은 돈이나 토큰이 아니라 **작업 한 번에서 허용하는 운반 재계획 횟수**다.

```text
전체 재계획 한도 2회
  첫 기둥: 직접 경로 거부 → 재계획 1회 → 남은 한도 1회
  두 번째 기둥: 직접 경로 거부 → 재계획 1회 → 남은 한도 0회
```

한 부품에서는 최대 1회만 재계획한다. 실행기는 다음 부품에 `min(1, 전체 남은 횟수)`를 전달한다. 재계획 동작을 처리한 `execute` 이벤트에서 성공·실패를 포함해 전체 횟수를 차감한다. 각 부품의 LangGraph가 새로 시작돼도 전체 장부는 같은 실행기에 남는다.

정렬 복구는 별도 한도로 작업 전체 최대 1회다. 운반 재계획은 ‘막힌 경로를 다시 찾는 것’, 정렬 복구는 ‘구멍 위에서 측정한 위치 오차를 바로잡는 것’이다. 두 작업을 같은 성공이나 같은 횟수로 세지 않는다.

정책에 제시하는 허용 동작과 재계획 한도는 현재 부품 기준이다. 전체 횟수의 배분·제한은 상위 실행기가 맡고 전체 사용량은 이벤트와 결과에 기록한다. 이번에는 LLM이 미래 부품까지 고려해 예산을 최적 배분하는 능력을 평가하지 않았다.

## 빈 그리퍼 접근과 부품 운반을 분리

첫 기둥 설치 후 두 번째 기둥을 집으러 갈 때도 장애물을 피해야 한다. 기존에는 빈 그리퍼 접근과 부품 운반이 하나의 `transport_strategy` 설정을 공유했다. 이번에는 다음처럼 지정할 수 있다.

| 옵션 | 담당하는 이동 |
|---|---|
| `--transport-strategy direct` | 부품을 든 운반은 먼저 직접 경로를 검사한다. 실패하면 정책에 알린다. 기본값이다. |
| `--empty-approach-strategy direct_then_rrt` | 열린 빈 그리퍼가 부품 위로 접근할 때 기존 모션 코드의 검사된 우회를 사용한다. |
| `--transport-replan-budget 2` | 정책이 선택하는 운반 재계획을 작업 전체에서 최대 2회 허용한다. |

빈 그리퍼의 자동 우회는 정책이 선택한 운반 재계획 횟수에 포함하지 않는다. 대신 `empty_approach_attempts`에 따로 기록한다. 이 값은 모든 플래너 호출이나 모든 우회를 합친 횟수가 아니다. 두 종류 모두 기존 충돌 검사를 거쳐 실행한다.

새 접근 옵션을 생략하면 기존처럼 운반 전략을 따른다. 따라서 기존 자동 우회 명령의 기본 동작은 유지된다. 정책 재계획은 현재 `--parts 2` 또는 `3`, 그래프 모드, 직접 운반에서만 활성화할 수 있다. 전체 10부품 실행기의 자동 우회는 이전 기능이며 이번 정책 재계획 범위와 구분한다.

## 다른 부품과 결합 규칙도 확인

21C의 로컬 일회성 기록은 시간·관절·제어값·파지·형상·목표가 그대로인지 확인한다. 다부품 작업에서는 여기에 다음 항목을 추가했다.

- 현재 조작하는 부품 ID.
- 이미 설치했다고 선언된 부품 목록.
- 각 부품의 목표, 선행조건, 지지·접촉 관계를 포함한 부품 등록 정보.

다른 부품이 움직였거나 설치 상태·접촉 허용 관계가 바뀌면 이전 실패 기록으로 재계획하지 않는다. 기존 `FrameVerifier`는 매 물리 단계에서 설치된 부품의 위치·방향·지지·속도와 실제 충돌 형상을 계속 검사한다. 모델이나 부품을 순간이동시켜 성공을 만든 것이 아니다.

## 실행 명령

작업 폴더는 `C:\dev\llm-robot-assembly`다.

```powershell
uv run --locked python scripts/run_frame_assembly.py --parts 3 --mode single --scenario first_alignment_offset --transfer-obstacle --empty-approach-strategy direct_then_rrt --transport-replan-budget 2 --snapshots
```

`--viewer`를 추가하면 같은 물리 실행을 창으로 볼 수 있다. `--snapshots`는 설치 후 이미지를 저장한다. 첫 기둥에는 개발용 6mm 정렬 오차를 넣어 재계획과 정렬 복구가 같은 작업에서 이어지는지 확인한다.

예산 소진을 확인하려면 위 명령에서 `--transport-replan-budget 1`로 바꾼다. 이 조건에서는 첫 기둥만 설치하고 두 번째 운반 경로 거부에서 `failed`로 종료하는 것이 기대 결과다. 명령 종료 코드 1도 이 시험의 예상 결과다.

## 실제 실행 결과

두 실행의 장면·정책·시나리오·기록된 소스 12개는 일치하고, 설정에서 전체 재계획 한도만 다름을 별도로 확인했다. 기록된 소스 지문은 이번 코드와도 일치한다.

| 항목 | 한도 2회 | 한도 1회 |
|---|---|---|
| 결과 | `success` | 두 번째 운반 계획 거부로 `failed` |
| 로봇 설치 | 2/2 | 1/2 |
| 소비한 운반 재계획 | 2회 | 1회 |
| 정렬 복구 | 첫 기둥 1회 | 첫 기둥 1회 |
| 정책 선택 | 10회 | 8회 |
| 물리 시간 | 222.868초 | 156.708초 |
| 물리 측정 | 111,484행 | 78,393행 |
| 실제 실행 시간 | 96.547초 | 78.547초 |
| 실제 LLM API | 0회 | 0회 |

실행 ID:

- 한도 2회: `runs/step23_frame/20261101T092900_641213Z_a6916448`.
- 한도 1회: `runs/step23_frame/20261101T093020_211581Z_50df6847`.

두 실행 모두 시간 기록의 역행이 없고 물리 측정 간 최대 간격은 2ms였다. 성공 실행에서 첫 기둥·두 번째 기둥의 최종 검사 구간 최대 위치 오차는 각각 **0.1986mm, 0.1742mm**였다. 두 번째 작업 중 첫 기둥의 목표 대비 최대 위치 오차도 **0.1986mm**로 1mm 기준 안에 유지됐다.

한도 1회에서는 첫 기둥에서 사용한 횟수가 두 번째 부품에 넘어가도 복구되지 않았다. 두 번째 부품은 집어 든 뒤 직접 경로 검사에서 멈췄으며 거부된 운반 경로와 삽입 하강은 실행하지 않았다. 부분 설치 1개를 전체 성공으로 처리하지 않았다. 실패 실행이 더 짧게 끝난 값은 성능 향상이나 속도 비교 근거가 아니다. 다른 검사와 CPU를 공유한 실행 시간이라는 점도 함께 기록한다.

중단 검사는 남은 한도가 있어도 규칙 시험 정책이 두 번째 재계획을 거절하는 경우다. 결과는 `stopped`, 설치 1/2, 사용 1회·잔여 1회였다. `failed`인 예산 소진 시험과 구분한다. 완료한 첫 설치를 전체 성공으로 올려 세지 않았다.

두 기둥 성공 검사는 매 물리 단계에서 실제 데이터의 관절·부품 상태가 물리 엔진 밖에서 덮어써지지 않는지, 고정 형상과 그리퍼 이외의 추가 결합이 생기지 않는지도 확인했다. 설치 선언·결합 허용 관계·다른 부품의 위치를 일부러 바꾸는 검사는 재계획 거부만 확인한 시험용 조작이며 성공적인 물리 조립으로 집계하지 않았다. 전략 비교 4개는 합성 로그 계약 검사로 물리 실행 횟수가 아니다.

기존 첫 기둥 정렬 복구 절차도 현재 코드로 새 물리 검증을 통과했다: `runs/step22_recipes/20261101T093235_612066Z_7ed8a41b`. 코드에 호환되는 등록본 1개를 확인했으며 자세한 ID는 [22C 보고서](STEP_22C_SKILL_RECIPES.md)를 따른다. 기존 장애물 없는 단일 결합 조건에만 유효하고 두 기둥 재계획을 학습한 등록은 아니다.

## 남은 범위

현재 정책은 허용된 동작을 고르는 규칙 정책이며 실제 LLM API 호출은 없다. 멀티에이전트 성능이나 학습 효과를 입증한 결과가 아니다. 정책이 자유롭게 파지점을 바꾸거나 임의 복구 코드를 작성하지 않는다. 고정된 개발 장면의 두 기둥까지 검증했으며 정책 재계획을 네 기둥·슬리브·덮개 전체로 확장하는 것은 후속 단위다.

API 키가 준비되기 전에도 변화된 장면 검증, 외부 계획 입출력 연동, 메모리·절차의 적용 조건 검사 등을 진행할 수 있다. 실제 LLM 선택·비용·성공률 비교는 API 설정 후 같은 관측·도구·전체 예산을 맞춰 별도로 수행한다. 실물은 이번 작업 범위에서 제외했다.
