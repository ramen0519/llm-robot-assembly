# 16C단계: API 없이 기존 ASAP/RedMax 백엔드로 우리 CAD 시험하기

작성: 2026-11-01. 기존 분해 프로젝트가 사용하는 네이티브 물리 백엔드를 직접 호출했다. 그 프로젝트의 LLM 의사결정이나 유료 API는 호출하지 않았다.

## 연결한 경계

`run_asap_native.py`는 현재 프레임 CAD를 별도 실행 폴더로 내보내고, 기존 WSL `ASAP-Ubuntu`의 `/opt/asap-research/ASAP`와 `/opt/asap-research/envs/asap/bin/python`을 호출한다. 확인한 소스 커밋은 `3727e716b57e0b508c4e9ecd9fefa6953e8f72da`다. 외부 프로젝트의 소스·기존 결과·키는 바꾸지 않았다.

기존 `heur-out` 후보 생성기와 DFS 계획기, RedMax 물리 검사를 사용한다. API 없는 기준선이며 LLM 플래너의 대체 성능을 주장하지 않는다. 고정 바닥판은 ID 0, 이동 부품을 잡는 그리퍼는 최대 1개, 전체 자세 전환과 로봇 파지·팔 경로 계획은 비활성이다.

우리 입력은 m 단위이지만 해당 네이티브 설정의 SDF 간격은 0.05이고 길이에 따른 고정 검사값이 있다. 따라서 OBJ 정점과 최종 배치의 이동량에 **동일하게 100배**를 적용한 별도 입력을 만들고 `source_length_scale_m = 0.01`로 기록했다. 원본 CAD와 m 단위 입력은 보존한다. 이것은 기하 형상 정규화이며, 밀도·중력·접촉 상수를 SI에 맞춰 재보정한 동역학 동등성 검증은 아니다. 실제 로봇 실행은 m 단위 MuJoCo에서 다시 검사해야 한다.

## 실행 중 발견해서 수정한 문제

1. Windows/WSL 공유 폴더에 SDF 캐시를 생성할 때 초기화가 오래 걸렸다. 입력을 바이트 단위 동일한 Linux 임시 폴더로 복사해 네이티브 캐시를 만들도록 변경했다. 원본 입력 해시를 다시 대조하고, 결과 JSON과 로그만 우리 실행 폴더에 저장한다.
2. 초기 자세가 미정일 때 `initial_state: null`을 쓰면 ASAP의 변환 로더가 `len(None)` 오류를 냈다. 네이티브용 변환 입력에서는 이 항목을 생략한다. 기존 미터 단위 원본은 그대로 보존한다.
3. 네이티브 실행이 예외로 끝난 경우를 단순히 '해 없음'으로 처리하면 안 된다. 현재 코드는 오류·중단을 `incomplete`로 기록한다. 이전 실패 실행의 파일은 수정하지 않고 이 차이를 보고서에 명시한다.

운영체제 `timeout`도 적용한다. 내부 계획 시간 제한만으로 개별 물리 시도와 초기화를 완전히 제한할 수 없기 때문이다. 시간 초과는 가능성 미확정이며 조립 불가능의 증거가 아니다. 강제 종료된 실행의 부분 SDF는 다음 실행에 재사용하지 않는다.

## 실제 실행

```powershell
uv run --locked python scripts/run_asap_native.py --parts 3 --timeout 120 --budget 12
uv run --locked python scripts/run_asap_native.py --parts 10 --timeout 300 --budget 30
uv run --locked python -m unittest discover -s tests -p test_native_asap.py -v
```

- 최초 공유 폴더 초기화 시험: `runs/asap_native/20261101T095214_402278Z_797e7dc9`, exit 124, 140.422초. 미완료.
- 초기화 300초 재시험: `20261101T095523_826823Z_30b3925d`, exit 124, 323.672초. 미완료.
- Linux 임시 입력으로 바꾼 최초 시험: `20261101T095706_392149Z_63ae2021`, 실제 검색에 진입한 뒤 `initial_state` 오류. 이 구버전 host 결과의 `native_no_solution` 표기는 기하 불가능이 아니라 로더 예외이며, `native_report.json`의 `stop_msg=exception`이 근거다.
- 입력 수정 후 3부품: `20261101T095751_655043Z_006a36d4`, **native_success**, 53.625초, 분해 순서 `[2, 1]`, 바닥판 0 유지. 경로·잔여 부품 안정성 검사 2단계와 추가 지지 없음 확인. 네이티브 `total_n_eval=1`에는 마지막 leaf 확장 검사가 포함되지 않으므로 물리 검사 1회라고 해석하지 않는다.
- 10부품, 내부 300초/탐색 예산 30: `20261101T095917_708451Z_5c9a6b2c`, exit 124, 324.688초. 후보 기둥 4개 거부 후 다음 검사 중 종료. 완성된 분해 계획 없음. 이 기록으로 10부품 분해 불가능이나 로봇 조립 실패를 주장하지 않는다.

3부품 결과는 역순 `[post_1, post_2]`이고 현재 로봇 스킬의 전제조건에 맞아 **조립 후보**로 분류했다. 해당 네이티브 실행에서 로봇을 움직인 것은 아니다.

입력 변환·후보 경계 단위 검사 **4개 PASS**, 최종 실행 0.151초. 정점과 배치의 단위 복원, 원본 불변, 추가 지지·옆 방향 제거·자세 전환·불연속/불완전 증거·입력 지문 불일치·조립 선행조건 위반 거부를 확인했다. 합성 계약 테스트를 네이티브 물리 성공에 포함하지 않는다.

## 후보를 받아들이는 기준과 한계

완전한 분해 순서, 정확한 입력 해시, 고정 베이스, 추가로 잡는 부품 없음, 순수 위쪽 제거, 자세 전환 없음, 역순의 로봇 선행조건을 모두 확인해야 `candidate`가 된다. 하나라도 어긋나면 `rejected`로 저장한다. `candidate`도 파지·IK·운반·삽입·현재 지지 상태의 별도 검증이 필요하며 `robot_execution_validated=false`를 유지한다.

이 어댑터는 새로운 네이티브 보고 형식 `asap_native_dfs/v1`을 사용한다. 기존 분해 에이전트의 explicit-action 보고서로 위장하거나, 실패한 검색에 임의 성공 순서를 채워 넣지 않는다. 10부품의 자동 검색 성공과 그 순서로 로봇이 조립하는 연결은 아직 이 결과로 입증되지 않았다.
