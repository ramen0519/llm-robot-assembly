# LLM 조립 시스템 긴급 비교 조사와 배터리팩 개선 판단

조사일: 2026-11-25. 대상: `C:/dev/llm-robot-assembly`, `codex/general-mesh-v2`, 기준 HEAD `cf8add83cb2704c61ab4dc928119fb5276f1d33f`와 보존한 미커밋 변경.

## 먼저 알아야 할 결론

**LLM을 조립 판단에 쓰는 방향 자체는 유지할 수 있다. 지금 우선 고쳐야 할 것은 LLM의 지능보다 실행 도구의 완성도와 검증 순서다.** 이는 아래 논문들을 비교하고 우리 실행 로그를 대조한 판단이다. 모든 실패의 원인이 동일하다고 확정한 것은 아니다.

논문에서 'LLM으로 로봇을 조립시킨다'는 말은 보통 다음 분담을 뜻한다.

1. 사람이 준비한 로봇 인터페이스 또는 학습한 조작 정책이 기본 동작을 담당한다.
2. LLM은 목표 해석, 잡을 부위·자세, 동작 조합, 복구 전략 또는 프로그램을 제안한다.
3. 별도 계산 도구가 좌표·IK·경로를 계산하고 제어기가 실제 동작을 실행한다.
4. 관측과 실행 결과로 성공 여부를 판단하고, 실패한 단계를 찾아 수정한다.

이 방식에서도 그리퍼가 들어갈 공간, 로봇의 도달 범위, 조립 중 지지, 접촉 제어는 해결해야 한다. 메모리가 많아져도 물리적으로 접근할 수 없는 조합을 해결해 주지는 않는다. 반대로, 제한된 탐색에서 경로를 못 찾았다는 것만으로 제품이 조립 불가능하다고 결론 내릴 수도 없다.

## 조사 범위와 읽은 수준

관련성이 높은 14개 연구를 아래에 비교했다. ASPIRE는 논문·공식 페이지뿐 아니라 고정된 공개 소스의 조립 예제와 실행 어댑터까지 확인했다. AGP는 논문·공식 결과·저장소 구조를 확인했다. 제조 분야 논문은 실제 로봇 동작을 검증했는지, 계획 정확도만 측정했는지 구분했다. RCIM의 MVUN-DP는 출판사 초록·공개 본문 발췌 범위로 읽었으며, 전체 구현을 재현했다고 주장하지 않는다.

논문의 수치는 서로 다른 제품·로봇·시작 상태·성공 기준에서 나온 값이다. 우리 배터리팩 성능과 직접 순위를 매기지 않는다. 아래 '적용 판단'은 조사자의 제안이며, 논문 저자가 우리 시스템을 평가한 결과가 아니다.

## 1. ASPIRE — 가장 직접적으로 참고할 디버깅·스킬 축적 방식

**무엇을 하는가:** 실행 프로그램을 작성하고, 호출별 실패 증거를 읽어 수정하고, 검증된 해결 방법을 재사용 지침으로 축적한다. 초기 논문은 호출 전후 이미지, API 입력·반환값, 파지·경로 증거를 남기는 실행 환경과 프로그램 탐색을 설명한다. 스킬에는 실패 특징, 적용 조건, 해결 절차, 필요하면 코드 예가 들어간다. 단순히 성공한 좌표 한 줄을 저장하는 것이 아니다. [논문, 2026 arXiv](https://arxiv.org/html/2607.00272v1)

**공개 코드에서 확인한 사실:** 조사한 커밋은 `fa00f0ef2bc1d91d594b9aa502c22133c9f538f7`이다. `nut_assembly_fix_code.py`는 관측 점군에서 너트 손잡이와 구멍을 구분하고, 네 가지 사각 대칭 설치 방향에 대해 위쪽·아래쪽 목표 IK를 먼저 검사한다. 이후 접근→잡기→들기→회전/운반→놓기→정착을 실행한다. 해당 예제의 움직임은 PyRoki IK와 interpolation 전략을 호출한다. Robosuite 어댑터 기본 제어기는 `JOINT_POSITION`이다. 따라서 ASPIRE의 모든 성공을 정교한 힘 제어기 덕분이라고 일반화하면 안 된다. [확인한 조립 코드](https://github.com/NVlabs/ASPIRE/blob/fa00f0ef2bc1d91d594b9aa502c22133c9f538f7/.claude/skills/iterative-debugging/robosuite/nut_assembly_fix_code.py), [어댑터](https://github.com/NVlabs/ASPIRE/blob/fa00f0ef2bc1d91d594b9aa502c22133c9f538f7/src/cap_harness/robosuite/adapter.py)

**최근 공개 스킬 등록 방식:** 제안자가 작성한 해결 지침을 별도 검증자가 읽고 재현한 뒤 승격한다. 개발에 사용한 작업에서 지침만으로 재현되었다는 것과 새로운 작업에도 일반화된다는 것을 따로 관리한다. 적용한 지침을 useful/misleading/wrong/not-applicable로 평가해 적용 조건을 다듬는다. [스킬 운영 문서](https://github.com/NVlabs/ASPIRE/blob/fa00f0ef2bc1d91d594b9aa502c22133c9f538f7/.claude/skills/iterative-debugging/skills/README.md)

**그대로 가져올 부분:** 호출 단위 기록, 원인 가설과 관측 사실 분리, 작은 프로그램 수정, 같은 조건 재시험, 지침만으로 재현되는지 확인하는 별도 시험. 초기에는 대규모 진화 탐색을 추가하지 않는다.

**주의:** 공개 페이지도 기본 API의 표현 범위, 비용이 많이 드는 탐색, 실제 환경 초기화·성공 판정의 한계를 명시한다. 최신 저장소 결과와 초기 논문 결과는 버전이 다르므로 섞지 않는다. LIBERO/Robosuite의 성공률은 13부품 밀집 배터리팩 완주율이 아니다. NVIDIA 소유 코드는 Apache-2.0이며 종속 자산의 조건은 별도다. [공식 페이지](https://research.nvidia.com/labs/gear/aspire/), [공개 저장소·라이선스](https://github.com/NVlabs/ASPIRE)

## 2. Agent as Policy — 실행 중 관측하고 프로그램을 바꾸는 방식

고정된 모델이 카메라와 로봇 상태를 확인하고, 필요하면 계산 프로그램을 작성하며, 움직임을 실행하고 결과를 다시 관측한다. 인터페이스가 Cartesian/관절 명령을 받아 IK와 궤적 실행을 담당한다. 조립 실험의 입력에는 사람 시연 영상과 설명이 있다. 8개 부품을 하나의 밀집 제품으로 조립한 것이 아니라 4개의 짝을 완성하는 과제라는 차이가 중요하다. [논문과 부록](https://arxiv.org/html/2609.12541v1)

공식 페이지에서 4쌍 조립은 8/10 성공, **성공 회차 평균** 37.2분·$16.62로 보고한다. 실패 회차까지 포함한 평균으로 해석하지 않는다. 이 숫자는 방법의 시간·비용이 무시할 수준이 아니라는 참고치이며 우리 실행 비용을 정당화하는 기준은 아니다. [공식 결과표](https://agent-as-policy-2026.github.io/)

우리에게 유용한 것은 '처음부터 끝까지 한 번에 계획'보다 관측→짧은 행동→재관측의 흐름이다. 다만 공개 코드는 YAM 로봇·카메라·전용 bridge에 연결되어 있으므로 UR3e용으로 그대로 실행할 수 없다. [공개 구현](https://github.com/agent-as-policy-2026/agent-as-policy)

## 3. VLM-MSGraph — 제조 조립에서 판단과 기하를 나눔

RCIM 94(2025), 102978. 상위 층은 부품 간 조립 관계와 순서를 다루고, 하위 층은 실제 물체의 3D 위치·공간 관계를 유지한다. AnyGrasp가 파지 후보를 생성하고 Grounding DINO/GroundedSAM-v2 결과로 대상 물체의 후보를 고른다. 접근 마지막 구간을 점점 작은 이동으로 나누는 설명도 있다. LLM 하나가 모든 파지·동작 계산을 대신하는 구조는 아니다. 127장 조립도면의 순서 평가와 실제 조립 실험은 다른 평가다. [저자 공개 논문](https://wangzuoxu.github.io/papers/Li%20et%20al_2025_Robotics%20and%20Computer-Integrated%20Manufacturing_VLM-MSGraph%20-%20Vision%20Language%20Model-enabled%20Multi-hierarchical%20Scene%20Graph%20for%20robotic%20assembly.pdf)

적용 판단: 우리도 CAD의 목표 관계와 현재 관측 관계를 구별해 관리하고, 파지 후보 생성기와 LLM의 전략 선택을 분리하는 것이 타당하다. AnyGrasp 설치만으로 현재의 손가락 닫힘·제어 문제까지 해결된다고 볼 근거는 없다.

## 4. MVUN-DP + LLM — 제조 스킬을 먼저 학습해 둠

RCIM 100(2026), 103263. LLM은 작업 계획을 담당하고, 실제 조작은 MobileViT+U-Net Diffusion Policy로 학습한 스킬이 담당한다. 도메인 무작위화와 데이터 증강을 사용하며 UR5·두 RGB 카메라·힘/토크 센서에서 평가했다. 출판사 자료는 8가지 조립 스킬과 평균 성공률 94.7%를 보고한다. 이는 범용 LLM에 CAD만 넣어 곧바로 얻은 성능이 아니라 **동작 데이터로 준비한 실행 계층**을 포함한 결과다. [출판사 자료](https://www.sciencedirect.com/science/article/pii/S0736584526000426)

적용 판단: 실행 계층을 먼저 검증한다는 구조는 가져온다. 급한 졸업 프로젝트에서 새 시범 데이터를 모아 전체 정책을 학습하는 방향으로 전환하는 것은 빠른 해결책이 아니다.

## 5. RWTH의 Embodied AI Agent Framework — 기존 로봇 소프트웨어 연결

CIRPe 2025, Procedia CIRP 139(2026), 59–65. 언어 모델이 도구를 호출하고, 물체 인식·Contact-GraspNet·ROS2·MoveIt2·MoveIt Task Constructor가 실행을 담당한다. 실험은 기본 명령, 케이블 집기, 장면 설명, 작업 기록/재생이다. 이 논문도 모든 제조 조립을 해결한 증거는 아니다. 기본 명령 해석 100%와 두 케이블 작업 성공 70%는 서로 다른 지표다. [공개 논문](https://publications.rwth-aachen.de/record/1029074/files/1029074.pdf?version=1)

적용 판단: 기본 동작을 전문 로봇 소프트웨어에 맡기는 것은 LLM의 의미를 없애지 않는다. 현재 MuJoCo/Mink/RRT를 보존하며 비교 가능한 인터페이스를 만드는 편이 당장 ROS2 전체 이주보다 작다.

## 6. CoRAL — 느린 판단과 빠른 접촉 반응의 분리

2026 arXiv. LLM은 목표 비용 함수와 접촉 전략을 만들고, MPPI 제어기가 반복 계산을 통해 실제 행동을 선택한다. 실패가 지속되면 느린 외부 루프에서 전략·계획용 물성 추정을 수정하며 성공한 전략을 검색해서 재사용한다. 실제 로봇 실험은 6대의 Vicon 카메라로 자세를 추적했다. FoundationPose만으로 모든 실물 관측을 처리했다고 읽으면 안 된다. [논문·부록](https://arxiv.org/html/2605.02600v1), [공식 페이지](https://sites.google.com/view/lira-coral)

적용 판단: 매 순간 모델을 호출하지 않고 로컬 실행기가 반응한다는 구분은 유용하다. MPPI 전체 이식은 계산·물성 동기화·제어기 검증이 추가되는 별도 과제다. 우리 정답 장면의 물성을 바꿔 성공을 만들어서는 안 된다.

## 7. FORGE-plus — 힘 제한을 유지한 복구 선택

2026 arXiv, 독립 연구자의 시뮬레이션 연구다. NVIDIA의 원래 FORGE 논문과 구별해야 한다. 고정 LLM은 힘 정보의 짧은 요약에서 미리 정해 둔 복구 동작을 선택하고, 빠른 실행 계층이 힘 상한을 지킨다. 삽입 정책은 학습하며 접근·운반·일부 복구는 scripted임을 구별한다. 실물 이전을 입증한 논문은 아니다. [논문](https://arxiv.org/html/2607.21227v1), [공개 구현](https://github.com/robot-team00/FORGE-plus)

적용 판단: 힘이 커졌다고 더 밀게 하는 대신, 후퇴·재정렬·재파지 중 가능한 전략을 고르는 구조를 참고한다. 우리 8N 검사 기준을 LLM 판단에 따라 올리는 방식은 채택하지 않는다.

## 우리 코드와 맞대어 확인한 차이

**자율성의 중요한 차이도 있다.** ASPIRE/AGP의 코딩 에이전트는 실행 도중 계산 함수와 동작 프로그램을 작성·수정한다. 현재 우리 내부 Astra는 정해진 행동 목록과 파지 자세 계약 안에서 제안한다. 지금 들기 높이·벌림 제어·설치 구간을 수정한 주체는 이 대화에서 개발하는 Codex이며, 실행 중인 조립 Astra가 스스로 공통 실행기를 고친 것이 아니다. 둘을 같은 '에이전트 학습'으로 보고하면 안 된다.

## 배터리팩에서 실제 확인한 문제와 수정

1. **접근하기 편한 벌림이 닫기에도 좋은 벌림은 아니었다.** 홀더 4는 85mm로 접근 공간을 넓히면 닫는 동안 손가락 뒷부분이 먼저 닿았다. 접근과 닫힘을 함께 비교하도록 수정했고, 후보 비교 시험에서 18.049mm가 선택되었다. 특정 폭 자체가 모든 부품의 정답인 것은 아니다.
2. **명령한 벌림과 실측 벌림이 달랐다.** 보정 후 별도 실제 시뮬레이션에서 10.049mm/28.997mm 요청에 대한 마지막 관찰 구간 최대 오차는 각각 약 0.0019mm/0.0066mm였다.
3. **잡은 물체가 접촉 중 조금 기울었다.** 마지막 구간을 10/6/3/1.5/0mm 남은 위치로 나누고, 현재 파지 상대변환을 다시 측정하도록 수정했다. 원래 미끄럼 기준은 초기화하지 않았다. 홀더 4의 실제 설치와 해제 후 검사를 통과했다.
4. **셀 5의 고정 100mm 들기 목표를 찾지 못했다.** 물리 명령 전 계획 실패에 한해서 100/80/65mm 후보를 검사하도록 바꾸었다. 80mm 들기가 실제로 성공했고 바닥 이격 50mm 기준은 유지했다.
5. **물체를 놓고 손을 뺀 뒤 시간 상한으로 끝났다.** 이를 파지 불가능으로 분류하지 않고, 모델·적분 상태·제어 상태의 해시를 검증해 남은 확인만 이어가는 경로를 추가했다. 재집기·순간이동 없이 셀 5와 기존 설치 부품을 같은 1초·501샘플 창에서 확인했다.

셀 5의 해당 창 최악값: XYZ 축별 약 0.094/0.042/0.106mm, 상대 회전각 약 0.029°, 경질 관통 약 0.435mm. 원래 한계인 축별 5mm·3°·0.5mm를 그대로 적용했다. 이 후속 확인으로 검증된 개발 분기는 3/4/5/6/10, 즉 설치 대상 12개 중 5개다. 이후 시도의 최신 상태는 `SEQUENCE_STATUS.json`을 확인한다.

이것은 여러 실패 분기를 보존하면서 이어 간 **scripted 개발 검증**이다. 처음 빈 장면에서 Astra가 한 번에 완주한 기록, 독립 평가, 새 제품 일반화 결과가 아니다. 이번 조사·후속 확인의 유료 모델 호출은 0회다.

## 우선 적용할 개발 순서

1. **기본 동작의 통과 시험을 제품 실행과 분리한다.** 벌림→접근→닫힘→들기→운반→설치→해제→후퇴 각각의 요구 입력과 성공 증거를 고정한다. 단계 시간 상한은 물리 실패와 별도로 기록한다.
2. **파지 하나를 전체 공정에 연결한다.** 시작 부위만 좋은 후보보다, 같은 파지로 설치·해제까지 가능한 후보를 우선한다. 계산상의 통과는 최종 성공이 아니며 현재 장면의 실제 동작으로 재확인한다.
3. **실패의 책임 층을 분류한다.** 잘못된 모델 응답, IK 탐색 미발견, 실제 충돌, 제어 추종, 접촉 중 미끄럼, 안정성 실패, 시간 소진을 분리한다. Python 도구 자체의 결함을 LLM이 계속 다른 좌표를 내며 덮도록 하지 않는다.
4. **ASPIRE식 지침을 작은 단위로 검증한다.** 관측 사실→원인 가설→변경한 항목→재시험 결과→적용 조건을 남긴다. 한 장면 통과는 그 장면의 근거이며, 같은 지침만으로 재현한 시험과 다른 형상으로 옮긴 시험은 별도다.
5. **실행기가 안정된 뒤 모델 판단을 다시 평가한다.** 조립/복구 역할과 기존 인터페이스는 보존하고, 동일 도구·예산으로 새 Astra 회차를 실행한다. 그전 개발 분기를 에이전트 성공률에 섞지 않는다.

이 순서는 새 제품마다 사람이 전용 Python 코드를 만드는 것을 최종 사용법으로 삼겠다는 뜻이 아니다. 현재 개발 중 찾는 수정은 공통 실행기와 공통 조건 생성기로 반영해야 한다. 다만 완성 CAD만으로 재질·체결력·스냅 변형·나사 체결·숨은 지그 요구가 모두 확정되는 것은 아니므로, 지원하지 않는 공정은 원인과 필요한 도구를 반환해야 한다.
