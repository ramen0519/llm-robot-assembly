# 12C: 부품을 잡은 상태에서 장애물을 우회하고 내려놓기

작성: 2026-11-01. 시뮬레이션 전용의 작은 모션 확장이다. [12B](STEP_12B_RRT_CONNECT.md)의 빈 그리퍼 우회에서, 실제 물체를 들고 움직이는 시험으로 확장했다.

## 무엇을 해결했나

로봇팔이 지나갈 수 있는 길이라도 손에 든 부품은 장애물에 걸릴 수 있다. 따라서 손끝 위치만 검사하면 부족하다. 이번 통과 기준은 **실제 접촉으로 상자를 집기 → 상자 때문에 막힌 경로 검출 → 현재 파지를 다시 확인 → 다른 경로 탐색 → 물리 운반 → 해제·후퇴 → 놓인 상태 확인**이다.

이 시험의 기본 전략은 규칙으로 지정한 `direct_then_rrt`다. 직선형 TCP 경로를 먼저 검사하고, `PLANNED_CONTACT`일 때만 한 번 다른 경로를 찾는다. 아직 LLM이 전략을 선택한 결과가 아니며 새로운 복구 방법을 스스로 생성하지도 않는다. 이후 에이전트가 호출할 수 있는 제한된 모션 도구를 먼저 검증한 것이다.

## 이번 코드의 역할

| 파일 | 맡는 일 |
|---|---|
| `scripts/loaded_transport.py` | 현재 파지와 운반 단계 확인, 직접 경로 검사, 충돌 예측 후 재관측과 RRT 대안 계획 |
| `scripts/run_loaded_detour.py` | 시험 장면 구성, 실제 집기·운반·놓기, FailureReport·측정값·이미지 저장 |
| `tests/test_loaded_transport.py` | 정상 물리 운반과 중단 조건, 강제 위치 변경·부착이 없는지 검사 |

IK와 탐색 알고리즘을 새로 작성하지 않았다. 기존 `joint_path_planner.py`의 **Mink 목표 IK + MIT 라이선스 motion-planners의 RRT-Connect**를 재사용한다. 출처·고정 커밋은 [12B 보고서](STEP_12B_RRT_CONNECT.md)와 `third_party/motion_planners/PROVENANCE.json`에 있다. 기존 `WorkcellMotion` 실행기와 `WorkcellVerifier` 판정 기준도 그대로 사용한다.

## 실제 흐름을 쉽게 풀면

1. 로봇이 상자를 양쪽 손가락의 접촉·마찰로 잡아 올린다. 현재 상자가 그리퍼에 대해 어디에 있는지 측정한다.
2. 상자를 목표 위치 위로 옮길 TCP 위치·방향을 계산한다. 이 계산은 물체를 실제로 옮기는 명령이 아니다.
3. 직접 경로를 계산용 복사본에서 검사한다. 각 후보 자세마다 로봇팔·그리퍼와 함께 상자의 예상 자세도 검사한다.
4. 장애물에 걸리는 후보를 발견하면 그 경로를 실행하지 않는다. 실패 코드·실제 상태·충돌 예상 후보를 기록한다.
5. 현재 파지를 다시 확인한다. 위치·속도·입력·장애물·시각이 바뀌었으면 기존 상태를 전제로 계속하지 않는다.
6. Mink로 목표의 관절 자세를 구하고 RRT-Connect로 중간 길을 찾는다. 반환된 경로도 관절당 최대 0.25도 간격으로 다시 검사한다.
7. 시간 정보를 붙인 경로를 기존 모터 제어기로 실행한다. 실제 물리 계산은 2ms마다 진행하며 금지 접촉, 양쪽 파지, 미끄러짐, 속도 등을 계속 검사한다.
8. 목표 위에 도착하면 기존 `place`가 내려놓기·그리퍼 열기·후퇴를 한다. 최종 1초의 부품 위치·방향·지지·정지 상태로 성공을 판정한다.

계산용 복사본에서는 부품의 예상 위치를 계산하지만, 실행 중 부품은 MuJoCo 접촉과 마찰로만 움직인다. 강제 부착이나 순간이동으로 성공시키지 않는다.

## 시험 장면과 공정한 해석

개발용 상자 1개와 빨간 구형 장애물 1개를 쓴다. 실제 집기를 마친 뒤, 직접 경로의 중간에서 **상자만 걸리는 위치**를 계산해 시험 장애물을 배치한다. 장애물은 반지름 10mm, 충돌 여유 6mm이며 이후 움직이지 않는다. 이는 통제된 반례 구성으로, 처음 보는 임의 장애물에 대한 일반화 시험이 아니다.

장애물은 MuJoCo의 위치 고정 물체다. 실제 지지대나 움직이는 장애물을 재현한 장면은 아니다. 제품 부품·로봇의 상태는 이 시험 장면 구성 과정에서도 바꾸지 않는다.

중간 후보에서 검출된 쌍은 `loaded_obstacle_geom`과 `workcell_part_part_a_geom`이었다. 별도의 계산용 복사본에서 상자만 치운 같은 중간 자세는 로봇·그리퍼 충돌 검사를 통과했다. 이는 **그 중간 자세**에 대한 비교이며, 부품을 제외한 전체 경로가 안전하다는 주장이나 그 경로를 실제 실행한 결과가 아니다.

## 실행 방법

```powershell
cd C:\dev\llm-robot-assembly
# 실제 집기 → 직접 경로 거부 → RRT 우회 → 놓기. 화면 창 없이 PNG 저장
uv run --locked python scripts/run_loaded_detour.py --snapshots
# 같은 장애물에서 직접 경로만 허용: 움직이기 전에 실패하는 반례
uv run --locked python scripts/run_loaded_detour.py --strategy direct
# 신규 검사와 기존 관련 검사
uv run --locked python -m unittest discover -s tests -p test_loaded_transport.py -v
uv run --locked python -m unittest discover -s tests -p test_joint_path_planner.py -v
uv run --locked python -m unittest discover -s tests -p test_pick_place.py -k carried_part -v
```

기본 실행은 `success`, 직접 경로만 사용하는 반례는 `PLANNED_CONTACT`와 종료 코드 1이 예상 결과다. 이 반례도 집기까지는 실제로 수행하며, 장애물을 통과하는 운반은 시작하지 않는다. `--strategy rrt`는 직접 TCP 경로 시도 없이 목표 IK와 관절 경로 검사·탐색을 요청한다. RRT 내부에서 관절 직선 경로가 통과하면 탐색 없이 그 경로를 사용할 수 있다.

## 검사한 실패 조건

- 직접 경로만 요청하면 사전 충돌 판정 이후 물리 시각·로봇·부품·모터 입력이 그대로 유지되고 파지도 유지된다.
- 사전 검사 이후 외부 입력이 달라지면 RRT 재계획이나 실행을 진행하지 않는다.
- 탐색 예산을 소진하면 `MOTION_PATH_NOT_FOUND`로 멈춘다. 가능한 경로가 없다는 증명이 아니라 이번 예산에서 찾지 못했다는 뜻이다.
- 실제 파지가 없거나 삽입·접촉 단계이면 이 운반 도구를 거부한다.
- 운반 시작 때 그리퍼가 열리는 고장을 넣으면 실제 접촉 상실을 `PART_LOST`로 감지하고 놓기 단계로 넘어가지 않는다.
- 정상 실행 중 모든 실제 `mj_step`·`mj_forward` 전후를 감시해 `qpos/qvel` 강제 변경이 없음을 확인했다. 부품은 자유 관절이며 추가 equality 부착, 중력 해제, 외력이 없었다. 물리 기록 시간 간격도 최대 2ms였다.

신규 5개 검사 중 첫 실행은 4개 통과, 1개는 **시험 종료 후 닫힌 CSV에 다시 기록하려던 테스트 코드 오류**였다(69.187초). 종료 후 확인을 검증기 직접 읽기로 수정하여 해당 검사 1개를 재실행했고 통과했다(10.101초). 정상 운반이나 충돌 판정 코드를 완화한 수정은 아니다. 결과적으로 신규 5개를 각각 통과했으며 수정 후 전체 5개를 한 번에 다시 돌린 것은 아니다.

기존 RRT 검사 4개(7.881초), 운반 부품 경로 충돌 검사 1개(5.335초)도 다시 통과했다. 신규·관련 검사 10개가 각각 통과한 범위이며 전체 저장소 회귀 검사를 이번에 다시 수행했다고 주장하지 않는다. 로그는 Git 제외 경로 `.scratch/test_loaded_transport.log`, `.scratch/test_loaded_transport_direct_fixed.log`, `.scratch/step12c_rrt_regression.log`, `.scratch/step12c_carried_regression.log`에 있다.

## 현재 적용 범위와 다음 연결

자유 공간의 `transport_transfer`, `place_transfer`, `insert_transfer`라는 허용 단계에서만 요청할 수 있다. 시작할 때 양쪽 파지와 테이블 위 50mm 이상의 여유를 확인하며 결합 접촉 검사 모드에서는 거부한다. 이름에 `insert_transfer`가 있어도 삽입 중 하강·접촉 동작에 쓰는 것은 아니다.

현재 검증 범위는 상자 하나·고정 장애물 하나·지정 장면·seed 3이다. RRT는 경로 내내 TCP 방향을 수직으로 유지하지 않는다. 이번에도 약 19도 기울었으므로 자세를 유지해야 하는 부품이나 정밀 삽입에는 그대로 적용할 수 없다. 충돌 여유 6mm와 이산 샘플 검사는 임의의 파지 오차나 연속 경로 안전성을 보장하지 않는다. 궤적은 기존 관절 보간이며 산업용 가속도·jerk 제한까지 구현한 것이 아니다.

10부품 전체 조립의 운반 구간에 자동 연결한 상태는 아니다. 이후 각 부품의 형상·파지·이미 조립된 구조물·허용 기울기를 포함해 검증해야 한다. 실제 LLM 연결부는 별도로 준비되어 있으나 제공자·모델·예산·키 설정이 없어 라이브 호출은 하지 않았다. 실물 로봇은 이번 범위에서 제외한다.
