# STEP 52 · 실제 Astra 시작에서 발견한 입력 크기 문제 수정

2026-11-26. 사용자 UI의 임시 키가 살아 있는 상태에서 실제 provider 연결을 확인했다. 키 값은 읽거나 파일에 저장하지 않았다.

## 확인된 실패

첫 실행 `8cc38de28de24974ab76285ab2a4ce8c-53d2de07`은 CAD 처리, native 분해와 완성 기준 장면·초기 안정성 검사까지 진행했다. 첫 판단 전에 실제 입력 토큰 계수 API가 **12,047토큰**을 반환했고, 요청당 8,000 한도 때문에 `Counted input exceeds the per-request limit`으로 종료됐다.

모델 생성 **0회**, 토큰 계수 HTTP 조회 **1회**, 기록된 추정 비용 **$0**, 설치 **0/2**다. 인증된 Astra 판단이 생긴 실행으로 집계하지 않는다. 전체 pipeline 94.640초이며 당시 자료와 영상·로그를 그대로 보존했다.

원인은 18개 파지 후보마다 같은 기하 검사 범위·미실행 상태·주의 설명을 반복해서 보내던 점이다. 별도로 후보에 들어 있던 선택 가능한 대체 파지 자세(`geometry_pose_alternatives`)가 최종 모델용 표에서는 빠지는 문제도 확인했다.

## 수정

- `scripts/assembly_v2/packets.py`는 후보별 검사와 동작 정보의 공통 항목을 한 번 저장하고, 후보 행에는 다른 값만 둔다. 읽기 규칙을 함께 보낸다. 후보 18개를 줄이거나 새 후보를 만든 것으로 표시하지 않는다.
- 공통 값과 후보 행을 합치면 기존 6자리 유효숫자 표시 형식의 모든 검사·동작 정보가 복원된다. 실제 후보 원본과 실행 좌표는 바꾸지 않는다.
- 선택 가능한 대체 자세와 그 출처·미검증 표시도 모델에 전달한다. 동일한 대체 자세 설명은 공통 항목으로 묶는다.
- `not_run`, 실패 이유, 검사 출처, `physical_success=false`를 유지한다. 실패 접촉·완료 측정값과 이전 대화 기록을 잘라내거나 성공으로 바꾸지 않는다.
- `config/llm.astra-high.toml`의 요청별 읽기 상한을 **8,000 → 24,000**으로 조정했다. 여러 동작과 실패 피드백이 공유 이력에 쌓이는 것을 수용하기 위한 상한이다. **전체 361,728토큰, 생성 36회, 출력 2,048토큰/회, 회차 비용 $1.50는 유지**했다. 이는 더 큰 비용 한도를 부여하는 변경이 아니다.
- `tests/test_v2_candidate_packet.py`에 후보별 복원, 다른 실패 상태 보존, 선택 가능한 대체 자세 전달 검사를 추가했다.

## 검증

기존 실제 MuJoCo 실행 `prototype_20261126_raw_full01`의 관측 5개로 복원을 검사했다. 세 파지 관측 각각 18개, 모든 후보의 검사·동작 정보·대체 자세가 복원됐다. 첫 관측의 JSON 문자 수는 **33,424 → 13,306**, 약 60.2% 감소했다. 이는 문자 수이며 토큰 감소율과 구별한다.

전체 회귀 검사 **128개 통과, 5.664초**. 물리 조건과 실행기의 동작은 변경하지 않았으며 수정된 입력을 사용하는 실제 통합 실행을 별도로 시작했다.

재실행 `0a6c0d202a6d40868b924909023a811f-42ed73bf`의 첫 실제 계수는 **7,267토큰**이었다. 이전 12,047 대비 약 **39.7% 감소**다. Astra high의 실제 첫 응답을 받았고, 모델은 Python 표면 후보 `1:r1:g65`를 선택했다. 이 좌표를 모델이 새로 생성했다고 주장하지 않는다. 첫 응답의 생성 1회, 사용량 입력 7,267/출력 308(추론 176 포함), 설정 단가 기준 비용 $0.1059였다. 최종 사용량은 통합 결과 보고서를 따른다.

재실행은 새 장면이며 첫 실패 실행의 물리 상태를 성공 장면으로 덮어쓰지 않았다. 앞서 쓴 실행 시간을 제외해 **805초**로 설정했다. 첫 실행의 소요 시간 94.640초와 재실행의 실행 한도 805초의 합은 900초 이내이고 합계 비용 상한은 $1.50다. 종료 후 영상/저장까지 포함한 실제 합계는 STEP 53을 따른다. 코드 수정/검사에 걸린 작업 시간은 별도다. 영상·마지막 기록 단계의 시간도 최종 결과에서 확인한다.
