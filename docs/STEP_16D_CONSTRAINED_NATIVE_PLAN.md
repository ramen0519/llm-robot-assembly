# 16D단계: 로봇 선행조건을 반영한 10부품 네이티브 분해 검증

작성: 2026-11-01. API 없이 기존 ASAP/RedMax에 우리 로봇의 선언된 제약을 연결했다.

## 왜 후보를 제한했나

제약 없는 `heur-out`은 덮개가 있는 상태에서 기둥·슬리브 제거를 먼저 시험했다. 16C의 300초 시험에 이어 600초 시험(`runs/asap_native/20261101T100507_577231Z_53969240`)도 완전한 계획을 반환하기 전에 종료됐다. 이 실행은 exit 124, 실제 경과 642.391초이며 미완료다. WSL 시작 시간은 내부 제한에 포함되지 않는다. 로그에는 8개 초기 후보 거부 후 덮개와 일부 슬리브의 성공이 남아 있다.

별도 진단에서는 사람이 선언한 역순으로 덮개·슬리브 하나의 검사를 통과했지만 180초 제한 안에 전체 순서를 끝내지 못했다. `reference_probe.json`은 `incomplete`이고 자동 계획 성공에 포함하지 않는다. 이 기록은 원인 구분용이며 새로운 실행 기능의 성공 증거를 대신하지 않는다.

현재 로봇에는 이미 “슬리브보다 해당 기둥을 먼저 조립”, “덮개보다 내부 부품을 먼저 조립”이라는 관계가 있다. 이 관계를 뒤집으면 덮개가 남아 있을 때 내부 부품을 제거하지 않도록 후보를 제한할 수 있다. `--respect-robot-prerequisites`는 이 **사람이 제공한 관계**를 사용한다. CAD만 보고 결합 관계를 추론한 것으로 표현하지 않는다.

## 구현

기존 ASAP 후보 정렬과 DFS 탐색은 유지한다. 우리 쪽 wrapper가 현재 남은 부품이 필요로 하는 부품을 제거 후보에서 제외한다. 알려지지 않은 부품 ID와 순환 의존성은 거부한다. 후보가 남아도 실제 경로·중간 안정성은 ASAP/RedMax가 새로 검사한다.

선행조건 JSON의 내용과 지문을 입력 manifest와 네이티브 보고서 양쪽에 기록하고 후보를 받을 때 대조한다. 조건이 바뀌면 같은 결과로 취급하지 않는다. 제약 없는 탐색과 제약을 추가한 탐색은 입력 정보가 다르므로 동일 정보의 알고리즘 성능 비교나 LLM 효과 비교가 아니다.

## 실제 실행

```powershell
uv run --locked python scripts/run_asap_native.py --parts 10 --timeout 600 --budget 30 --respect-robot-prerequisites
uv run --locked python -m unittest discover -s tests -p test_native_asap.py -v
```

기록: `runs/asap_native/20261101T101241_037230Z_6897a2be`.

- **native_success**, 바닥판 0을 남기는 완전한 분해 9단계.
- 순서: `9 → 7 → 8 → 4 → 3 → 6 → 2 → 5 → 1`.
- 각 단계의 경로·잔여 안정성 검사 통과, 추가로 잡아주는 부품 없음, 전체 자세 전환 없음.
- API 0회, 실제 경과 467.390초. 다른 시험과 CPU를 공유했으므로 속도 성능 수치로 쓰지 않는다.
- 네이티브 통계는 `total_n_eval=8`. 별도로 마지막 leaf 제거도 검사하므로 완료된 선택 경로는 9단계다.
- 결과 상태는 `candidate`, `robot_execution_validated=false`.
- 확장한 네이티브 계약 검사 **5개 PASS**, 0.112초. 기본 입력·거부 경계에 더해 로봇 의존성 필터, 순환/미지 ID, 조건 지문 불일치를 검사했다.

역순 조립 후보는 다음과 같다.

`post_1 → sleeve_1 → post_2 → sleeve_2 → post_3 → post_4 → sleeve_4 → sleeve_3 → cover`

현재 로봇 입력 경계에서 이 10부품 후보의 CAD·좌표·선행조건도 다시 검사할 수 있다. 그 검사는 모터 명령이나 9개 부품의 로봇 조립을 의미하지 않는다. 실제 외부 후보 연결의 작은 물리 시험은 [16E](STEP_16E_PLANNER_TO_ROBOT.md)에 별도로 기록한다.

기존 전체 MuJoCo 조립은 기둥 4개를 먼저 설치하는 순서다. 위 외부 후보의 순서는 다르므로 기존 전체 성공을 이 후보의 실행 성공으로 복사하지 않는다. 정규화된 RedMax 물리와 m 단위 MuJoCo 로봇 물리도 같은 검증으로 취급하지 않는다.
